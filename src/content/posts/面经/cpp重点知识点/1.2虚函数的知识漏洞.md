## 先复习这一版：三个场景串起 48 个考点

**只记一条故事线：创建一个 Boss → 用角色接口调用它 → 给它增加多个接口 → 识别它的类型 → 接入 UE → 分析每帧性能 → 销毁它。**

下面用三个场景建立记忆入口。第一个是主例，第二个只改变继承结构，第三个把同一套“角色攻击”搬进 UE。纯虚函数等追问直接修改主例，不再另起一套人物和类名。原来的逐题详解保留在后面，忘了哪个点再按题号查。

先背这句：**静态类型管“能不能调、选哪个签名、补什么参数”，动态类型管“虚函数最后执行谁”；构造析构期间，还要看当前进行到哪一层。**

### 场景一：一个 Boss，串起调用规则、对象布局和生命周期

#### 1. 主例：先认识同一组角色

这是教学代码，构造和析构中调用 `Attack(0)` 只用于观察分派规则。

```cpp
#include <iostream>
#include <typeinfo>

class Character {
public:
    int hp = 100;
    Character() { Attack(0); }
    virtual ~Character() { Attack(0); }

    virtual void Attack(int damage = 10) {
        std::cout << "Character:" << damage << '\n';
    }
    virtual void Idle() { std::cout << "Character::Idle\n"; }
    virtual Character* Self() { return this; }
    void Kind() { std::cout << "Character::Kind\n"; }
    void Skill(int) { std::cout << "Character::Skill(int)\n"; }
    void Skill(double) { std::cout << "Character::Skill(double)\n"; }
    void Hit() { OnHit(); }

private:
    virtual void OnHit() { std::cout << "Character::OnHit\n"; }
};

class Boss final : public Character {
public:
    Boss() { Attack(0); }
    ~Boss() override { Attack(0); }
    void Attack(int damage = 20) override {
        std::cout << "Boss:" << damage << '\n';
    }
    Boss* Self() override { return this; }
    void Kind() { std::cout << "Boss::Kind\n"; }
    void Skill(double) { std::cout << "Boss::Skill(double)\n"; }
    virtual void Roar() {}

private:
    void OnHit() override { std::cout << "Boss::OnHit\n"; }
};
```

`Boss boss; Character* p = &boss; Character& r = boss;` 是后续所有问题的起点。`p` 的静态类型是 `Character*`，完整对象的动态类型是 `Boss`。

#### 2. 先预测调用结果：一张表分清所有“绑定”

以下各行均在 `boss` 构造完成后执行，结果不含构造、析构的额外输出。

| 表达式 | 结果 | 由此回忆的考点 |
| --- | --- | --- |
| `p->Attack()` | `Boss:10` | 编译期选基类默认参数，运行期选 Boss 实现 |
| `boss.Attack()` | `Boss:20` | 换了静态类型，默认参数也换了 |
| `r.Attack(7)` | `Boss:7` | 引用同样支持动态绑定；参数已显式给出 |
| `p->Character::Attack()` | `Character:10` | 显式类名限定会抑制虚分派 |
| `p->Idle()` | `Character::Idle` | 未重写的槽位沿用基类实现 |
| `p->Kind()` / `boss.Kind()` | `Character::Kind` / `Boss::Kind` | 非虚函数由静态类型决定，派生同名函数隐藏基类函数 |
| `p->Skill(1)` | `Character::Skill(int)` | 基类作用域内两个 `Skill` 重载，编译期选参数更匹配的版本 |
| `boss.Skill(1)` | `Boss::Skill(double)` | 派生同名声明隐藏基类整组 `Skill`，`1` 转成 `double` |
| `p->Hit()` | `Boss::OnHit` | 公共非虚入口调用私有虚钩子：NVI；`private` 不阻止重写 |
| `p->Self()` | 执行 `Boss::Self()`，表达式类型仍为 `Character*` | 协变返回：实现可返回 `Boss*`，调用方仍按基类声明看返回类型 |
| `boss.Self()` | 返回 `Boss*` | 通过派生接口调用，得到更具体的返回类型 |
| `p->Roar()` | 编译错误 | 基类接口没有这个成员，动态类型不能扩展编译期可见接口 |

**重载选参数，隐藏挡名字，重写换实现。** 如果在 `Boss` 的 `public` 中加入 `using Character::Skill;`，基类重载重新参与选择，`boss.Skill(1)` 就调用 `Character::Skill(int)`。

把 `Skill(int)` 改成虚函数，也不会让 `Boss::Skill(double)` 成为重写，因为参数不同。给后者加 `override` 会报错，正好暴露这个误解。

默认参数的精确说法是：**编译期选择默认参数表达式；表达式本身可能在运行时求值。** 不建议在重写时改默认参数。

#### 3. 再问“为什么”：对象、虚表、代码分开记

下面是典型单继承的概念图，省略 ABI 的实际排列、析构入口和调整桩等细节。

```text
boss 对象                         Boss 对应的共享虚表
┌──────────────────┐             ┌─────────────────────────┐
│ vptr ────────────┼────────────→│ Attack → Boss::Attack   │
│ hp = 100         │             │ Idle   → Character::Idle│
└──────────────────┘             │ Self   → Boss::Self     │
                                 │ OnHit  → Boss::OnHit    │
另一个 Boss：自己的 vptr ───────→│ Roar   → Boss::Roar     │
                                 └───────────┬─────────────┘
                                             ↓ 函数入口
                                      代码区中的机器指令
```

沿着 `p->Attack()` 回答底层原理：

1. **编译期**：按 `Character*` 查找成员、检查访问权限、做重载决议、选默认参数；典型 ABI 中确定调用所用的虚表槽位。
2. **运行期**：从 `p` 指向的基类子对象取得 `vptr`，找到相应虚表部分，读取 `Attack` 的入口，执行最终重写者 `Boss::Attack(10)`。
3. **优化后**：如果编译器能证明目标就是 Boss，可以去虚化为直接调用，甚至内联，语言层面的结果不变。

| 面试问法 | 用这个对象回答 |
| --- | --- |
| `vptr` 与 `vtable` 属于谁？ | `vptr` 通常在对象内；同类型、相同布局角色的对象共享对应虚表 |
| 分别放在哪里？ | `vptr` 跟着对象所在内存走；虚表通常在静态数据区，常见为只读或重定位后只读；函数机器码通常在 `.text` |
| 什么时候准备？ | 编译器生成虚表数据，链接和加载处理必要的地址解析、重定位；运行时构造代码初始化或更新 `vptr` |
| 1000 个 Boss 有多少张表？ | 典型单继承下是 1000 个对象各有一个 `vptr`，共享一组对应的虚表数据 |
| 多加几个虚函数会怎样？ | 通常增加表中槽位，不再增加对象的 `vptr`；表和函数体不直接计入 `sizeof` |
| `sizeof(Character)` 大约多少？ | 常见 64 位 ABI、默认对齐下：8 字节 `vptr` + 4 字节 `hp` + 4 字节填充，常见为 16；不是标准保证 |
| 继承来的槽位怎样变化？ | 未重写保留，重写替换，新虚函数通常追加；这是布局记忆法，不是每次调用都复制虚表 |

**表里存入口，代码在代码区；对象带指针，同类共享表。** `vptr` 指向虚表的地址点，不保证是整张表的物理起始地址。C++ 标准规定多态行为，没有强制要求采用这一套布局。

若临时去掉 `Boss` 的类级 `final`，增加一个不重写 `Attack` 的 `EliteBoss : public Boss`，它的最终重写者仍是 `Boss::Attack`。典型槽位直接关联这个入口，不需要沿 `EliteBoss → Boss → Character` 逐张找表。

#### 4. 对象出生、使用、销毁：一条时间线

```text
new Boss
  → 先分配存储
  → Character 构造体：Attack(0) → Character:0
  → Boss 构造体：Attack(0)      → Boss:0
  → 构造完成：p->Attack()       → Boss:10
delete p（p 必须来自这次 new，基类有虚析构）
  → Boss 析构体：Attack(0)      → Boss:0
  → Character 析构体：Attack(0) → Character:0
  → 释放存储
```

**建到谁，就按谁分派；拆到谁，就按谁分派。** 典型实现会按阶段设置相应 `vptr`；不是新造三个独立对象，也不是基类析构时虚指针突然消失。生命周期结束后不能继续使用对象。

构造函数不能是虚函数：创建时必须确定具体类型和布局，构造函数负责建立这个对象，不能依靠尚未建立的对象多态来选择构造目标。但构造体内可以调用普通虚函数。

基类需要虚析构的关键是**是否允许通过基类指针销毁派生对象**。本例中删除 `virtual ~Character` 的 `virtual`，还需删除 `~Boss` 的 `override` 才能编译；随后 `delete Character*` 指向的 `new Boss` 就是未定义行为，不能断言“一定只执行基类析构”。其他虚函数不会自动把基类析构变虚。常用设计是公有虚析构，或受保护非虚析构来禁止外部这样删除。

再改变传递方式：`Character copy = boss; copy.Attack();` 输出 `Character:10`。这是新建了一个真正的 `Character`，只复制基类部分，发生**切片**；`Character& r = boss` 仍引用原来的 Boss。函数按值接收 `Character` 也会切片。

#### 5. 面试官改声明：只在主例上做变体

下面各变体独立理解，不要同时叠加到主例上。

| 改动或追问 | 必须记住的结论 |
| --- | --- |
| 派生 `Attack` 不写 `virtual` | 仍是虚函数；虚属性沿重写继承。`override` 可省略，但建议保留以检查签名 |
| `Attack` 加 `override final` | 检查重写正确，并禁止后续重写该函数；类上的 `final` 则禁止继承整个类 |
| 基类为 `virtual int Damage() const & noexcept;` | 派生重写要匹配名字、参数、cv 和引用限定符；异常规格不能更宽松，不能去掉这里的 `noexcept` |
| 修改返回类型 | 需相同或满足协变规则：类的指针/引用，继承可访问且无歧义等；对象值、`unique_ptr` 等不支持这种协变 |
| 把 `OnHit` 改成 `protected` | 仍可重写，派生类还可直接调用基类实现；`private` 时可重写但不能直接访问基类私有实现 |
| 基类函数公有、派生重写私有 | 经基类公共接口可以虚调用到私有重写；直接经派生类型调用则要检查派生访问权限 |
| 静态函数能虚吗？ | 不能：没有对象的 `this`，不参与对象虚分派 |
| 成员函数模板能虚吗？ | 不能直接声明为虚函数；模板类里的普通成员函数可以是虚函数 |

**纯虚变体**：把 `Character::Attack` 改为声明 `virtual void Attack(int damage = 10) = 0;`，原来的函数体移到类外定义 `void Character::Attack(int damage) { /* 公共实现 */ }`。

- `Character` 仍是抽象类，不能实例化；`Boss` 已提供非纯虚重写，仍可实例化。尚未提供全部非纯虚最终重写的派生类仍是抽象类。
- 纯虚函数可以有定义；`boss.Character::Attack(7)` 是显式限定调用，可以复用这个定义。
- **先移除本例基类构造和析构中的 `Attack(0)`，再运行此变体**：当前层仍为纯虚时，对正在构造或析构的对象直接或间接进行纯虚的虚调用是未定义行为，即使有类外定义也一样。若有定义，显式 `Character::Attack(0)` 抑制虚分派则可以调用它。[标准草案：抽象类规则](https://eel.is/c++draft/class.abstract)
- 因为基类变成抽象类，上面的 `Character copy = boss` 此时会编译失败；切片例使用原始主例。

**纯虚析构变体**：只把析构改为 `virtual ~Character() = 0;`，并在类外提供 `Character::~Character() {}`。这也能让基类抽象，但析构链必须执行基类析构，因此必须有定义；派生析构自动重写基类虚析构，无须为了满足“纯虚”而一定手写派生析构。

记忆：**纯虚要求具体类提供非纯虚最终重写，有函数体仍然纯；纯虚析构还必须有函数体供析构链执行。**

#### 6. “执行谁”之后，再问“它是谁”：RTTI

仍然用构造完成的 `Boss boss; Character* p = &boss;`。

| 表达式 | 结果或用途 |
| --- | --- |
| `typeid(p) == typeid(Character*)` | `true`，问的是指针表达式类型 |
| `typeid(*p) == typeid(Boss)` | `true`，多态对象表达式可识别动态类型 |
| `dynamic_cast<Boss*>(p)` | 成功，返回指向同一 Boss 的指针 |
| `static_cast<Boss*>(p)` | 本例动态类型有保证，因此合法；它本身没有运行时检查 |
| `Character normal; p = &normal; dynamic_cast<Boss*>(p)` | 失败，返回 `nullptr` |
| `dynamic_cast<Boss&>(*p)`，此时 `p` 指向 `normal` | 失败，抛 `std::bad_cast` |
| `static_cast<Boss*>(p)`，此时 `p` 指向 `normal` | 错误向下转换是未定义行为，不会帮你检测或返回空指针 |

RTTI 是运行时类型信息，`typeid` 返回 `std::type_info` 的引用；类型描述数据通常共享，具有静态存储期。典型实现把 RTTI 与虚表关联，**虚表可以保存指向类型描述的指针，类型描述不等于虚表本身**。

需要运行时检查的向下、横向 `dynamic_cast` 要求源对象属于多态体系，还会检查继承的访问性和歧义，必要时调整指针。普通向上转换不必做这类动态类型检查。

关闭 RTTI 后，普通虚调用仍能工作；需要类型信息的向下/横向转换受限，`typeid` 的限制取决于编译器。不要说“所有 `dynamic_cast` 都失效”：GCC 的 `-fno-rtti` 仍允许无歧义向上转换以及向 `void*` 的转换。[GCC 官方选项说明](https://gcc.gnu.org/onlinedocs/gcc/C_002b_002b-Dialect-Options.html)

记忆：**虚表回答“做什么”，RTTI 回答“是什么”；指针失败给空，引用失败抛异常。**

### 场景二：Boss 有多个接口，串起偏移、Thunk、横向转换和虚继承

#### 1. 两个接口：一个完整对象，多个基类子对象

这是独立于场景一的第二个继承结构。`MultiBoss` 就是同时能攻击和渲染的 Boss。

```cpp
#include <iostream>

struct Fighter {
    virtual ~Fighter() = default;
    virtual void Attack() {}
};
struct Drawable {
    virtual ~Drawable() = default;
    virtual void Draw() {}
};
struct MultiBoss : Fighter, Drawable {
    int hp = 100;
    void Attack() override {}
    void Draw() override { std::cout << hp << '\n'; }
};

// 以下放入 main：
// MultiBoss boss;
// Fighter* pf = &boss;
// Drawable* pd = &boss;
// pd->Draw();                              // 100
// Drawable* side = dynamic_cast<Drawable*>(pf); // 横向转换成功
```

```text
一个 MultiBoss（典型布局示意）
├─ Fighter 子对象：vptr_F   ← pf
├─ Drawable 子对象：vptr_D  ← pd，可能与 &boss 地址不同
└─ hp = 100

pd->Draw()
  → Drawable 子对象的 vptr
  → 相应虚表槽位中的入口
  → Thunk：必要时把 Drawable* 调整成 MultiBoss* 作为 this
  → MultiBoss::Draw() 正确读取 hp
```

这里通常有**两个 `vptr`**，不是“两个基类加自己一共三个”；派生类可与主要多态基类共享一个 `vptr`。数量取决于多态子对象、继承结构和 ABI，既不是虚函数个数，也不是简单的基类个数。

如果某个典型布局中完整对象地址为 `0x1000`，`Drawable` 子对象地址为 `0x1008`：向上转换定位它是 `+8`，通过它调用派生实现所需的 `this` 调整是 `-8`。**先定位接口，再把 this 调回实现需要的位置。** 偏移值仅用于理解，不是本代码的实际布局保证。

Thunk 是编译器生成的调整桩：必要时修正 `this`，协变返回等情形还可能修正返回指针，然后转交目标实现；它不负责再沿继承链查虚表。

`dynamic_cast<Drawable*>(pf)` 是横向转换：RTTI 确认同一完整对象里存在合法的公共目标子对象，然后返回调整后的地址。若 `pf` 指向一个独立 `Fighter`，转换就失败。**转换成功不要求目标类型等于完整对象的动态类型。**

#### 2. 同一个多接口场景，增加共同祖先：菱形继承

只改变第二个场景的继承结构；下面的定义替换上面的三组类，不能同时重复定义。

```cpp
struct Entity {
    int hp;
    explicit Entity(int value = 100) : hp(value) {}
    virtual ~Entity() = default;
    virtual void Update() {}
};
struct Fighter : virtual Entity { Fighter() : Entity(1) {} };
struct Drawable : virtual Entity { Drawable() : Entity(2) {} };
struct MultiBoss : Fighter, Drawable {
    MultiBoss() : Entity(300) {}
    void Update() override {}
};
// MultiBoss boss;
// boss.hp;                    // 300，最派生类初始化共享虚基类
// Entity* pe = &boss;
// pe->Update();               // MultiBoss::Update()
```

去掉两条继承边上的 `virtual`，完整对象就有两份 `Entity`，直接访问 `boss.hp` 或转换到 `Entity*` 会歧义，需要指定路径；同时原来的 `MultiBoss() : Entity(300)` 初始化写法也不再合法，因为 `Entity` 既非直接基类也非虚基类。

保留虚继承，两条路径共享一份 `Entity`。虚基类由**最派生类**初始化：本例是 `MultiBoss`，中间类的 `Entity(1)`、`Entity(2)` 在构造这个完整对象时不负责初始化那份共享 `Entity`。若独立构造 `Fighter`，它自己就是最派生类，此时 `Entity(1)` 才生效。

**虚函数统一行为，虚继承共享祖先。** 虚继承不保证消除一切歧义：若两个中间类都重写 `Update`，最终类通常需要提供唯一的最终重写者，否则会编译失败。

| 底层名词 | 顺着刚才两种动作回忆 |
| --- | --- |
| `vptr + vtable` | **找函数入口**，支持虚分派 |
| MSVC 的 `vbptr + vbtable` | **找共享虚基类子对象**：对象内的表指针关联偏移表 |
| Itanium ABI 的 `vbase offset` | 定位共享 `Entity` 所需的偏移，常通过虚表相关信息获取 |
| Itanium ABI 的 `vcall offset` | 从虚基类接口虚调用派生重写时，供调整桩修正 `this` |

**vbase 找基类，vcall 调 this；一个定位数据，一个配合调用。** 两者都不是函数地址。MSVC 的独立虚基表与 Itanium 的虚表偏移信息是不同实现方案，不能认为所有编译器都必须有 `vbptr`。[Itanium ABI：虚表组成](https://itanium-cxx-abi.github.io/cxx-abi/abi.html#vtable-components)

### 场景三：把“角色攻击”接入 UE，再回答性能问题

#### 1. 同一个动作，C++ 和蓝图分别怎样扩展

以下是已有 UE `ACharacter` 派生类中的声明和定义片段，需要正常的 UE 头文件、`UCLASS` 和 `GENERATED_BODY` 环境。

```cpp
// AMyCharacter 类内
public:
    virtual void NativeAttack(); // 普通 C++ 虚函数

    UFUNCTION(BlueprintNativeEvent, BlueprintCallable, Category="Combat")
    void Attack();
    virtual void Attack_Implementation();

// .cpp 中
void AMyCharacter::NativeAttack() { /* C++ 攻击逻辑 */ }
void AMyCharacter::Attack_Implementation() { /* C++ 默认攻击逻辑 */ }

// 已有调用位置中，Target 是 AActor*
if (AMyCharacter* character = Cast<AMyCharacter>(Target)) {
    character->Attack();
}
```

| --- | --- |
| 调 `NativeAttack()` | 普通 C++ 虚分派，支持 C++ 派生类重写；仅有 `virtual` 不会使它成为蓝图可重写事件 |
| 调 `Attack()` | 进入 UHT 生成的事件分发；有蓝图实现就执行蓝图，否则进入 C++ 的 `_Implementation()` |

UE 的 UObject 类型检查与 C++ RTTI 是两套体系：普通 C++ 多态类的运行时向下转换可用 `dynamic_cast`；UE 反射对象通常用 `Cast<T>`，它不是任意普通 C++ 类的通用替代品。[Epic：对象类型检查](https://dev.epicgames.com/documentation/en-us/unreal-engine/unreal-object-handling-in-unreal-engine)

**C++ virtual 找 C++ 重写，UE 事件找蓝图重写；dynamic_cast 查 RTTI，UE Cast 查反射。** 蓝图调用父实现的方式见 [Epic：Blueprint Native Events](https://dev.epicgames.com/documentation/unreal-engine/implementing-blueprint-interfaces-in-unreal-engine)。

#### 2. 如果每帧有一万个角色：最后才谈性能

仍然想象一批角色通过统一接口执行更新或攻击。虚调用潜在代价是间接访存、间接分支预测，以及无法确定目标时限制内联；分散对象还可能造成缓存局部性差。没有固定的“必然慢几倍”。

`virtual` 可以被内联，关键是能否确定调用目标。主例里的 `boss.Attack()` 对象类型已知，编译器可能去虚化并内联；`final` 可提供额外证明，但**仅知道 Boss 为 final，并不能证明任意 `Character*` 都指向 Boss**。`inline` 关键字也不保证一定发生内联。

面试优化顺序只记：**测 → 减 → 降 → 批 → 去虚化 → 复测。**

1. **测**：定位真实热点；UE 中可用 `stat game`、Unreal Insights 看帧耗时和调用情况。
2. **减**：关闭无用 Tick，用事件或定时器减少无效更新。
3. **降**：非关键、远距离对象降频或分帧更新；攻击判定等需要及时响应的逻辑按需求保留频率。
4. **批**：对相似工作批量处理，改善连续数据访问和缓存局部性。
5. **去虚化**：在语义允许时用 `final` 等帮助确定目标，考虑后续内联优化。
6. **复测**：比较帧耗时，确认真正收益。

## 领悟的重点
### 1.编译期与运行期
多态的基础是要有虚指针和虚函数表，并且使用基类指针或引用去指向子类对象，并且调用虚函数的时候，必须得是父类有的虚函数，不然编译期间静态类型(父类指针)就找不到只有子类有的虚函数而父类没有的虚函数，该静态类型指针在编译期间只会从自己的虚函数表中去找所需运行的虚函数，并且进行重载决议，确定虚函数要调用的对应槽位。所以若指向子类才有的虚函数，在编译期会直接报错找不到

#### 1.1🧠 C++ 动态多态的底层运作法则
##### 法则一：多态成立的三大先决条件（缺一不可）
1. **结构基础**：类中含有 `virtual` 关键字，对象内存头部拥有 **虚表指针（`vptr`）**，且类拥有对应的 **虚函数表（`vtable`）**。
2. **指针/引用绑定**：必须使用 **基类指针（`Base*`）或引用（`Base&`）** 指向/绑定子类对象。
3. **接口契约覆盖**：调用的必须是 **基类中已声明的虚函数**（且通常在子类中被 `override`）。

##### 法则二：编译期的“两步走”审判（静态类型控制）
在编译期，编译器**只看指针/引用的静态类型（即 `Base*`）**，它根本不关心运行期实际指向的是哪个子类对象：
1. **符号查找与重载决议**：编译器只在 `Base` 类的作用域里查找函数名，并根据实参完成你的领悟**极其透彻，彻底抓住了 C++ 编译期与运行期的核心分工**！
为了让这段话更符合工业级技术语言的严谨性，同时方便你未来一眼就能复习和回忆起底层逻辑，我帮你重构并提炼为“一个核心铁律 + 两个阶段演译”的精炼表达：

#### 1.2📝 知识点完美梳理版
核心铁律：**多态的前提是“接口继承”。静态类型决定“能调什么（编译期查槽位）”，动态对象决定“真正执行什么（运行期寻地址）”。**
##### 1.编译期（静态类型决定“调哪个槽位”）
当通过**基类指针/引用**调用函数时，编译器的视角只有指针的**静态类型（基类）**：
- **符号查找与重载决议**：编译器只会在基类的作用域中寻找函数名并进行重载决议。如果调用的是**子类独有、基类没有**的函数，编译器在基类符号表里找不到该函数，会直接在**编译期报语法错误**（`has no member named...`）。
- **锁定槽位（Slot Index）**：一旦在基类接口中找到匹配的虚函数，编译器就会确定该虚函数在基类虚表中的**固定槽位序号（Index）**，并硬编码生成指令：`call ptr->vptr[Index]`。
##### 2.运行期（动态对象决定“执行哪段代码”）
程序跑起来后，基类指针实际指向了**子类对象**：
- **虚表寻址**：CPU 顺着子类对象头部的虚表指针（`vptr`）找到子类的虚表（`vtable`）。
- **多态触发**：CPU 拿着编译期算好的**槽位序号（Index）**去子类虚表中取函数地址。由于子类已经重写（Override）了该槽位上的指针，最终执行的就是**子类覆盖后的函数逻辑**。
#### 1.3💡 记忆口诀
> **编译期看左边（指针类型）：** 负责查符号、做重载、锁槽位，没有接口直接报错！
> **运行期看右边（内存对象）：** 负责顺着 `vptr` 查槽位、拿地址、执行子类重写逻辑！


### 2.RTTI和对象偏移量
- **RTTI（运行时类型信息）**：是寄生在虚表之上的“身份证”。它让程序在运行期能够通过 `dynamic_cast` 和 `typeid` 识别对象的真实血统。
- **对象偏移量**：是多重继承下由于内存排布错位而产生的“空间距离”。编译器必须依靠偏移量和 Thunk 机制来修正 `this` 指针，确保多态调用时指针不会迷路。
#### 2.1什么是 RTTI（Run-Time Type Information，运行时类型信息）？
在默认情况下，C++ 是一门**静态类型语言**——变量的类型在编译期就已经死死定下来了。但在多态场景下（比如用 `Base*` 指针指向一个未知的子类对象），有时我们在**运行期**需要知道：“**这个指针背后活生生的对象，到底是个什么类型？**”

这就是 RTTI 诞生的原因：**它让 C++ 程序在程序跑起来的时候，具备“自我审视（Introspection）”类型身份的能力。**

##### 2.1.1RTTI 的两大核心工具

C++ 语言标准提供了两个直接暴露给开发者的 RTTI 关键字：
- **`dynamic_cast`（安全向下转型）**： 我们在前面提到过它。当你把一个 `Base*` 转成 `Derived*` 时，RTTI 会在运行期去检查：_“这个对象到底是不是 `Derived` 或者是它的子类？”_ 如果是，转换成功返回地址；如果不是，返回 `nullptr`（或者抛异常）。

- **`typeid`（获取类型信息）**： 它会返回一个 `std::type_info` 对象的引用，你可以用来打印或者比较类型：
```cpp
 Base* ptr = new Derived();
 std::cout << typeid(*ptr).name() << std::endl; // 运行期输出实际类型名字（如 "7Derived"）
 if (typeid(*ptr) == typeid(Derived)) { ... } // 运行时类型比对
```

##### 2.1.2 底层黑科技：RTTI 是怎么实现的？
编译器为了支持 RTTI，在幕后做了一件非常巧妙的事情：
1. **绑定在虚表上**：RTTI **极其依赖虚函数表**。如果一个类没有任何虚函数，编译器是绝不会为它生成 RTTI 信息的（`dynamic_cast` 会直接编译报错）。

2. **`type_info` 指针**：在每个包含虚函数的类的**虚表指针（`vptr`）正上方（通常是 `vtable` 的 `-1` 索引位置）**，编译器会安插一个指针，指向一个全局唯一的 `std::type_info` 结构体。这个结构体里记录了类的名字、继承链关系等元数据。

3. 当你执行 `dynamic_cast` 时，运行期库不会凭空猜测，而是直接顺着对象的 `vptr` 找到虚表，再通过 `-1` 找到 `type_info`，像查族谱一样去对比父子继承关系。

#### 2.2 什么是对象偏移量（Offset Adjustment / `this` 指针偏移）？

“对象偏移量”通常出现在 **多重继承（Multiple Inheritance）** 或 **菱形继承（虚继承）** 的复杂内存布局中。

用一句话概括：**当一个子类继承了多个基类时，子类对象内部不同基类子对象的内存起始地址，与整个子类对象真正的起始地址之间的“字节距离”，就是对象偏移量。**

##### 2.2.1. 为什么会有对象偏移量？（一个直观的内存痛点）
假设你有两个独立的基类，和一个多重继承的子类：
```C++
class Base1 { public: int a; };
class Base2 { public: int b; };

class Derived : public Base1, public Base2 {
public:
    int c;
};
```
在内存中，`Derived` 对象的排布通常是**按继承顺序线性拼接**的：
```Plaintext
【Derived 对象的完整内存布局】
+-----------------------+
| Base1 部分 (包含成员 a)  |  <-- 偏移量 = 0 字节
+-----------------------+
| Base2 部分 (包含成员 b)  |  <-- 偏移量 = sizeof(Base1) 字节 (比如 4 或 8 字节)
+-----------------------+
| Derived 独有部分 (c)   |
+-----------------------+
```
当你写下这段代码时，神奇的事情发生了：
```C++
Derived* d = new Derived();
Base1* b1 = d; // 隐式转换：b1 和 d 的地址【完全相同】（偏移量为 0）
Base2* b2 = d; // 隐式转换：b2 指向内存中间的 Base2 部分，它的地址被【自动加上了偏移量】！
```

**关键点来了：**
- `b1` 指向整个对象的开头。
- `b2` 指向对象内部靠后的位置。也就是说，**`b2` 的内存地址在数值上比 `d` 大了一个固定的偏移量（Offset）**！

##### 2.2.2 偏移量在多态调用中的生死考验（Thunk 技术）

当多重继承遇上虚函数和多态时，对象偏移量变得极其关键：
```C++
Base2* b2 = new Derived();
b2->f(); // 调用虚函数！
```

因为 `b2` 指向的是 `Derived` 对象内部“腰部”的 `Base2` 子对象，它的 `this` 指针在数值上并不是整个对象的真正起点。 如果直接调用 `Derived::f()`，而 `Derived::f()` 内部去访问了属于 `Derived` 或 `Base1` 的成员变量，由于 `this` 指针指错了个位置，程序会瞬间发生**内存越界和段错误（Crash）**。
###### 编译器的解决方案：Thunk（跳转桩 / 偏移修正）
为了解决这个问题，编译器在生成多重继承的虚表时，会在虚表里插入一个叫 **Thunk** 的微型汇编跳转胶水代码：
1. 当通过 `Base2*` 调用虚函数时，CPU 会先执行 Thunk 代码。
2. Thunk 代码会自动把当前的 `this` 指针**减去（或加上）那个固定的对象偏移量**，让 `this` 重新正向指回整个 `Derived` 对象的真正起点。
3. 然后，再安全地去执行 `Derived` 的成员函数。

### 3.协变
在 C++ 的面向对象和多态体系中，协变（Covariance，通常指“返回类型协变”，Covariant Return Type）是一个非常优雅且实用的高级特性。

用一句话概括它的核心定义：**当子类重写（Override）父类的虚函数时，子类的虚函数可以返回“更具体的子类类型指针或引用”，而不必硬性规定必须和父类返回完全相同的类型。**
#### 3.1 为什么需要协变？（一个直观的痛点）
假设我们在写一个游戏或者文档编辑器，里面有一个“原型克隆（Clone）”接口：
```C++
class Monster {
public:
    // 父类的 clone 接口，返回 Monster*
    virtual Monster* clone() const = 0;
};

class Undead : public Monster {
public:
    // 子类重写 clone
    // 如果没有“协变”机制，这里被迫只能写 virtual Monster* clone() const override;
};
```
**痛点所在**：
如果没有协变，当你在上层代码中拿着一个 `Undead` 对象，想调用它的 `clone()` 得到一个新的亡灵时，返回的居然是一个 `Monster*`（基类指针）。你不得不每次都写一句繁琐且容易出错的向下转型：`Undead* u = dynamic_cast<Undead*>(myUndead->clone());`
而有了**协变**，C++ 允许你在子类中直接返回 `Undead*`！
#### 3.2 什么是协变规则？（三大核心铁律）
要想让编译器允许这种“返回类型不一样”的虚函数重写顺利通过编译，必须严格遵守以下三条规则：
##### 规则 1：必须是“指针（Pointer）”或“引用（Reference）”
协变**只适用于指针和引用类型**。
- ❌ **按值返回（Value）绝对不行**：如果父类虚函数返回 `Monster`（对象本身），子类重写时返回 `Undead`（对象本身），编译器会直接报错，认为签名不匹配。
- ✅ **指针或引用可以**：父类返回 `Base*` / `Base&`，子类返回 `Derived*` / `Derived&`。

> **底层原因**：在底层的虚函数表（vtable）中，所有虚函数的槽位必须具有固定的二进制兼容性。不同大小的对象按值返回会导致栈布局错乱，而指针和引用的底层大小在同一个平台上是绝对固定的（都是 4 字节或 8 字节），修改指针类型不会破坏虚表的二进制结构。
##### 规则 2：返回的类型必须具有公开的继承关系
子类函数返回的指针/引用所指向的类（如 `Undead`），必须是父类函数返回的类（如 `Monster`）的**公开、无歧义的派生类**。
- 父类返回 `Base*` $\rightarrow$ 子类可以返回 `Derived*`。
- 如果毫无血缘关系，编译直接报错。
##### 规则 3：CV 限定符（Const-ness）必须兼容
子类函数返回类型的 `const` 修饰必须符合安全规范：
- 如果父类返回的是 `const Base*`，子类可以返回 `const Derived*`（或者更严格的 `Derived*`，因为非 const 可以安全隐式转换为 const）。
- 反之，如果父类返回非 `const`，子类无权擅自加上 `const`（会导致类型退化或编译不通过）。
#### 3.3 协变在真实代码中的优雅示范
来看一段符合协变规则的标准代码：
```C++
#include <iostream>

class Shape {
public:
    // 基类虚函数，返回 Shape*
    virtual Shape* clone() const = 0;
    virtual ~Shape() {}
};

class Circle : public Shape {
public:
    // 💡 协变返回类型：这里返回的是 Circle*，而不是 Shape*！
    Circle* clone() const override {
        return new Circle(*this); 
    }
    void draw() { std::cout << "Drawing Circle\n"; }
};

int main() {
    Circle c1;
    Circle* c2 = c1.clone(); // 直接拿到 Circle*，无需任何强转！
    c2->draw();
    
    delete c2;
    return 0;
}
```
#### 总结
- **协变是什么**：它允许子类虚函数“收窄”返回类型，返回指向子类自己的指针或引用。
- **协变规则是什么**：仅限指针或引用，必须存在继承血缘关系，且满足 const 安全。
- **它的价值**：消除了面向对象编程中大量烦琐、丑陋的 `dynamic_cast` 向下转型代码，让工厂模式和原型模式（Prototype Pattern）的代码变得极其优雅。


### 4. 构造函数为什么不能是虚函数
#### 4.1 核心悖论：“鸡生蛋，蛋生鸡”

要搞懂为什么构造函数不能是虚函数，只需要盯着一个问题：**虚函数是怎么被调用的？**
前面学过：
1. 调用虚函数，必须靠对象头部的 **`vptr`（虚表指针）** 去查 **`vtable`（虚表）**。
2. 换句话说，**要想使用虚函数机制，这个对象必须已经“活了”，也就是它的 `vptr` 已经安插好并指向了正确的虚表。**
那么问题来了：**是谁负责把 `vptr` 安插到对象内存里的？**
答案是：**构造函数！**

当你在执行 `Derived::Derived()` 时，编译器会悄悄在构造函数开头写一行代码，把对象的 `vptr` 指向 `Derived` 的虚表。
  

如果构造函数本身是**虚函数**会发生什么？
1. 如果构造函数是虚函数，那么调用它就必须通过 `vptr` 去查虚表。
2. 但是，**对象现在还没构造出来呢，哪里来的 `vptr`？！**
3. 也就是说，为了调用构造函数，你需要先有 `vptr`；但要产生 `vptr`，又必须先执行构造函数。这就陷入了死结。

> **结论**：`vptr` 是构造函数“生”出来的，而虚函数机制又必须依赖 `vptr`。所以，**身为“生出 vptr 的人”，构造函数自己绝对不可能是虚函数。**

#### 3.2 拆解那段话的前半句：“构造之前必须确定类型和内存布局”
当你写下这行代码时：
```C++
Derived d; // 或者 Base* p = new Derived();
```
在**进入构造函数的那一瞬间**，你要造什么东西、需要多大的内存空间、里面包含哪些成员变量，**在编译期和调用点就已经被 100% 死死决定了**。它是静态的、明确的。
- 你不能说：“我手里拿了一个模糊的 `Base*` 指针，我不知道它是什么，我让虚函数机制去帮我‘动态猜一下’它到底该调用哪个类的构造函数来造一个新对象。”
- 动态绑定（多态）的意义，是**针对已经存在、已经出生、带有 `vptr` 的活对象**，去决定它该执行哪个行为。而构造函数是负责把对象从无到有“生出来”的过程，此时对象还没出生，虚函数机制根本无法运转。

#### 4.3 现实中的变通方案：“虚构造函数”长什么样？
虽然 C++ 语法上禁止 `virtual Constructor`，但在实际开发中，我们经常遇到类似的需求：“**我手里有一个基类指针，我不知道它具体是 A 还是 B，但我希望能克隆（复制）出一个和它一模一样的全新对象。**”

为了实现这个目的，工业界设计了一个经典的设计模式——**虚复制函数（Virtual Copy Constructor / Clone 模式）**。

虽然构造函数不能是虚函数，但**普通的成员函数可以是虚函数**：
```C++
class Shape {
public:
    // 这是一个普通的虚函数，用来模拟“虚拟构造”
    virtual Shape* clone() const = 0; 
    virtual ~Shape() {}
};

class Circle : public Shape {
public:
    Shape* clone() const override {
        // 内部通过真实的、具象的构造函数来造一个新对象
        return new Circle(*this); 
    }
};
```
- **外界调用**：`Shape* s = unknownShape->clone();`
- **底层逻辑**：外界不需要知道 `unknownShape` 究竟是 `Circle` 还是 `Rectangle`。通过虚函数 `clone()` 的多态分发，正确触发了对应子类的 `new Circle(...)` 或 `new Rectangle(...)`。

### 一句话总结

构造函数不能是虚函数，因为**虚函数依赖 `vptr` 查表，而 `vptr` 是由构造函数亲手塞进对象内存里的。** 在对象被造出来之前，虚函数机制根本无从谈起。

### 5.基类子对象
所谓“基类子对象”（Base Subobject），用最通俗的话来解释就是：**当一个子类对象在内存中被创建时，它内部包含的“属于父类的那一部分内存空间或实体”。**
在 C++ 的面向对象内存模型中，继承绝对不只是逻辑上的“概念继承”，而是**物理上的“包含与拼接”**。
我们可以通过内存布局图和多重继承的场景，彻底把这个概念看透。
##### 5.1 什么是“对象里的子对象”？
假设我们有最简单的单继承：
```C++
class Base {
public:
    int m_baseVar; // 假设占 4 字节
};

class Derived : public Base {
public:
    int m_derivedVar; // 假设占 4 字节
};
```
当你写下 `Derived d;` 在内存里开辟一块空间时，这个 `d` 对象内部的物理长相是这样的：

```Plaintext
【Derived 对象完整的物理内存布局】
+-----------------------------------+
|  [ Base 子对象 (Base Subobject) ]  | <-- 内存开头 (Offset 0)
|       m_baseVar (4字节)           |
+-----------------------------------+
|  [ Derived 自己的独有成员部分 ]    | <-- 紧随其后 (Offset 4)
|       m_derivedVar (4字节)        |
+-----------------------------------+
```
看到了吗？在 `Derived` 对象的内部，**前半部分完整地嵌入了一个 `Base` 类型的实体**。这个被嵌入在子类体内的“父类本体”，就叫做 **Base Subobject（基类子对象）**。
##### 5.2 为什么叫“子对象”？
- 说它是**对象**：因为它有自己的内存空间、有自己的成员变量（比如 `m_baseVar`），甚至有自己的 `vptr`（如果带虚函数的话）。
- 说它是**基类的**：因为它在结构上完全由基类定义。
- 说它是**子对象**：因为它不是一个独立的、孤立的 Base 对象，而是作为“寄生虫”一样被包裹在一个更大的 `Derived` 对象内部。

##### 5.3 为什么“基类指针需要指向对应子对象的起始位置”？
这句话在多重继承（Multiple Inheritance）的情况下，意义尤为致命和关键。

假设我们有多个基类：
```C++
class Base1 { public: int x; };
class Base2 { public: int y; };

class Derived : public Base1, public Base2 {
public:
    int z;
};
```
此时，一个 `Derived` 对象的内存里，塞了**两个**基类子对象：
```Plaintext
【Derived 对象的物理内存布局】
+-----------------------------------+
|  [ Base1 子对象 (Base Subobject) ]  | <-- 偏移量 = 0 字节
|       x (4字节)                   |
+-----------------------------------+
|  [ Base2 子对象 (Base Subobject) ]  | <-- 偏移量 = 4 字节（紧跟在 Base1 后面）
|       y (4字节)                   |
+-----------------------------------+
|  [ Derived 自己的独有部分 ]        | <-- 偏移量 = 8 字节
|       z (4字节)                   |
+-----------------------------------+
```
现在，魔法（或者说指针的指针算术）发生了：
```C++
Derived* d = new Derived(); // 假设 d 的地址是 0x1000

Base1* b1 = d; 
// 此时 b1 指向 Base1 子对象的起始位置
// 因为 Base1 在最头部，所以 b1 的地址依然是 0x1000 (偏移量为 0)

Base2* b2 = d; 
// 💡 注意看这里！
// b2 指向的是 Base2 子对象在内存中的起始位置！
// 编译器会自动把 d 的地址做一次数学计算：0x1000 + 4 = 0x1004
// 所以 b2 的内存地址变成了 0x1004！
```
#### 为什么必须这么做？
如果 `b2` 不指向 `Base2` 子对象的起始位置（即 0x1004），而是依然指向整个对象的开头（0x1000）：
- 当你通过 `b2->y` 去访问变量 `y` 时，CPU 会按照 `Base2` 的偏移规则去取数据。
- 结果 `b2` 指错地方了，导致读出来的不是 `y`，而是 `Base1` 的数据，从而引发**严重的内存错乱和崩溃**。

##### 总结
1. **基类子对象**：就是子类内存里，由基类模板克隆出来的那个“父类本体片段”。
2. **指针的使命**：当你把一个子类指针赋值给基类指针（向上转型）时，基类指针绝对不能盲目地只指着整个对象的开头，它**必须精准地对准它所代表的那个“基类子对象”的物理起始地址**（在多重继承时，这通常需要编译器在底层悄悄加上一个“对象偏移量”）。
