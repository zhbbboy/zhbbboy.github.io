# 一颗弹丸的三个回忆锚点

> 配套笔记：[36 道题与学习记录](3内存布局、对齐.md)。本文用于学完后的提取练习。
>
> 只记一个场景：**服务器发来弹丸出生消息 → 客户端创建弹丸 → 工作线程计算 → 主线程更新 → 弹丸回收 → 排查内存上涨与卡顿。**
>
> 三段核心代码分别回答：**怎么摆、怎么活、怎么交接。**其余知识是对同一系统改变一个条件后的追问，无须另背一套业务例子。

## 先记住这一条线

**消息的字节 → 对象的布局 → 合适的存储 → 构造与所有权 → 线程交接 → 连续更新 → 回收与验证。**

沿线只问自己六句话：

1. **它在哪？**——分区、存储期、虚拟地址。
2. **它多大、怎么摆？**——偏移、对齐、填充、继承。
3. **它活着吗？**——构造、析构、存储复用、合法类型访问。
4. **谁负责它？**——RAII、拷贝移动、智能指针、UE GC。
5. **谁可以碰它？**——边界、悬空引用、同步、线程约束。
6. **为什么卡、怎么证明？**——分配、缓存、缺页、GC、测量。

这里的“问句”是回忆入口。先遮住解释口述，卡住时再回原题。

## 案例一：收到出生消息——先把弹丸的字节账算清

**回忆口令：先算偏移，再算步长；协议和对象分开；成员与基类分清。**

下面三个案例的普通 C++ 代码可按顺序合在一个源文件中。布局计算采用常见 x64 自然对齐：`char` 为 1 字节、`short` 为 2、`int/float` 为 4、对象指针为 8；相应自然对齐为 1、2、4、8，支持 16 字节显式对齐。多态对象的具体布局仍需以目标 ABI 核实。

```cpp
#include <cstddef>
#include <cstdint>

struct Spawn
{
    char type;
    int id;
    short team;
};

struct SpawnCompact
{
    int id;
    short team;
    char type;
};

struct SpawnBatch
{
    char channel;
    SpawnCompact spawn;
    short count;
};

struct alignas(16) Motion
{
    float x, y, z;
};

struct Entity
{
    int hp = 100;
    virtual ~Entity() = default;
    virtual int Damage() const { return 1; }
};

struct Tickable
{
    int tickGroup = 0;
    virtual ~Tickable() = default;
    virtual void Tick() {}
};

struct Projectile : Entity, Tickable
{
    SpawnCompact spawn{};  // 成员子对象，无须单独 new。
    Motion position{};
    inline static int total = 0;
    int Damage() const override { return 10; }
};
```

### 1. 先在纸上画三个格子，召回对齐计算

| 类型 | 成员起始偏移 | 大小／对齐 | 为什么 |
| --- | --- | --- | --- |
| `Spawn` | `type=0, id=4, team=8` | `12 / 4` | 中间填 3 字节，末尾填 2 字节 |
| `SpawnCompact` | `id=0, team=4, type=6` | `8 / 4` | 末尾填 1 字节 |
| `SpawnBatch` | `channel=0, spawn=4, count=12` | `16 / 4` | 嵌套成员按自身对齐 4 放置，占用完整的 8 字节 |
| `Motion` | `x=0, y=4, z=8` | `16 / 16` | 三个浮点数共 12 字节，末尾补到 16 |

**计算口诀：当前末尾向上对齐到成员要求 → 放完整成员 → 最后向上对齐到类型要求。**这套算法用于这里的普通结构体，不能直接套在任意继承布局或特殊 ABI 上。

- `sizeof` 是完整对象大小，包含填充；`alignof` 是起始地址需要满足的对齐要求。**对齐不是大小。**
- `SpawnCompact batch[3]` 占 24 字节，相邻元素相距 8 字节；尾部填充是元素内部的一部分，没有额外的“数组间隙”。
- `Spawn` 改为 `SpawnCompact`，100 万个对象节省 **4,000,000 字节，约 3.81 MiB**；重排可能改变 ABI、持久化格式和依赖偏移的代码。
- 用 `offsetof(Spawn, id)` 验证普通标准布局类型的偏移；不要把它当作任意多态类的可移植布局探针。标准布局涉及基类、虚函数和成员访问控制等约束，不只是“看起来像 struct”。
- `sizeof` 的结果类型是 `std::size_t`；`std::max_align_t` 描述基本对齐能力的上界，不代表覆盖任意过度对齐类型。

### 2. 面试官改变消息格式时，沿着同一张字节账回答

| 改一个条件 | 立刻召回的答案 |
| --- | --- |
| 把 `Spawn` 放在 MSVC `pack(1)` 中 | 典型大小变为 7、布局对齐为 1，成员可能失去自然对齐；`push/pop` 控制影响范围。节省字节可能增加访问成本 |
| 把位置设为 `alignas(16)` | 提高类型对齐要求，可能增加尾部填充；`alignof` 用于查询。SIMD 对齐与缓存行隔离有各自目的 |
| 把存活、可见、阵营写成位域 | 可压缩小范围整数，但排列、分配单元与大小依实现；不能对位域成员取普通指针，不作为跨平台协议布局 |
| 用 `union Payload { int id; double ttl; };` 复用空间 | 假设 `double` 大小／对齐均为 8，则联合体典型大小／对齐为 8；成员共享空间，不能任意读取非活动成员 |
| 拿收到的字节直接转成 `Spawn*` | 还要检查长度、对齐、对象生命周期、类型访问、字节序和填充。`reinterpret_cast` 不会替你完成这些检查 |
| 要把浮点数的位模式看作整数 | 不通过不兼容类型指针解引用；满足条件时用 `memcpy` 或 C++20 `bit_cast`。后者要求等大小、可平凡复制，不负责字节序转换 |
| 想直接把内存发上网 | 按协议逐字段编码／解码，明确宽度和字节序。对象布局、位域、指针和虚表不是协议格式 |

通过 `char`、`unsigned char` 或 `std::byte` 可以查看对象表示，但填充字节没有业务字段语义，不能据此做可靠的值比较。特别是对于这里的非平凡多态 `Projectile`，字节拷贝不能代替对象构造。

### 3. 从消息数据走到多态弹丸，召回类布局

先在脑中画：**`Projectile = Entity 子对象 + Tickable 子对象 + spawn + position + 可能的填充与实现数据`。**

| 追问 | 回答抓手 |
| --- | --- |
| 每个对象到底带什么？ | 普通数据成员和基类子对象；典型 ABI 下还可能有 `vptr`。`total` 是独立静态数据，普通／静态成员函数代码不随每个对象复制 |
| 两个多态基类会怎样？ | 常见 ABI 下各有自己的虚指针；转成第二个基类指针时数值可能调整。虚调用可能通过 thunk 调整 `this`，具体偏移不由标准固定 |
| 若只保留 `Entity` 一个基类？ | 回到典型单继承：基类子对象与派生成员组织在一起，常见实现可复用主基类的虚指针，无须机械地多加一个指针 |
| `Entity copy = projectile; Entity& view = projectile;` | 前者创建独立基类对象并切片，`copy.Damage()` 为 1；后者引用原对象，`view.Damage()` 为 10。原弹丸没有被截断 |
| 两个能力分支都需要同一份状态？ | 普通菱形可能有两份公共基类；两条分支均虚继承该基类时，最派生对象中共享一份。MSVC 常用 `vbptr/vbtable` 定位虚基类；不要混用 Itanium ABI 的布局解释 |
| 加一个空策略类型？ | 独立空对象大小至少为 1，不是因为保存“类 ID”。空基类可能采用 EBO；C++20 `[[no_unique_address]]` 允许空成员等潜在重叠优化，效果需看实现 |
| 能否直接把基类大小相加？ | 不能概括任意继承布局。尾部填充可能被复用，也可能不能复用，还可能有额外对齐和 ABI 数据 |
| 把成员改成 private？ | 不改变 `int` 自身的大小。C++17/20 对不同访问控制成员的顺序保证有限；`public` 不等于可稳定序列化 |
| 武器、位置应该继承还是作为成员？ | “有一个”通常用组合，“可作为某接口使用”考虑继承。成员对象已属于外层对象，不需要另 `new` |

**本例最后必须说出的边界：标准规定语义；ABI 决定许多具体布局。**

## 案例二：让弹丸出生又回收——把存储、对象和所有权分开

**回忆口令：先有房，再住人；走人不拆房；谁拥有，谁善后。**

这里调用一次普通 C++ 函数，先用 RAII 管理动态弹丸，再演示同一槽位的两次构造。它们是两种创建方案的对照。

```cpp
#include <memory>
#include <new>

int g_spawned = 1;
int g_zero;
thread_local int threadSpawns = 0;

void SpawnAndRetire()
{
    static int calls = 0;
    ++calls;
    ++threadSpawns;
    int ids[3]{1, 2, 3};
    [[maybe_unused]] int* first = ids;
    [[maybe_unused]] const char* label = "Projectile";

    auto owner = std::make_unique<Projectile>();
    auto* observer = owner.get();
    owner.reset();             // 析构对象并释放其动态存储。
    observer = nullptr;        // 只处理这一个观察者，不影响其他别名。
    (void)observer;

    alignas(Projectile) std::byte slot[sizeof(Projectile)];
    auto* p = ::new (static_cast<void*>(slot)) Projectile{};
    p->~Projectile();          // 对象生命周期结束，slot 仍存在。
    auto* next = ::new (static_cast<void*>(slot)) Projectile{};
    next->~Projectile();       // 最后一个对象也结束生命周期。
}                             // slot 的底层存储随后随作用域退出。
```

### 1. 对着这一个函数，回答“在哪”和“活多久”

| 看到的东西 | 应该区分什么 |
| --- | --- |
| `g_spawned/g_zero/calls` | 静态存储期，典型实现分别涉及已初始化数据与零初始化数据；`calls` 名字只有局部作用域 |
| `threadSpawns` | 线程存储期，每个线程有独立实例；不因为名字相同就共享一个对象 |
| `ids/first/label/owner/slot` | 自动存储期；常见实现使用栈，但局部变量也可能在寄存器或被优化掉。调用栈帧还涉及返回地址、寄存器保存和调用约定 |
| `owner` 和它管理的弹丸 | 前者是局部智能指针对象，后者是动态创建对象；两者不能混为同一块内存 |
| `label` 与 `"Projectile"` | 指针变量与字符串字面量不同；字面量有静态存储期，典型实现位于只读区域；`const` 本身不决定对象所在段 |
| `ids` 与 `first` | 数组是对象，不是指针；此处 `sizeof(ids)=12`、`sizeof(first)=8`。多数表达式有数组到指针的转换，但 `sizeof(ids)`、`&ids`、`decltype(ids)` 等不发生这种转换 |
| `slot` 与槽位中的弹丸 | 存储可跨越多个对象生命周期；非平凡对象需正确构造，显式析构不会自动释放外部缓冲区 |

**作用域管名字，存储期管空间，生命周期管对象。**分区是典型实现，三者是语言语义。函数调用也不保证一定产生可见的独立栈帧；递归深度可能耗尽线程栈，优化则可能改变实际调用形态。

### 2. 把出生与回收记成两个方向

**普通 `new`：找分配函数 → 获得合适存储 → 初始化对象。普通 `delete`：析构 → 匹配释放。**

- `operator new` 管分配，构造函数管初始化；普通分配失败通常抛 `bad_alloc`，`malloc` 失败返回空指针；`nothrow new` 不保证构造函数不抛异常。
- 构造失败时，普通 new 表达式会调用匹配的释放函数回收所分配存储；已构造完成的成员／基类也会按异常展开规则清理。
- `malloc/free` 不调用非平凡构造／析构；C++20 的部分隐式生命周期规则，不能当作已经构造了任意非平凡对象。
- 必须配对：`new/delete`、`new[]/delete[]`、`malloc/free`；UE 的 `FMemory::Malloc/Free` 也要匹配。即使是 `int[]`，也不能把数组释放换成 `delete`。
- 数组析构按构造的逆序；实现可能用 Array Cookie 记录数量，但并非所有类型与实现都需要同样的 cookie。
- 本例两次 Placement New 不申请额外的对象存储；不能对槽位中的指针使用普通 `delete`。重新构造后直接使用返回的新指针。旧指针能否透明指代新对象有条件，`std::launder` 也不能补救尺寸、对齐或对象根本不存在的问题。[对象生命周期规则](https://eel.is/c++draft/basic.life)
- 通过 `Entity*` 普通删除动态 `Projectile`，本例的虚析构支持完整析构链。不是对基类和派生类各 `delete` 一次；`delete nullptr` 安全，但不会修复其他悬空别名。

### 3. 同一个弹丸系统，怎样选所有权与分配策略？

| 场景 | 选择与回忆点 |
| --- | --- |
| 一个管理者负责普通 C++ 弹丸 | 默认考虑 `unique_ptr`；RAII 把清理绑定到对象生命周期，也适用于锁、文件和其他句柄 |
| 弹丸带动态轨迹数组 | 优先用 `vector` 成员获得 Rule of Zero；原始拥有指针若默认拷贝，可能两个对象释放同一资源。深拷贝需重新分配并复制元素 |
| 被问 Three／Five | Three：析构、拷贝构造、拷贝赋值；Five 再考虑移动构造、移动赋值。移动是按类型实现的资源转移，不是 `std::move` 自动搬内存 |
| 返回轨迹结果 | 返回具名局部可能 NRVO；符合条件的 C++17 纯右值返回有保证的消除。不能断言必拷贝或必移动；标准库被移动对象通常有效但状态未指定，按具体契约继续使用 |
| 确实有共同所有权 | `shared_ptr` 配控制块，典型含强弱计数、删除器等；智能指针对象通常不只一个原始指针大小，确切大小依实现 |
| 只观察目标，或打破相互持有 | `weak_ptr` 不保活，`lock()` 成功才获得临时共享所有权。弱引用不等于只读；引用计数安全也不等于被管理对象线程安全 |
| 每帧临时轨迹／UI 数据 | Linear 推进偏移、Arena 整体回收；不同实现中术语可能重叠。重置前处理需要析构的对象，禁止继续使用旧分配结果 |
| 大量同大小、独立回收的弹丸 | 固定槽位 Pool，用空闲链表管理；回收槽位与析构不是一回事。也可以保留活对象并重置业务状态，二者需明确选择 |
| 大小各异、寿命交错 | 通用大小分类分配器；内部碎片是块内未用空间，外部碎片是分散空洞导致利用困难。还要考虑元数据、粒度、锁与缓存管理 |

**把对齐分配器缩成一条可手推的规则：**假设底座 64 字节对齐、容量为 `capacity`，只接受不超过 64 的二次幂对齐值 `a`，当前偏移为 `offset`。

先验证参数及 `offset <= capacity`，算 `padding = (a - offset % a) % a`。再依次检查 `padding <= capacity - offset`、`bytes <= capacity - offset - padding`，最后才返回 `base + offset + padding` 并推进偏移。拒绝零字节和非法对齐，请求失败不改变状态。减法检查避免先做加法而溢出。

**唯一要背的分配演算：**偏移 3 → 申请 5 字节／对齐 8 → 从 8 开始、用到偏移 13；再申请 4 字节／对齐 16 → 从 16 开始、用到偏移 20。提高支持对齐范围时，必须重新核实底座条件。

### 4. 弹丸若是 UE Actor，把同一套“谁负责”翻译为 UE 语义

| 持有场景 | 召回选择 |
| --- | --- |
| 可达的 UObject 中持续持有已加载对象 | 通过可被 GC 追踪的反射字段表达强引用，常用 `UPROPERTY() TObjectPtr<T>`；仅有包装类型或宏字样不足以绕过持有者可达性要求 |
| 观察一个可能销毁的目标 | `TWeakObjectPtr<T>`，使用时检查目标状态；保活、业务有效和线程可访问是不同条件 |
| 非 UObject 类需要临时／持续保活 UObject | 可考虑 `TStrongObjectPtr<T>`，或通过 `FGCObject` 等显式报告引用；评估额外引用和不可回收环的风险 |
| 资源按需加载 | `TSoftObjectPtr<T>` 描述资源路径与加载入口；软引用本身不保证对象常驻，加载完成后的长期使用需考虑强引用 |
| 创建与销毁 | 普通 UObject 用 `NewObject`，Actor 通过世界的 `SpawnActor` 进入创建流程；Actor 通常请求 `Destroy`，不用普通 `delete` 管理 UObject |
| 弹丸池复用 Actor | 区别于释放再重建：要复位碰撞、移动、生命计时、委托、目标引用等；保留对象复用可能增加常驻内存 |
| 回调或异步任务访问目标 | 避免把裸 UObject 指针捕获后无条件延迟解引用；按需使用弱引用，并把依赖游戏线程的访问安排到游戏线程 |

GC 判断可达性与普通共享指针引用计数不是同一套回收机制；普通 `shared_ptr` 不能接管所有 UObject 的生命周期。对象指针选择与具体引擎版本的条件见 [Epic 对象指针文档](https://dev.epicgames.com/documentation/en-us/unreal-engine/object-pointers-in-unreal-engine)。

## 案例三：工作线程算弹丸，主线程更新——把安全和性能连起来

**回忆口令：先安全交接，再连续访问；先找证据，再改布局。**

限定为一次发布：一个生产者创建结果，一个消费者读取并更新；发布后生产者不再访问结果，两个线程结束前不清空或复用共享状态。实际客户端可用任务系统传递所有权，这里用最小协议展示同步条件。

```cpp
#include <atomic>
#include <thread>
#include <vector>

std::vector<Motion> results;
std::atomic<bool> ready{false};
std::atomic<std::uint64_t> completed{0};

void Calculate()
{
    results.assign(10000, Motion{0.0f, 0.0f, 0.0f});
    completed.fetch_add(1, std::memory_order_relaxed);
    ready.store(true, std::memory_order_release);
}

void RunOneFrame()
{
    std::thread worker(Calculate);
    while (!ready.load(std::memory_order_acquire))
        std::this_thread::yield();

    for (auto& motion : results)
        motion.x += 1.0f;

    worker.join();
}
```

### 1. 用一条箭头召回内存模型

**写 results → release 发布 → acquire 读到这次发布 → 读写 results。**

写结果先于发布；读到该发布的获取操作与它建立同步，再把结果访问串成 happens-before。`completed` 只用作独立统计，不承担发布协议，所以可使用 relaxed。若只把 `ready` 改成原子却使用 relaxed，不能据此保护普通共享数据；`volatile` 也不能代替同步。[原子操作顺序](https://eel.is/c++draft/atomics.order)

| 追问变化 | 回忆答案 |
| --- | --- |
| acquire／release 分别在哪？ | release 常用于发布的存储，acquire 用于获取的加载；acq_rel 用于需要两者语义的读改写；不能任意给普通 load／store 指定所有内存序 |
| 全改 seq_cst 是否万事大吉？ | 它为相关原子操作提供更强的全局顺序约束，不自动保护所有普通数据或对象生命周期 |
| 原子一定无锁吗？ | 不一定；可查询 `is_lock_free` 等能力。`fetch_add` 是原子读改写，CAS 可用于条件更新，失败重试也有协议与内存序约束 |
| 插一条 fence 能修好任意代码吗？ | 不能；屏障需要符合规则的原子同步协议，不能让任意数据竞争合法。编译器重排、CPU 重排和机器指令需要分层理解 |
| 下帧继续复用 ready 和 results？ | 本例的一次发布证明失效，需要握手、双缓冲、队列或其他完整协议，防止生产者修改消费者仍在读取的缓冲区 |
| 主线程这样等会不会卡？ | 会等待结果；此处只展示同步语义，实际任务调度要避免无必要阻塞，也不能忽略异常和线程回收的工程处理 |

### 2. 读同一批结果，召回缓存、虚拟内存与伪共享

| 观察到的现象 | 从弹丸场景展开 |
| --- | --- |
| 只更新所有弹丸的 x | `vector<Motion>` 是 AoS，每个元素步长为 16，而每次只需 4 字节的 x；SoA 分离 x 数组可能减少无用数据流量并利于 SIMD，但要测量 |
| 每次处理某颗弹丸全部字段 | AoS 可能更方便且有良好对象内局部性；选布局要看真实访问模式，不是 SoA 永远更好 |
| 顺序扫描快，追指针慢 | 空间局部性、时间局部性及硬件预取影响命中；L1／L2／L3 一般逐级变大、延迟变高，主存更远，具体数值与硬件相关 |
| 数据量增大后变慢 | 初次访问、容量压力和缓存冲突会增加 Miss；工作集、冷热字段、依赖链与访问顺序都可能比相同的 O(n) 更影响实际耗时 |
| 容器扩容后，旧指针不能用 | 重分配可能移动元素。`reserve` 预留容量而不增加元素数量；`resize` 改变数量。预留也会增加常驻容量，不保证全生命周期永不失效 |
| UE 数组存的是 UObject 指针 | 指针元素连续，不代表所指对象连续；大对象内联与对象指针的取舍涉及拷贝、缓存和稳定地址要求 |
| 两个线程各改独立统计计数器仍然慢 | 若它们落在同一缓存行，缓存一致性可能引发伪共享。可以没有数据竞争，却有明显性能损失 |
| 给每个字段都加 alignas(64)？ | 64 只是常见缓存行假定，不是标准常量；分离热写数据可能有利，也可能因工作集膨胀变慢，应按平台测量 |
| 第一次访问大块内存有尖峰 | 地址转换和页面驻留都需考虑，首次提交、按需清零等缺页处理不一定读磁盘；无效映射可能最终成为访问违规 |

**两条不同的逻辑线，不能混淆：**

- **地址翻译：**程序使用虚拟地址，MMU 依据映射做翻译，TLB 缓存近期翻译；TLB Miss 可能需要页表遍历。不同进程有独立映射，数值相同的虚拟地址不等于同一对象。
- **数据访问：**CPU 数据 Cache 缓存数据行，Miss 涉及更远的缓存／内存。两条路径在硬件中可能重叠，不是必须逐级串行的固定时序图。

64 位指针不等于进程实际能用完整的 2⁶⁴ 字节空间；地址宽度、系统限制和资源都有限。ASLR 改变运行时布局。**TLB Miss 不等于 Cache Miss，缺页异常不等于栈溢出。**

### 3. 弹丸消失后内存仍涨，按症状回到同一条线

| 症状 | 首先怀疑什么 | 如何获得证据 |
| --- | --- | --- |
| 访问弹丸时崩溃 | 悬空指针、回调捕获过期引用、容器重分配、越界 | 最小复现；MSVC ASan 的访问／分配／释放调用栈；区分 UAF 与重复释放 |
| Debug 能跑，Release 错 | 未初始化读取、越界、非法类型访问或同步缺失等 UB | 审查访问条件；按平台选择 ASan／UBSan 等工具。没有崩溃不证明正确 |
| 生成销毁若干轮后，活对象仍增加 | 强引用滞留、共享指针环、未注销委托、容器无界增长 | 对象数与引用链；快照之间的存活分配差；区分业务缓存与意外保留 |
| 活对象下降，进程内存不降 | 分配器缓存、容器容量、资源池、CPU／GPU 资源保留 | 对比逻辑活对象、已分配字节、预留容量和进程／GPU 指标；不能只看任务管理器判定泄漏 |
| 每次发射时 CPU 尖峰 | 分配、锁竞争、资源加载、首次访问或 GC | 对齐 CPU 时间线、分配事件、GC 事件与资源加载事件，再决定预分配、池化或调度优化 |

**工具记忆分工：**ASan 查许多越界、UAF、重复释放等内存安全错误，不是 MSVC 的通用泄漏检测器，也不证明无全部 UB；Debug CRT 的泄漏工具只覆盖适用的 CRT 分配路径。容器的 `.at()` 可提供边界检查；C++17/20 的 `span` 表达范围但不保活底层对象，也不能把未检查访问自动变成安全访问。[MSVC ASan 支持范围](https://learn.microsoft.com/en-us/cpp/sanitizers/asan)

UE 中先固定地图、生成频率、游玩时长和构建配置，再从启动时采集所需内存 Trace 与符号；用 Memory Insights 比较时间区间的存活分配和调用栈，结合 `memreport` 快照与 CPU／GC 时间线定位。修复后重复相同场景，比较**稳定／峰值内存、分配次数、对象数、帧时间分位数及尖峰次数**，同时排除 GPU 资源瓶颈。[Memory Insights 的采集与查询](https://dev.epicgames.com/documentation/en-us/unreal-engine/memory-insights-in-unreal-engine)

再向下一层回忆 UE 分配：**容器分配策略 → 内存分配接口 → 具体分配器。**`FMemory` 提供内存相关接口，典型路径会接到全局分配器；`FMalloc` 是其接口，`GMalloc` 指向具体实例。默认堆式 `TArray` 与 `TInlineAllocator` 等策略不完全相同。`Reserve`、`Reset`、`Empty` 的数量／容量行为要结合参数和版本看；容器释放元素与分配器向系统归还内存也不同。Binned 大小分类能再次联系到碎片、粒度和缓存，不能假定所有平台或配置始终用同一实现。参阅 [FMemory](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Core/FMemory)、[FMalloc](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Core/FMalloc) 与 [TArray](https://dev.epicgames.com/documentation/en-us/unreal-engine/array-containers-in-unreal-engine)。

## 一段可以直接口述的贯穿回答

> 我会以弹丸系统说明内存问题。首先区分网络字节格式和 C++ 对象布局，按成员对齐计算偏移、填充与数组步长；涉及多态和继承时再声明 ABI 假定，不能把对象原始字节当稳定协议。
>
> 创建时把存储分配、对象构造和所有权分开。普通 C++ 对象优先 RAII，按寿命和大小选择容器、线性分配器或对象池；复用槽位时明确是否结束对象生命周期，并处理旧引用。UE 对象则采用合适的 GC 引用和创建销毁流程。
>
> 多线程计算时先设计交接和复用协议，再谈原子或内存序；大量更新时看真实访问模式、缓存和重分配，不能只比较栈堆或复杂度。遇到增长和卡顿，我会固定复现场景，区分错误访问、资源滞留、分配器缓存、分配与 GC 压力以及 GPU 占用，再用调用栈和时间线定位，最后用相同指标复测。
