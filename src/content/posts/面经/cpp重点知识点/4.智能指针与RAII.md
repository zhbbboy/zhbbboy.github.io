## 一、所有权与独占管理

### 第 1 题：如何用所有权和 RAII 解释智能指针的作用，并选择合适的资源管理方式？

**必答范围：资源与生命周期 → 所有权分类 → 类型选择 → 拷贝与移动。**
1. 什么是 RAII？正常返回、提前返回和异常发生时，资源怎样得到清理？构造函数抛异常时，完整对象、已构造成员和基类分别会怎样？RAII 除了内存还能管理哪些资源？
2. `unique_ptr`、`shared_ptr`、`weak_ptr` 分别表达什么所有权？能否复制、移动、直接访问对象？它们与值对象、引用、裸指针各适合什么场景？
3. `std::move` 到底做了什么？智能指针的移动构造、移动赋值分别如何处理源和目标？能否把智能指针的移动后状态推广到所有类型？
4. Rule of Three、Five、Zero 与资源所有权有什么关系？含智能指针成员的类如何决定拷贝、移动和析构行为？
5. 智能指针能否自动解决越界、悬空借用、循环引用和数据竞争？它与 GC 有什么区别？旧的 `auto_ptr` 有什么问题？

#### 正确回答
RAII 是将资源所有权与对象生命周期绑定，利用构造和析构自动管理资源。正常返回、提前返回以及异常栈展开时，已构造完成的局部 RAII 对象都能够按规则清理资源。
智能指针主要有三种：`unique_ptr` 表达独占所有权，支持移动但不支持复制；`shared_ptr` 通过引用计数管理共享所有权；`weak_ptr` 不延长对象生命周期，可以通过 `lock()` 尝试访问有效对象。
`std::move` 本身不会移动资源，它只是进行右值转换，实际是否移动取决于类型的移动操作。
对于管理资源的类，需要考虑 Rule of Three/Five；实际开发中更推荐 Rule of Zero，优先使用 RAII 成员，让标准库类型负责资源释放和所有权管理。
智能指针不能自动解决越界访问、悬空借用、循环引用及数据竞争。`shared_ptr` 与 GC 也不等价，前者主要基于引用计数，后者依据具体垃圾回收机制管理对象生命周期。
旧的 `auto_ptr` 因为复制会转移所有权，语义容易产生误用，已经在 C++17 中移除。

#### 示例
##### 一、RAII：资源为什么能自动清理？（第 1 问）
RAII（Resource Acquisition Is Initialization，资源获取即初始化）的核心是：
通过对象生命周期管理资源，在对象构造或初始化阶段建立资源所有权，在析构时自动清理资源。
例如：
```cpp
void Test()
{
    auto p = std::make_unique<int>(100);

    if (SomeCondition())
        return;

    // 其他操作
}
```
无论函数正常结束还是提前 `return`，局部变量 `p` 离开作用域时都会析构，自动释放拥有的动态资源。
如果函数抛出异常，正常的栈展开（Stack Unwinding）同样会析构已经构造完成、需要清理的局部对象。


RAII 除了动态内存，还能管理互斥锁（`std::lock_guard`）、文件句柄、网络套接字等资源。C++20 的 `std::jthread` 也提供了自动请求停止并等待线程结束的生命周期管理能力。
##### 二、unique_ptr、shared_ptr、weak_ptr（第 2 问）
三种智能指针最重要的区别如下：

|对比|unique_ptr|shared_ptr|weak_ptr|
|---|---|---|---|
|所有权|独占|共享|不拥有|
|能否复制|不可以|可以|可以|
|能否移动|可以|可以|可以|
|能否直接 `->` 访问|可以|可以|不可以|
|是否延长对象生命周期|是|是|否|
###### 为什么 weak_ptr 不能直接访问对象？
因为它不负责保持对象存活。
```cpp
auto p = std::make_shared<Enemy>();

std::weak_ptr<Enemy> weak = p;

if (auto temp = weak.lock())
{
    temp->health = 50;
}
```
`lock()` 会尝试获取临时的共享所有权。成功之后可以修改对象（如果对象类型允许修改），失败说明被管理对象已经销毁。所以 weak_ptr 是弱所有权关系，不是只读指针。

至于什么时候选择哪种类型：

|使用场景|推荐方式|
|---|---|
|普通成员对象，不需要动态分配|值对象|
|唯一负责销毁对象|`unique_ptr`|
|多个模块确实需要共同负责生命周期|`shared_ptr`|
|只需要观察共享对象是否还存活|`weak_ptr`|
|临时访问非空对象，不接管所有权|`T&`|
|临时访问可能为空的对象，不接管所有权|`T*`|
原则：能用值对象就不必使用动态分配；需要动态所有权时，优先考虑独占所有权。
###### 三、std::move 到底做了什么？（第 3 问）

你说“把非右值资源变成具有右值移动能力”，方向接近，但不够准确。
`std::move` 本质上进行类型转换，将表达式转换成右值类别中的 xvalue（将亡值），使移动构造或移动赋值有机会被选中。

它自己并不移动资源。
例如：
```cpp
auto a = std::make_unique<int>(10);

auto b = std::move(a);
```

这里真正转移资源的是 `unique_ptr` 的移动构造函数。
注意区分：
```cpp
auto b = std::move(a); // 移动构造

b = std::move(c);      // 移动赋值
```
移动赋值时，`b` 已经存在，因此还要正确处理 `b` 原来拥有的资源。
对于标准 `unique_ptr` 和 `shared_ptr`，移动后源智能指针为空；但不能推广成所有 C++ 类型移动后都为空。
例如被移动的 `std::vector` 通常只保证处于有效但未指定的状态。
##### 四、Rule of Three、Five、Zero（第 4 问）
你已经能记住三法则和五法则的成员函数，这部分没有问题。

还要进一步理解它们与所有权的关系。

|法则|主要意义|
|---|---|
|Rule of Three|自己管理资源时，需要协调析构、拷贝构造和拷贝赋值|
|Rule of Five|在三法则基础上，还需要考虑移动构造和移动赋值|
|Rule of Zero|尽量将资源管理交给 RAII 成员，让业务类不需要自己实现这些特殊成员函数|
###### 智能指针成员对类有什么影响？
例如：
```cpp
class Player
{
public:
    std::unique_ptr<Weapon> weapon;
};
```

在没有其他特殊成员函数干扰的情况下：
- `Player` 默认不能复制，因为 `unique_ptr` 禁止复制。
- `Player` 可以通过隐式生成的移动操作转移 `weapon` 所有权。
- `Player` 销毁时，成员 `weapon` 会自动析构并处理其资源。

如果改成：
```cpp
class Player
{
public:
    std::shared_ptr<Weapon> weapon;
};
```
默认复制 `Player` 时，共享指针成员会被复制，因此两个 `Player` 可能共享同一个 `Weapon` 对象。
Rule of Zero 不代表完全不用考虑所有权，而是让资源管理机制由成员类型承担。
业务类仍然需要决定允许复制、允许移动还是禁止复制。
##### 五、智能指针不能解决哪些问题？（第 5 问）
智能指针能减少部分资源管理错误，但不能自动解决所有内存安全问题。

|问题|能否自动解决|原因|
|---|---|---|
|普通数组越界|不能|智能指针不保证下标检查|
|悬空借用指针|不能|外部裸指针可能仍指向已销毁对象|
|shared_ptr 循环引用|不能|相互持有的强引用计数可能无法归零|
|多线程数据竞争|不能|引用计数安全不等于对象成员线程安全|
|不匹配的资源释放|取决于管理方式|需要正确选择删除器和所有权构造方式|
###### 智能指针与 GC 的区别
`shared_ptr` 主要根据引用计数判断何时销毁对象。
GC（Garbage Collection，垃圾回收）则根据具体实现的规则确定对象是否仍然可达或存活。
以 UE 的 UObject GC 为例，主要根据引擎可以识别的引用关系判断对象的可达性，而不是依赖普通 `std::shared_ptr` 的强引用计数。
所以两者不等价。
###### 旧的 auto_ptr 为什么被淘汰？
`std::auto_ptr` 的突出问题是复制操作会意外转移所有权。

例如，概念上：
```cpp
std::auto_ptr<int> a(new int(10));
std::auto_ptr<int> b = a;
```
执行所谓的“复制”后，`a` 会失去所有权。这违反了人们对正常拷贝语义的直觉，容易造成错误，也不适合现代容器要求。因此 `auto_ptr` 在 C++11 被弃用，并在 C++17 从标准库中移除，应该使用 `unique_ptr` 替代。
#### 面试追问
- 一个类的构造函数抛出异常，完整对象的析构函数会执行吗？已经构造成功的成员和基类怎么办？
- `unique_ptr`、`shared_ptr`、`weak_ptr` 分别能不能复制、移动？为什么 `weak_ptr` 需要 `lock()`？
- `std::move` 本身会移动资源吗？`unique_ptr` 移动后源指针是什么状态？能否把结论推广到 `std::vector`？
- 一个类只有 `std::unique_ptr<T>` 成员，通常能否默认拷贝？为什么这仍然符合 Rule of Zero？
- `shared_ptr` 能否自动解决循环引用和被管理对象的数据竞争？`auto_ptr` 为什么被淘汰？
**回答：**
- 部分正确①： 如果某个类的构造函数抛出异常，这个完整对象自身的析构函数不会执行，因为它没有构造成功。但已经构造完成的成员对象和基类子对象，会按照规定逆序析构。你把完整对象与成员子对象混淆了。
- 基本正确②： `unique_ptr` 不能复制但能移动，`shared_ptr` 和 `weak_ptr` 都能复制、移动。注意 `weak_ptr::lock()` 是尝试获取临时强引用，不是先修改对象，修改失败才说明对象被销毁。`lock()` 返回空指针才表示没有成功获取共享所有权。
- 正确③： `std::move` 本身不会移动资源。更准确地说，它把表达式转换为将亡值（xvalue），使移动操作有机会被选中。移动后的 `unique_ptr` 为空，不能把这个结论推广到所有类型。
- 正确④： 含 `unique_ptr` 成员的类通常不能隐式拷贝，但可以在满足条件时隐式移动。使用 RAII 成员管理资源，符合 Rule of Zero。
- 正确⑤： 智能指针不能自动解决所有越界、悬空借用、循环引用和数据竞争问题；`auto_ptr` 被淘汰的重要原因是复制操作会转移所有权。
RAII 是将资源管理与对象生命周期绑定，通过构造和析构自动管理资源。在正常退出、提前返回和异常栈展开时，已经构造成功的 RAII 对象能够按规则清理资源。
`unique_ptr` 表示独占所有权，不能复制但能移动；`shared_ptr` 表示共享所有权；`weak_ptr` 不拥有资源，可以通过 `lock()` 尝试获取有效的共享所有权。
`std::move` 本身只进行类型转换，不负责实际移动资源。
对于资源管理类，需要理解 Rule of Three/Five；实际开发优先采用 Rule of Zero，利用 RAII 成员自动处理资源。
智能指针不能自动解决循环引用、越界和数据竞争等问题，也不等价于垃圾回收机制。
### 第 2 题：怎样正确使用 `unique_ptr` 管理对象、数组和自定义资源？

先分析下面的所有权变化，并分别判断两条注释语句能否成立：

```cpp
void TestUnique()
{
    auto first = std::make_unique<int>(10);
    auto second = std::move(first);
    // auto copy = second;

    int* observed = second.get();
    int* raw = second.release();
    std::unique_ptr<int> third(raw);
    third.reset(new int(20));

    // std::cout << *observed << '\n';
}
```

逐行说明 `first/second/third` 是否拥有资源，`observed/raw` 在哪些时刻可以访问对象，以及原来的 `int(10)` 在哪里被清理。

**必答范围：独占与转移 → 操作接口 → 创建与释放 → 工程用法。**

1. 为什么 `unique_ptr` 禁止复制？如何接管已有资源、传递所有权、从工厂返回对象、放入容器？返回局部变量时如何选择是否写 `std::move`？
2. `get()`、`release()`、`reset()`、`swap()` 分别做什么？调用后谁负责释放？`delete p.get()`、`p.reset(p.get())`、忽略 `release()` 返回值各有什么风险？
3. `unique_ptr<T>` 与 `unique_ptr<T[]>` 在删除方式和访问接口上有什么区别？是否记录数组长度、检查越界？什么时候应改用 `vector`？
4. `make_unique` 怎样创建和初始化对象、数组？与直接使用 `new` 有什么区别？私有构造函数、自定义删除器及 `make_unique_for_overwrite`【进阶，首轮可略】分别有哪些限制和版本要求？
5. 怎样用自定义删除器管理文件、`malloc` 内存、对象池或库句柄？删除器的类型、状态、异常行为会怎样影响资源释放、移动和 `sizeof(unique_ptr)`？Placement New 的对象如何清理？
6. `unique_ptr<Derived>` 转为 `unique_ptr<Base>` 时，怎样保证正确析构？不完整类型、PImpl 和在 `.cpp` 中定义析构函数之间有什么关系？
7. 如果要求手写一个简化的独占指针，至少需要实现哪些操作、删除哪些操作、维护哪些不变量？如何检查移动赋值、自赋值和异常路径？

#### 正确回答
`std::unique_ptr` 是表达独占所有权的 RAII 智能指针，禁止复制但支持移动。移动会转移资源所有权，并使源 `unique_ptr` 为空。
它的核心接口包括 `get()`、`release()`、`reset()` 和 `swap()`。其中 `get()` 只返回非拥有型原始指针，`release()` 放弃所有权但不释放资源，`reset()` 负责清理原有对象并可接管新对象，`swap()` 交换管理状态。
`unique_ptr<T>` 默认使用 `delete`，`unique_ptr<T[]>` 使用 `delete[]`。对于需要维护长度和动态扩容的数组，通常优先考虑 `std::vector`。
`make_unique` 是推荐的创建方式。对于文件、内存池等需要特殊释放协议的资源，可以提供自定义删除器。
实际使用中还要注意多态删除时的虚析构要求，以及 PImpl 中不完整类型的析构位置。
如果手写简化版 `unique_ptr`，重点是禁止复制，实现析构、移动构造、移动赋值及所有权管理接口，保证同一资源只由一个管理者负责释放。

#### 示例
##### 一、先从零理解 unique_ptr 的工作原理

###### 1. unique_ptr 究竟是什么？
看两种管理动态内存的方式。

普通指针：
```cpp
int* p = new int(10);

// 使用资源

delete p; // 必须自己负责释放
```

使用 `unique_ptr`：
```cpp
auto p = std::make_unique<int>(10);

// 使用资源
// 离开作用域时自动清理
```
`unique_ptr` 本质上是一个 C++ 类模板，它将一个资源的独占所有权封装起来，并通过析构函数执行清理。
![](../../_Pasted_Image/Pasted%20image%2020261022132441.png)
关键区分：
- `unique_ptr` 变量是一个管理对象。
- 堆中的 `int(10)` 是被管理对象。
- `unique_ptr` 销毁时，调用删除器清理自己拥有的对象。
可以把它理解为一个管理资源的类，简化思想如下：
```cpp
template <typename T>
class SimpleUniquePtr
{
private:
    T* ptr;

public:
    explicit SimpleUniquePtr(T* p) : ptr(p) {}

    ~SimpleUniquePtr()
    {
        delete ptr;
    }

    SimpleUniquePtr(const SimpleUniquePtr&) = delete;

    SimpleUniquePtr& operator=(
        const SimpleUniquePtr&) = delete;
};
```
这段代码仅用于说明核心原理，还不是完整实现，缺少移动构造、移动赋值和访问接口等。
###### 2. 为什么 unique_ptr 禁止复制，但允许移动？
你这一点已经回答正确。

如果允许普通复制：
```cpp
auto p1 = std::make_unique<int>(10);

auto p2 = p1; // 编译错误
```
就可能产生两个独立管理者都认为自己应该删除同一个对象的问题。因此，`unique_ptr` 禁止复制。

但可以移动：
```cpp
auto p1 = std::make_unique<int>(10);

auto p2 = std::move(p1);
```
![](../../_Pasted_Image/Pasted%20image%2020261022132829.png)
![](../../_Pasted_Image/Pasted%20image%2020261022132838.png)
最重要的结论：移动的是所有权，不是把堆对象本身搬到另一个地址。
##### 二、四个最重要的成员函数（第 2 分项）
这部分是整道题的核心，建议你重点记忆。

|接口|做了什么|是否删除原资源|
|---|---|---|
|`get()`|返回保存的原始指针，供临时访问|否|
|`release()`|放弃所有权，返回原始指针|否|
|`reset()`|替换当前管理的指针，清理旧资源|是，若旧资源存在|
|`swap()`|交换两个智能指针的管理状态|否|
###### 1. get()：只借地址，不转移所有权
```cpp
auto p = std::make_unique<int>(10);

int* raw = p.get();

std::cout << *raw;
```
此时：
```
p ───────→ int(10)   拥有资源
raw ─────→ int(10)   仅临时借用
```
`raw` 不能因为自己拿到了地址，就擅自释放它。

尤其不要这样写：
```
delete p.get(); // 错误
```
因为 `p` 仍然认为自己拥有这个资源，将来还会尝试删除，可能造成重复释放。
###### 2. release()：放弃所有权，但不删除资源
```cpp
auto p = std::make_unique<int>(10);

int* raw = p.release();
```
现在：
```
p   → nullptr
raw → int(10)
```
`p` 不再管理资源。这时候调用者必须明确安排谁负责清理这块资源。

例如：
```cpp
delete raw;
```
特别注意：`release()` 不是“释放堆内存”，而是“释放智能指针对资源的所有权”。

如果写成：
```
p.release(); // 没有接收返回值
```
在没有其他所有者接管时，就可能导致内存泄漏。
###### 3. reset()：释放旧资源，可以接管新资源
```cpp
auto p = std::make_unique<int>(10);

p.reset(new int(20));
```
执行结果：
```
原来：p → int(10)

执行 reset：

① p 接管 int(20)
② 原来的 int(10) 被删除
```
你还可以：
```cpp
p.reset();
```
效果是清理当前管理的对象，并使 `p` 为空。

但是：
```cpp
p.reset(p.get()); // 错误
```
这不是安全的重置方式。它会让 `p` 继续保存原来的地址，却删除原来管理的对象，造成悬空指针，后续可能重复释放。
###### 4. swap()：交换所有权
```cpp
auto p1 = std::make_unique<int>(10);
auto p2 = std::make_unique<int>(20);

p1.swap(p2);
```
交换后：
```cpp
p1 → int(20)
p2 → int(10)
```
不会因为交换而删除这两个对象。
##### 三、现在重新分析文档给出的代码
```cpp
void TestUnique()
{
    auto first = std::make_unique<int>(10);
    auto second = std::move(first);
    // auto copy = second;

    int* observed = second.get();
    int* raw = second.release();
    std::unique_ptr<int> third(raw);
    third.reset(new int(20));

    // std::cout << *observed << '\n';
}
```

逐行看：

|语句|发生的事情|
|---|---|
|`first = make_unique<int>(10)`|first 独占 `int(10)`|
|`second = std::move(first)`|所有权转给 second，first 为空|
|`auto copy = second`|不合法，unique_ptr 禁止复制|
|`observed = second.get()`|observed 借用地址，不拥有对象|
|`raw = second.release()`|second 放弃所有权，raw 获取地址|
|`third(raw)`|third 接管原来的 `int(10)`|
|`third.reset(new int(20))`|删除 `int(10)`，third 接管 `int(20)`|
|`*observed`|不合法，observed 已经悬空|
|函数结束|third 析构，删除 `int(20)`|
这里有一个非常重要的细节：在 `second.release()` 执行之后，`observed` 和 `raw` 都仍指向有效的 `int(10)`，只是它们都不拥有资源。直到 `third.reset(new int(20))` 删除原来的对象之后，它们才变成悬空指针。
理解这段代码，`unique_ptr` 的所有权机制就基本通了。
##### 四、unique_ptr 管理单对象和数组有什么区别？（第 3 分项）
两种类型：
```cpp
// 管理一个对象
std::unique_ptr<int> p1 = std::make_unique<int>(10);

// 管理一个动态数组
std::unique_ptr<int[]> p2 = std::make_unique<int[]>(5);
```
区别：

|对比|`unique_ptr<T>`|`unique_ptr<T[]>`|
|---|---|---|
|默认删除方式|`delete`|`delete[]`|
|常用访问方式|`*p`、`p->member`|`p[index]`|
|自动记录数组长度|不适用|不提供数组长度接口|
|自动检查数组越界|不适用|不保证检查|
特别注意：
```cpp
auto p = std::make_unique<int[]>(5);

p[0] = 10;
p[4] = 50;

p[5] = 100; // 越界，未定义行为
```
所以如果你需要动态改变数组大小、查询长度、进行边界检查，优先考虑 `std::vector<T>`。
##### 五、make_unique 与自定义删除器（第 4、5 分项）
###### 1. make_unique 的作用
比较：
```cpp
std::unique_ptr<int> p(new int(10));
```
与：
```cpp
auto p = std::make_unique<int>(10);
```
两者都能够创建由 `unique_ptr` 独占管理的整数对象。

但是一般更推荐 `make_unique`，因为它可读性更好，也更容易避免把裸指针暴露在复杂表达式中导致的所有权和异常安全问题。

`make_unique` 从 C++14 开始提供。

它还有一些限制：例如无法直接指定 `unique_ptr` 的自定义删除器；通过标准库内部调用构造函数时，也不能直接绕过类的私有构造函数访问控制。
文档中的 `make_unique_for_overwrite` 属于 C++20 功能，首轮先不展开。
###### 2. 为什么需要自定义删除器？
因为不是所有资源都应该使用 `delete` 清理。

例如使用 C 语言文件接口：
```cpp
#include <cstdio>
#include <memory>

int main()
{
    using FilePtr = std::unique_ptr<
        FILE, decltype(&std::fclose)>;

    FilePtr file(
        std::fopen("data.txt", "r"),
        &std::fclose
    );
}
```
这里的资源是文件句柄。
`unique_ptr` 析构时调用 `fclose`，而不是普通 `delete`。

类似地：
- `malloc()` 分配的内存应该使用 `free()` 清理。
- 对象池借出的对象应该按照对象池约定归还。
- 第三方库句柄应该调用对应的释放接口。

自定义删除器可以是函数、函数对象或 lambda。它的类型以及是否保存状态，会影响 `unique_ptr` 的实际对象大小与移动行为。清理操作应避免抛出异常，否则可能导致 `std::terminate` 等严重后果。
###### 3. Placement New 怎么处理？

你之前学过 Placement New，它只是在已有存储上构造对象。
例如：
```cpp
void* memory = ::operator new(sizeof(Enemy));

Enemy* p = new (memory) Enemy();
```
如果由我们手动管理，就需要匹配两个动作：
```cpp
p->~Enemy();               // 结束对象生命周期
::operator delete(memory); // 释放原始存储
```
不能想当然地用普通 `delete p` 代替这一套操作。如果希望通过智能指针管理，需要设计与构造方式匹配的自定义删除器，并确保底层分配器或内存池仍然有效。
##### 六、继承与不完整类型（第 6 分项）
###### 1. 为什么基类析构函数需要关注 virtual？
```cpp
class Base
{
public:
    virtual ~Base() = default;
};

class Derived : public Base
{
};

std::unique_ptr<Base> p =
    std::make_unique<Derived>();
```
这里实际创建的是 `Derived` 对象，但最终可能通过 `Base*` 执行删除。使用默认删除器时，基类通常需要虚析构函数，才能保证通过基类指针正确销毁派生类对象。如果基类析构函数不是虚函数，通过普通基类指针删除派生类对象通常属于未定义行为（特殊销毁删除机制除外）。
这和你之前学过的多态析构是同一个知识点。
###### 2. 不完整类型与 PImpl
例如，我们想隐藏一个类的具体实现：
头文件中：
```cpp
class Widget
{
private:
    struct Impl;

    std::unique_ptr<Impl> impl;

public:
    Widget();
    ~Widget();
};
```
在 `.cpp` 中：
```cpp
struct Widget::Impl
{
    int value = 10;
};

Widget::Widget()
    : impl(std::make_unique<Impl>())
{
}

Widget::~Widget() = default;
```
`Impl` 在头文件里只是前置声明，属于不完整类型。

在 `.cpp` 文件中定义析构函数，可以保证默认删除器需要销毁 `Impl` 时，编译器已经看到它的完整定义。

这个技巧叫作 PImpl（Pointer to Implementation，实现隐藏），用于降低头文件依赖、隐藏实现细节等。

##### 七、面试如何手写简化版 unique_ptr？（第 7 分项）

这是验证你真正理解所有权的最好方法之一。

下面只实现管理单个对象、使用默认 `delete` 的简化版本：
```cpp
#include <utility>

template <typename T>
class MyUniquePtr
{
private:
    T* ptr_ = nullptr;

public:
    // 1. 构造
    explicit MyUniquePtr(T* p = nullptr) noexcept
        : ptr_(p) {}

    // 2. 析构
    ~MyUniquePtr()
    {
        delete ptr_;
    }

    // 3. 禁止复制
    MyUniquePtr(const MyUniquePtr&) = delete;

    MyUniquePtr& operator=(const MyUniquePtr&) = delete;

    // 4. 移动构造
    MyUniquePtr(MyUniquePtr&& other) noexcept
        : ptr_(other.release())
    {
    }

    // 5. 移动赋值
    MyUniquePtr& operator=(MyUniquePtr&& other) noexcept
    {
        if (this != &other)
        {
            reset(other.release());
        }

        return *this;
    }

    // 6. 获取原始指针
    T* get() const noexcept
    {
        return ptr_;
    }

    // 7. 放弃所有权
    T* release() noexcept
    {
        return std::exchange(ptr_, nullptr);
    }

    // 8. 替换资源
    void reset(T* p = nullptr) noexcept
    {
        T* old = std::exchange(ptr_, p);
        delete old;
    }

    // 9. 访问对象
    T& operator*() const
    {
        return *ptr_;
    }

    T* operator->() const noexcept
    {
        return ptr_;
    }
};
```
这个教学版本不支持数组、自定义删除器等完整标准库功能，也要求被管理对象按约定由普通 `delete` 正确销毁。

你当前最需要理解的是其中三个设计：

第一：复制操作被删除。
```cpp
MyUniquePtr(const MyUniquePtr&) = delete;
```
保证不能通过普通复制产生第二个所有者。

第二：移动必须让源对象失去所有权。
```cpp
ptr_(other.release())
```
`release()` 将旧对象管理的地址交给新对象，同时让源指针为空。

第三：移动赋值必须先处理目标已有资源。
```cpp
reset(other.release());
```
目标对象原本可能已经管理一个资源。
如果直接覆盖它保存的指针，就会丢失旧资源的释放路径。
`if (this != &other)` 用于处理自移动赋值。`reset()` 还必须遵守不能用自身 `get()` 的结果重新接管自身这一约束。

## 二、共享所有权与弱引用

### 第 3 题：`shared_ptr` 的控制块怎样工作，引用计数与对象生命周期怎样变化？

不运行代码，先预测各次计数输出和析构输出的顺序：

```cpp
struct Resource
{
    ~Resource() { std::cout << "~Resource\n"; }
};

void TestCounts()
{
    auto first = std::make_shared<Resource>();
    std::weak_ptr<Resource> observer = first;
    {
        auto second = first;
        auto third = std::move(second);
        std::cout << first.use_count() << '\n';
        first.reset();
        std::cout << third.use_count() << '\n';
    }
    std::cout << observer.expired() << '\n';
    observer.reset();
}
```

在 `first.reset()`、内层作用域结束和 `observer.reset()` 三个位置，分别画出智能指针、控制块与对象之间的关系。

**必答范围：变量、对象与控制块 → 计数推演 → 析构与存储回收。**
1. `shared_ptr` 变量、控制块、被管理对象分别是什么？典型控制块需要保存哪些信息？`sizeof(shared_ptr<T>)` 与对象大小、指针大小有什么关系，哪些属于实现细节？
2. 复制、移动、赋值、重置、按值传参、返回和离开作用域时，强引用计数如何变化？临时对象和 lambda 捕获怎样影响计数？
3. 强引用计数归零、最后一个弱引用消失时，分别发生什么？对象析构、调用删除器、归还对象存储、回收控制块是否一定同时发生？
4. 强计数与弱引用管理信息如何配合？弱计数是否必然等于用户创建的 `weak_ptr` 数量？为什么不能只给对象加一个普通整数就完成可靠的引用计数？
5. 如果手写一个简化共享指针，需要怎样设计控制块、复制/移动、赋值和销毁？增加弱引用后还需要补什么？教学实现与标准库实现在并发、异常、删除器和别名语义上有什么差距？（完整线程安全的 `shared_ptr/weak_ptr` 实现【进阶，首轮可略】。）

#### 正确回答
`shared_ptr` 是通过共享所有权管理动态对象的 RAII 智能指针。典型实现中，每个 `shared_ptr` 保存对象指针及控制块关联信息，多个共享所有者共同使用一个控制块。
控制块通常包含强引用计数、弱引用管理信息、删除器以及相关分配信息。
复制 `shared_ptr` 会增加强引用计数，移动则主要是转移所有权，不额外增加强引用计数。
当强引用计数归零时，被管理对象销毁；但如果仍存在 `weak_ptr`，控制块通常需要继续保留。
`make_shared` 往往将控制块与对象合并分配，因此对象析构后，其所在分配块可能需要等控制块不再使用时才能整体回收。
实现简化版 `shared_ptr`，需要围绕共享控制块实现复制、移动、赋值、析构和引用计数管理。完整标准库实现还要考虑线程安全、异常安全和自定义删除器等问题。
#### 我存在的问题
| 分项               | 判断   | 需要纠正的内容                              |
| ---------------- | ---- | ------------------------------------ |
| 1. 控制块与对象布局      | 部分正确 | `sizeof(shared_ptr<T>)` 通常不只是一个指针的大小 |
| 2. 引用计数变化        | 部分正确 | 赋值、移动赋值、按值传参需要区分具体情况                 |
| 3. 对象与控制块销毁      | 部分正确 | 对象析构、对象存储回收、控制块回收不一定同时发生             |
| 4. 强弱计数配合        | 部分正确 | 内部弱计数不一定等于用户创建的 `weak_ptr` 数量        |
| 5. 手写 shared_ptr | 不会   | 需要建立控制块、引用计数与清理逻辑的整体模型               |
#### 示例
###### 一、先分析原题代码
```cpp
void TestCounts()
{
    auto first = std::make_shared<Resource>();
    std::weak_ptr<Resource> observer = first;

    {
        auto second = first;
        auto third = std::move(second);

        std::cout << first.use_count() << '\n';

        first.reset();

        std::cout << third.use_count() << '\n';
    }

    std::cout << observer.expired() << '\n';
    observer.reset();
}
```
最终输出：
```
2
1
~Resource
1
```
逐步解释：

|操作|强引用计数|发生的事情|
|---|---|---|
|创建 `first`|1|first 拥有 Resource|
|`observer = first`|1|创建弱引用，不增加强计数|
|`second = first`|2|复制 shared_ptr，增加强计数|
|`third = std::move(second)`|2|转移所有权，强计数不变|
|`first.reset()`|1|first 放弃所有权|
|内层作用域结束|0|third 析构，Resource 被销毁|
|`observer.expired()`|0|返回 true，输出 1|
|`observer.reset()`|0|释放弱引用，控制块可被回收|
这里最关键的是：
`shared_ptr` 移动时不会产生一个额外的共享所有者。复制通常增加强计数，移动则转移已有的所有权。而 `observer` 虽然一直存在，却不会阻止 `Resource` 析构。

你要建立一个清晰的概念：
`shared_ptr` 不是只有一个指针加一个计数器那么简单。通常要区分三个部分。

###### sizeof(shared_ptr) 是多少？
你回答“一个指针的大小”，不准确。
在常见的 64 位 MSVC 标准库实现中，`sizeof(std::shared_ptr<T>)` 通常是 16 字节，因为其对象通常包含两个指针大小的状态。

##### 三、哪些操作会改变引用计数？（第 2 分项）
这是面试中最高频的部分。

|操作|对强引用计数的影响|
|---|---|
|创建新的共享对象|初始强计数为 1|
|复制 shared_ptr|新所有权组的强计数 +1|
|移动 shared_ptr|转移已有所有权，不因移动而 +1|
|`reset()`|放弃原有所有权，原强计数 -1|
|离开作用域|若持有所有权，强计数 -1|
|按值传入左值 shared_ptr|通常 +1，参数销毁时 -1|
|按值传入 `std::move(p)`|转移所有权，不额外 +1|
|Lambda 按值捕获 shared_ptr|复制时通常 +1|
|Lambda 按引用捕获|不因为引用捕获而 +1|
但你说的“赋值就会 +1”并不总是正确。

例如：
```cpp
auto a = std::make_shared<int>(10);
auto b = std::make_shared<int>(20);

a = b;
```
执行时：
- 原来由 `a` 管理的 `int(10)` 失去其最后一个强引用，因此被销毁。
- `a` 加入 `b` 的共享所有权组。
- `int(20)` 的强引用计数从 1 变为 2。
所以赋值可能同时涉及旧控制块减计数、新控制块加计数。
对于返回值，还需要考虑返回值优化和移动语义，不能简单认为返回一次就增加一次引用计数。
##### 四、强引用归零与弱引用归零的区别（第 3、4 分项）
这是你这次回答中最需要纠正的地方。

你说：
> 对象析构、调用删除器一起，而归还对象存储、回收控制块一起。

前半句通常成立，但后半句不一定成立。原因是 `make_shared` 经常采用合并分配。

例如：
```cpp
auto p = std::make_shared<Resource>();

std::weak_ptr<Resource> weak = p;

p.reset();
```
执行 `p.reset()` 之后：
- 强引用计数归零。
- `Resource` 对象执行析构，生命周期结束。
- `weak` 仍然存在。
- 控制块需要保留。
- 如果对象与控制块采用合并分配，那块分配的存储通常也还不能整体归还。

随后：
```cpp
weak.reset();
```
当最后的弱引用也消失，控制块才可以被回收。
而如果对象和控制块分别分配，对象对应的存储通常可以在强计数归零时释放，控制块则继续保留。
因此要区分：
对象析构 ≠ 对象存储立即归还 ≠ 控制块立即回收。
###### 弱引用计数一定等于 weak_ptr 数量吗？
不一定。

在一些标准库实现中，内部弱计数除了表示外部弱引用，还可能包含为了协调控制块生命周期而使用的额外计数。

所以你要区分：
- 逻辑上的弱引用数量。
- 控制块内部用于管理生命周期的计数值。
二者在实现层面不一定完全相等。
这也是为什么仅给被管理对象放一个普通整数计数器，不足以实现可靠的 `shared_ptr` / `weak_ptr`：还需要处理对象销毁后控制块继续存活、并发原子操作、竞态条件和异常安全等问题。

##### 五、如果手写一个简化版 shared_ptr，应该怎样设计？（第 5 分项）
你暂时不需要直接写完整代码，先理解底层结构。

假设我们实现一个单线程教学版本，最核心的是：
```cpp
template <typename T>
struct ControlBlock
{
    T* ptr;
    size_t strongCount = 1;
};
```
再让每个共享指针保存指向同一控制块的指针：
```cpp
template <typename T>
class MySharedPtr
{
private:
    ControlBlock<T>* cb = nullptr;
};
```

核心操作是：

|操作|内部实现思路|
|---|---|
|构造|创建控制块，强计数初始为 1|
|拷贝构造|共享控制块，强计数 +1|
|移动构造|转移控制块指针，源对象置空|
|拷贝赋值|正确处理旧所有权，再共享新控制块|
|移动赋值|正确处理旧所有权，再转移控制块|
|析构|强计数 -1；归零时清理资源|
增加 `weak_ptr` 后，还需要维护弱引用的有效性：强计数归零时销毁对象，但只要还有弱引用，就不能销毁控制块。
这个教学设计还没有解决线程安全、自定义删除器、异常安全及别名构造等问题，不能直接替代标准库。
底层重点：多个 `shared_ptr` 共享的是同一个控制块，而不是每个 `shared_ptr` 各自拥有一个独立的引用计数器。

**回答：**
`shared_ptr` 的多个副本共享同一个控制块。拷贝构造不会创建新的控制块，而是共享已有控制块并增加强引用计数。

常见 64 位实现中，`shared_ptr` 对象通常包含一个存储指针和一个控制块指针，但实际布局属于标准库实现细节。
### 第 4 题：如何选择 `shared_ptr` 的创建方式，并理解其分配、异常安全与删除策略？

**必答范围：创建与初始化 → 分配策略 → 异常路径 → 销毁类型。**

3. 自定义删除器与分配器分别负责什么？删除器的类型为什么不体现在 `shared_ptr<T>` 的类型参数里？`get_deleter` 有什么用途【进阶，首轮可略】？删除器捕获的状态、内存池应存活到什么时候？（自定义分配器及其与删除器、内存池的复杂组合【进阶，首轮可略】。）
4. 对象构造失败、控制块分配失败、接管前的其他操作抛异常时，资源分别由谁清理？多个实参求值带来的异常安全问题，在 C++17 前后有什么差别？
5. 私有构造函数、类专属 `operator new`、过度对齐类型【进阶，首轮可略】及自定义释放方式，怎样影响创建方案？`shared_ptr<T[]>`、数组版 `make_shared`、`for_overwrite`【进阶，首轮可略】有什么版本和初始化差异？
6. `shared_ptr<Base>(new Derived)`、先保存为 `Base*` 再创建共享指针、由 `make_shared<Derived>` 转成基类指针，销毁策略是否相同？与默认删除器的 `unique_ptr` 转换有什么区别？
#### 正确回答
`shared_ptr<Base>` 管理 `Derived` 对象，不一定要求 `Base` 具有虚析构函数，这取决于创建共享指针时建立的删除策略。
如果直接使用 `shared_ptr<Base>(new Derived)`，由于构造时传入的是 `Derived*`，控制块能够保存对应的销毁策略，因此可以正确析构派生类。
如果先将 `Derived*` 转成 `Base*`，再创建 `shared_ptr<Base>`，默认删除策略会通过 `Base*` 删除对象。当基类没有虚析构函数时，通常会产生未定义行为。
对于 `make_shared<Derived>()` 转换为 `shared_ptr<Base>`，由于共享原来的控制块，销毁机制不会改变，因此也能正确析构派生类。
而 `unique_ptr<Derived>` 转换为使用默认删除器的 `unique_ptr<Base>`，通常需要基类具有虚析构函数。
实际工程中，如果基类设计用于多态使用和通过基类指针销毁对象，我会优先将它的析构函数声明为 virtual，避免出现所有权和删除策略方面的隐患。

##### 一、make_shared 与直接 new 有什么区别？（第 1 问）
先回顾你已经掌握的三个概念：
- 被管理对象： 例如 `Enemy`，是真正需要使用的对象。
- 控制块： 存储强弱引用计数、删除器等管理信息。
- shared_ptr 变量： 保存访问对象和管理共享所有权所需的信息。
现在问题来了：创建一个 `shared_ptr` 时，被管理对象和控制块的内存是怎么分配的？
###### 1. shared_ptr(new T)：通常两次分配
```cpp
std::shared_ptr<int> p(new int(10));
```

典型过程：
1. 执行 `new int(10)`，分配内存并构造对象。
2. 构造 `shared_ptr`，分配控制块。
3. 控制块与 `int(10)` 建立管理关系。
###### 2. make_shared：通常一次分配
```cpp
auto p = std::make_shared<int>(10);
```
典型实现会申请一块足够大的内存，同时放下控制块和被管理对象，并在其中构造对象。
![](../../_Pasted_Image/Pasted%20image%2020261027142800.png)
所以 `make_shared` 通常有这些优势：
- 减少一次动态内存分配的开销。
- 控制块和对象位于同一分配块，可能改善缓存局部性。
- 代码简洁，减少手动暴露裸指针的机会。
`allocate_shared<T>(allocator, args...)` 则允许指定用于分配的分配器，通常也能合并分配。它适合需要自定义内存分配策略的场景，首轮了解即可。
面试结论：正常创建共享对象时，通常优先使用 `make_shared`。但它不是所有情况下都最合适。
##### 二、为什么 weak_ptr 可能让内存一直没有释放？（第 2 问）
这里需要联系你第 3 题学过的内容：
强引用计数归零，对象会析构；但如果还有弱引用，控制块仍需要保留。
例如：
```cpp
auto p = std::make_shared<Enemy>();

std::weak_ptr<Enemy> weak = p;

p.reset();
```
我们逐步观察：
![](../../_Pasted_Image/Pasted%20image%2020261027143119.png)
![](../../_Pasted_Image/Pasted%20image%2020261027143132.png)
![](../../_Pasted_Image/Pasted%20image%2020261027143144.png)
###### 这里最容易混淆两个概念
- 对象析构： `Enemy` 的生命周期结束，析构函数被执行。
- 内存归还： 保存对象的存储空间交还给分配器。
如果 `make_shared` 采用合并分配，长期存在的 `weak_ptr` 可能导致那块包含对象存储的分配块一直无法整体释放。
如果采用 `shared_ptr<Enemy>(new Enemy)` 的分离分配，通常可以在强引用计数归零时释放 `Enemy` 的独立存储，同时继续保留控制块。
###### 大对象需要特别注意
```cpp
struct BigObject
{
    char data[1024 * 1024]; // 假设大对象本身占约 1 MB
};
```
如果采用合并分配，长期存在的弱引用可能让包含大对象存储的分配块持续保留。但如果对象只是包含一个 `std::vector`，其元素缓冲区一般是另外分配的：
```cpp
struct BigObject
{
    std::vector<int> data;
};
```
强引用归零、对象析构时，`vector` 的缓冲区通常会被正常释放。所以应该区分对象本体的存储与成员对象另外申请的存储。
##### 三、删除器和分配器有什么区别？（第 3 问）
你说删除器负责资源释放，基本正确。
更准确的区分如下：

| 机制             | 主要责任                   |     |
| -------------- | ---------------------- | --- |
| Deleter（删除器）   | 按正确协议清理被管理资源           |     |
| Allocator（分配器） | 分配与归还存储空间，通常也提供配套的构造支持 |     |
例如：
```cpp
auto deleter = [](FILE* f)
{
    if (f)
        std::fclose(f);
};

std::shared_ptr<FILE> file(
    std::fopen("test.txt", "r"),
    deleter
);
```
这里 `shared_ptr` 的删除器调用 `fclose()`，而不是 `delete`。
###### 为什么 shared_ptr 的类型中没有删除器参数？
比较：
```cpp
std::unique_ptr<T, Deleter>
```
和：
```cpp
std::shared_ptr<T>
```
`unique_ptr` 的删除器类型是模板参数的一部分，而 `shared_ptr` 将不同类型的删除器统一封装进所有权管理机制中，典型实现是将删除器信息保存在控制块中。
因此：
```
std::shared_ptr<int> p1(new int(10));
std::shared_ptr<int> p2(new int(20), customDeleter);
```
二者都可以是 `std::shared_ptr<int>`。
要注意，删除器如果捕获了内存池指针或其他状态，这些依赖必须在删除器最后一次需要使用它们时仍然有效。
例如对象池已经被销毁，删除器却继续调用它的回收函数，就可能产生 Use-after-free。
`get_deleter` 可以用于查询特定类型的删除器；复杂的自定义分配器与删除器组合，首轮可以先略过。
##### 四、shared_ptr 创建失败时，谁负责清理资源？（第 4 问）
这道题主要考察异常安全（Exception Safety）。
###### 情况 1：对象构造函数抛出异常
```cpp
auto p = std::make_shared<Enemy>();
```
如果 `Enemy` 构造函数抛异常：
- 不会得到一个成功构造的 `Enemy` 对象。
- 已完成构造的成员和基类会按异常清理规则析构。
- `make_shared` 负责释放这次创建过程使用的存储。
不会因为对象构造失败就简单留下无法回收的内存。
###### 情况 2：控制块分配失败
```cpp
std::shared_ptr<Enemy> p(new Enemy());
```
这个操作典型地涉及对象分配和控制块分配。
需要注意一个常见误区：并不是说只要控制块分配失败，`new Enemy()` 创建的对象就必然泄漏。
标准 `shared_ptr` 的原始指针构造函数要求在自身构造失败时，按照对应删除策略清理已经传入的对象指针。
###### 情况 3：裸指针还没有被智能指针接管，就抛出异常
真正危险的是：
```cpp
Enemy* raw = new Enemy();

DoSomethingThatMayThrow();

std::shared_ptr<Enemy> p(raw);
```
如果中间函数抛出异常，`raw` 尚未交给任何 RAII 对象管理，就可能泄漏。

因此推荐：
```cpp
auto p = std::make_shared<Enemy>();

DoSomethingThatMayThrow();
```
这样对象在创建完成后立即处于共享所有权管理中。
###### C++17 前后有什么区别？
这是文档要求的一个重要标准版本差异。

在 C++17 之前：
```cpp
Foo(std::shared_ptr<Enemy>(new Enemy), MayThrow());
```
不同函数实参的求值过程可能交错，存在 `new Enemy` 已经执行、`shared_ptr` 尚未完成构造，另一个参数却先抛异常的风险。
从 C++17 开始，各函数实参的求值不会这样交错执行，因此这个特定风险得到消除。但是实参之间先执行哪一个仍然没有统一的从左到右保证，而且其他裸指针所有权问题依然存在。

面试结论：优先使用 `make_shared` 建立共享所有权，避免在建立所有权之前留下可能抛异常的操作。

##### 五、私有构造函数、数组和特殊分配方式（第 5 问）
这部分有一些首轮需要知道的边界。
###### 1. make_shared 不能随意访问私有构造函数
```cpp
class Enemy
{
private:
    Enemy() {}

public:
    static std::shared_ptr<Enemy> Create()
    {
        return std::make_shared<Enemy>(); // 通常无法通过访问检查
    }
};
```
虽然 `Create()` 是类的成员函数，但真正执行构造操作的是标准库内部的模板代码，它并不会自动获得访问私有构造函数的权限。
可以采用合适的工厂设计，或者在有权访问私有构造函数的上下文中使用明确的创建方式。
###### 2. 类自定义 operator new
如果类定义了自己的 `operator new`：
```cpp
struct Enemy
{
    static void* operator new(std::size_t size);
    static void operator delete(void* p) noexcept;
};
```
那么：
```cpp
std::shared_ptr<Enemy> p(new Enemy);
```
创建 `Enemy` 对象时会按照相应规则调用类专属的 `operator new`。
而 `make_shared<Enemy>()` 通常通过统一分配块构造对象，不使用该类单对象创建时的专属 `operator new`。
因此有特殊对象池或分配协议时，需要重新考虑创建方式。过度对齐类型及复杂的自定义释放策略属于进阶部分。
###### 3. shared_ptr 可以管理数组吗？
可以，但要区分 C++ 版本：
```cpp
// C++17 支持的数组管理形式
std::shared_ptr<int[]> p(new int[5]{});
```

```cpp
// C++20 开始支持
auto p = std::make_shared<int[]>(5);
```
对于上述 `make_shared<int[]>(5)`，五个整数会进行值初始化，因此初始值为 0。

C++20 还增加了：
```cpp
auto p = std::make_shared_for_overwrite<int[]>(5);
```
它允许避免某些不必要的初始化，适用于准备完整覆盖写入的场景；但不能在写入前读取未初始化的普通整数元素。第一遍记住：shared_ptr 数组支持与数组版 make_shared 的出现时间不同。
##### 六、shared_ptr 管理派生类时，一定需要虚析构吗？（第 6 问）
这一问特别值得注意，因为它与你第 2 题学过的 `unique_ptr` 多态析构有区别。
假设：
```cpp
#include <iostream>
#include <memory>

class Base
{
public:
    ~Base()
    {
        std::cout << "~Base\n";
    }
};

class Derived : public Base
{
public:
    ~Derived()
    {
        std::cout << "~Derived\n";
    }
};
```
注意：`Base` 没有虚析构函数。
###### 情况 A：直接用 Derived* 创建 shared_ptr
```cpp
std::shared_ptr<Base> p(new Derived());
```
这段代码可以正确销毁 `Derived` 对象。
为什么？关键在于：
```cpp
new Derived()
```
返回的是 `Derived*`。
构造 `shared_ptr<Base>` 时，虽然最终管理接口的类型是 `Base`，但控制块建立时保留了与 `Derived*` 对应的删除策略。因此，`p` 析构且最后一个强引用消失后，会按照 `Derived` 类型正确删除对象。
输出：
```cpp
~Derived
~Base
```
核心原因：控制块建立时知道需要删除的是 `Derived` 对象。
###### 情况 B：先转换为 Base*，再创建 shared_ptr
```cpp
Base* raw = new Derived();

std::shared_ptr<Base> p(raw);
```
这段代码存在未定义行为。
为什么？首先：
```cpp
Base* raw = new Derived();
```
这里 `raw` 的静态类型是 `Base*`，虽然实际指向 `Derived` 对象，但原来的 `Derived*` 类型信息没有作为模板构造参数传入 `shared_ptr`。
随后：
```cpp
std::shared_ptr<Base> p(raw);
```
构造函数接收到的是 `Base*`。
因此，默认删除策略会按照 `Base*` 执行删除。但 `Base` 的析构函数不是虚函数。
根据 C++ 的多态删除规则，通过普通的 `Base*` 删除实际的 `Derived` 对象，通常属于未定义行为（Undefined Behavior）。不能认为它一定只调用 `~Base()`，因为未定义行为没有确定的执行结果。
核心原因：构建控制块时，默认删除策略使用的是 `Base*`，而 Base 缺少虚析构函数。
###### 情况 C：通过 make_shared 创建 Derived，再转换成 shared_ptr<Base>
```cpp
std::shared_ptr<Base> p =
    std::make_shared<Derived>();
```
这段代码也可以正确销毁 `Derived` 对象。

执行过程：
1. `make_shared<Derived>()` 创建 `Derived` 对象及其控制块。
2. 控制块建立与 `Derived` 对象对应的销毁机制。
3. 转换为 `shared_ptr<Base>` 时，共享原来的控制块。
4. 最后一个强引用消失时，仍按照原来的销毁机制析构 `Derived`。
输出：
```cpp
~Derived
~Base
```
核心原因：转换 shared_ptr 的类型不会改变原来控制块的销毁策略。
###### 情况 D：unique_ptr< Derived> 转换为 unique_ptr<Base>
```cpp
std::unique_ptr<Base> p =
    std::make_unique<Derived>();
```
在当前 Base 没有虚析构函数的条件下，这段代码同样存在未定义行为。
为什么？因为 `unique_ptr<Base>` 使用默认删除器时，最终通常执行相当于：
```cpp
Base* raw = /* 指向 Derived 对象 */;

delete raw;
```
而 `Base` 没有虚析构函数，无法满足正常通过基类指针销毁派生类对象的要求。
所以对于这样的默认删除器，应该改成：
```cpp
class Base
{
public:
    virtual ~Base()
    {
        std::cout << "~Base\n";
    }
};
```
此时：
```cpp
std::unique_ptr<Base> p =
    std::make_unique<Derived>();
```
就可以正确销毁整个派生类对象。
##### 五种常见写法对比

|创建方式|Base 没有虚析构函数|原因|
|---|---|---|
|`shared_ptr<Base>(new Derived)`|正确|创建控制块时保留 Derived 删除策略|
|`shared_ptr<Base>(Base* 指向 Derived)`|未定义行为|默认通过 Base* 删除|
|`make_shared<Derived>()` 转为 `shared_ptr<Base>`|正确|共享原控制块的 Derived 销毁机制|
|`make_unique<Derived>()` 转为 `unique_ptr<Base>`|未定义行为|默认删除器使用 Base* 删除|
|上述写法，且 Base 具有虚析构函数|通常都能正确销毁|基类指针支持正确的多态析构|
以上结论针对标准默认删除机制和普通单继承情形；特殊自定义删除器或销毁删除函数可能改变结论。

### 第 5 题：`shared_ptr` 有哪些所有权陷阱，怎样正确进行转换、借用和比较？

比较复制、从裸指针构造和别名构造这三种写法：

```cpp
struct Player
{
    int health = 100;
    ~Player() { std::cout << "~Player\n"; }
};

void TestOwners()
{
    auto owner = std::make_shared<Player>();
    auto copy = owner;
    // std::shared_ptr<Player> another(owner.get());
    std::shared_ptr<int> health(owner, &owner->health);

    owner.reset();
    copy.reset();
    std::cout << *health << '\n';
}
```

哪些变量共享控制块？`health` 最终负责保持哪个对象存活？如果启用注释语句，会怎样改变控制块和释放关系？

**必答范围：所有权组 → 重复接管 → 别名与类型转换 → 观察接口。**

1. 从同一裸指针分别创建两个 `shared_ptr`，与复制已有 `shared_ptr` 有什么区别？接管栈对象、对 `this` 直接构造共享指针、重新接管 `get()` 的结果分别有什么风险？
2. `get()`、`reset()` 是否转移或解除整个所有权组的管理？为什么标准 `shared_ptr` 没有 `release()`？`unique_ptr` 与 `shared_ptr` 能否双向转换，`use_count()==1` 是否足以反向接管？
3. 什么是别名构造？存储指针、实际管理的资源及控制块可以是什么关系？如何让成员子对象的句柄保持外层对象存活？内部容器扩容后还可能有哪些悬空风险？
4. `static_pointer_cast`、`dynamic_pointer_cast`、`const_pointer_cast`、`reinterpret_pointer_cast` 各适合什么情况？如何保留原所有权？转换失败、错误向下转换、修改真正的 const 对象分别怎样分析？
5. `get()`、布尔转换、`use_count()`、地址相等和所有权等价各能说明什么？【进阶，首轮可略】能否出现「有所有权但地址为空」或「地址非空但没有所有权」？【进阶，首轮可略】`owner_before/owner_less` 怎样使用？
#### 正确回答
`shared_ptr` 的所有权由控制块管理，复制已有 `shared_ptr` 会共享控制块，而从同一个裸指针分别创建两个 `shared_ptr`，会建立独立所有权组，可能导致重复释放。
`get()` 只返回非拥有型原始指针，`reset()` 只解除当前指针的共享所有权。标准 `shared_ptr` 没有与 `unique_ptr` 对应的 `release()` 接口。
`unique_ptr` 可以通过移动转换为 `shared_ptr`，但不能直接反向转换。
`shared_ptr` 支持别名构造，使存储指针可以指向成员子对象，同时共享外层对象的控制块，延长外层对象生命周期。
类型转换可以使用 `static_pointer_cast`、`dynamic_pointer_cast` 等接口，它们能够保留原共享所有权关系。
最后，指针地址相等不代表所有权等价，因为共享所有权由控制块决定，而不是单纯由对象地址决定。

| 2. 所有权管理接口   | 部分正确 | `get()` 不等于 `weak_ptr`；`unique_ptr` 可以转为 `shared_ptr` |
| 3. 别名构造      | 不会   | 不清楚管理对象和访问对象可以不同                                      |

| 5. 观察与比较     | 不会   | 不清楚地址相同与所有权相同的区别                                      |
#### 示例
##### 一、为什么同一个裸指针不能创建两个独立 shared_ptr？（第 1 问）
你之前学过：
```cpp
auto p1 = std::make_shared<int>(10);
auto p2 = p1;
```
这种写法正确。
因为 `p2` 是复制 `p1` 得到的，它们共享同一个控制块。
![](../../_Pasted_Image/Pasted%20image%2020261027155919.png)
###### 错误写法
```cpp
int* raw = new int(10);

std::shared_ptr<int> p1(raw);
std::shared_ptr<int> p2(raw); // 错误！
```
这里不是复制已有的 `shared_ptr`，而是使用同一个裸指针分别构造两个共享指针。
结果是：
![](../../_Pasted_Image/Pasted%20image%2020261027155946.png)
当 `p1` 和 `p2` 分别析构时，各自控制块都会尝试清理同一资源。
因此，不能对已经由 shared_ptr 管理的裸指针再次建立独立所有权。
同样的错误还有：
```cpp
auto owner = std::make_shared<int>(10);

std::shared_ptr<int> another(owner.get()); // 错误
```
`get()` 只是返回裸指针，不会把原来的控制块一起交给 `another`。
###### 那么 shared_ptr(this) 为什么也危险？
```cpp
std::shared_ptr<MyClass> p(this);
```
如果当前对象已经由另一个 `shared_ptr` 管理，这样写就会创建第二个独立控制块。
正确做法通常是使用 `std::enable_shared_from_this` 和 `shared_from_this()` 获取共享现有控制块的指针。
这个知识点会在第 7 题详细学习。
另外，不能用默认删除策略的 `shared_ptr` 随意接管栈对象，否则可能尝试删除不属于动态分配的对象。
##### 二、get、reset、release 和 unique_ptr 转换（第 2 问）
###### 1. get() 不等于 weak_ptr
你说：get 获取的原始指针没有所有权，所以应该算 weak 指针。
这不准确。
```cpp
auto p = std::make_shared<int>(10);

int* raw = p.get();
```
这里的 `raw` 就是一个普通的 `int*`。
它不拥有资源，但它也没有 `weak_ptr` 的安全观察机制。
区别是：

|对比|`get()` 返回的裸指针|`weak_ptr`|
|---|---|---|
|是否拥有资源|否|否|
|是否关联控制块|否|是|
|能否检查对象是否过期|无内建机制|可以通过 `expired()`|
|能否尝试获取有效强引用|不可以|可以通过 `lock()`|
如果 `p` 是最后一个强所有者：
```cpp
p.reset();
```
原来的 `raw` 就会悬空。所以裸指针的非拥有型借用关系和 weak_ptr 的弱引用关系不是同一个概念。
###### 2. reset() 只解除当前 shared_ptr 的所有权
```cpp
auto p1 = std::make_shared<int>(10);
auto p2 = p1;

p1.reset();
```
执行后：
- `p1 == nullptr`
- `p2` 仍然管理 `int(10)`
- 强引用计数从 2 变成 1
- `int(10)` 没有被销毁
`reset()` 不会强制让其他共享所有者全部失效。
###### 3. 为什么 shared_ptr 没有 release()？
`unique_ptr` 可以安全地表达“我放弃独占所有权，由其他代码负责清理”。但 `shared_ptr` 可能存在多个共享所有者。
假设：
```cpp
auto p1 = std::make_shared<int>(10);
auto p2 = p1;
```
如果 `p1` 能够直接取出原始指针并随意转移清理责任，就可能与 `p2` 的共享所有权冲突。
所以标准 `shared_ptr` 不提供类似 `unique_ptr::release()` 的所有权释放接口。
###### 4. unique_ptr 与 shared_ptr 可以互相转换吗？
可以从 unique_ptr 转成 shared_ptr。
```cpp
std::unique_ptr<int> p1 =
    std::make_unique<int>(10);

std::shared_ptr<int> p2 = std::move(p1);
```
执行后：
- `p1` 为空。
- `p2` 接管资源。
- 为该共享所有权建立控制块。
但不能直接从 `shared_ptr` 反向转换成 `unique_ptr`。

即使：
```cpp
p.use_count() == 1
```
也不能因此安全地把共享所有权直接改造成独占所有权。因为还可能存在弱引用、外部借用、特殊删除器、别名所有权等情况，而且标准库没有提供这样的直接逆向转换操作。
##### 三、什么是 shared_ptr 别名构造？（第 3 问）
这是你这次完全不了解的知识点。

先分析文档中的代码：
```cpp
struct Player
{
    int health = 100;

    ~Player()
    {
        std::cout << "~Player\n";
    }
};

void TestOwners()
{
    auto owner = std::make_shared<Player>();
    auto copy = owner;

    // std::shared_ptr<Player> another(owner.get());

    std::shared_ptr<int> health(owner, &owner->health);

    owner.reset();
    copy.reset();

    std::cout << *health << '\n';
}
```
最重要的是这一句：
```cpp
std::shared_ptr<int> health(owner, &owner->health);
```
这叫作 别名构造（Aliasing Constructor）。

你可以这样理解：
- `owner` 原来负责管理整个 `Player` 对象。
- `health` 保存的是 `Player::health` 成员的地址。
- 但是 `health` 共享 `owner` 的控制块。
- 所以 `health` 可以让整个 `Player` 对象继续存活。
![](../../_Pasted_Image/Pasted%20image%2020261027190446.png)
当执行：
```cpp
owner.reset();
copy.reset();
```
虽然 `owner` 和 `copy` 已经放弃所有权，但 `health` 仍然共享原来的控制块。因此，`Player` 还活着。
最后输出：
```cpp
100
~Player
```
`~Player` 在 `health` 离开作用域时才输出。
###### 别名构造有什么风险？
假设 `Player` 内部是一个会扩容的 `vector`：
```cpp
struct Player
{
    std::vector<int> values;
};
```
如果别名智能指针保存的是某个 `vector` 元素的地址，那么即使外层 `Player` 还活着，`vector` 扩容后原来的元素地址也可能失效。
因此：别名构造保证共享的拥有关系，但不自动保证它保存的成员地址始终有效。

##### 四、四种智能指针类型转换（第 4 问）
这部分与你之前学过的 `static_cast`、`dynamic_cast` 等知识基本对应。
区别是智能指针版本会保留共享所有权关系，不会重新建立独立控制块。

|接口|主要作用|注意事项|
|---|---|---|
|`static_pointer_cast`|编译期允许的指针类型转换|不检查实际动态类型是否符合错误的向下转换假设|
|`dynamic_pointer_cast`|运行时检查多态类型转换|失败返回空 shared_ptr|
|`const_pointer_cast`|调整 const 限定|不能合法修改本来就是 const 的对象|
|`reinterpret_pointer_cast`|低层指针重新解释|容易违反类型访问、对齐等规则|
###### 1. static_pointer_cast
```cpp
std::shared_ptr<Base> base =
    std::make_shared<Derived>();

auto derived =
    std::static_pointer_cast<Derived>(base);
```
如果实际对象确实是 `Derived`，这种转换可以成立。但错误向下转换没有自动的运行时保护。
###### 2. dynamic_pointer_cast
```cpp
std::shared_ptr<Base> base =
    std::make_shared<Derived>();

auto derived =
    std::dynamic_pointer_cast<Derived>(base);
```
对于合适的多态基类，`dynamic_pointer_cast` 会在运行时检查实际对象类型。如果转换失败，得到空的共享指针，而不是有效的派生类指针。
###### 3. const_pointer_cast
```cpp
std::shared_ptr<const int> p =
    std::make_shared<int>(10);

auto q = std::const_pointer_cast<int>(p);
```
这里只是类型限定发生变化。如果底层对象原本真正定义为 const，那么通过移除 const 后的指针修改它，仍属于未定义行为。
###### 4. reinterpret_pointer_cast
用于低层重新解释指针类型。
但它不会保证指向的存储中真的存在目标类型的对象，因此不能因为转换编译成功，就认为访问一定合法。
面试时优先理解 `static_pointer_cast` 和 `dynamic_pointer_cast`，其他两个掌握适用边界即可。
##### 五、get、bool、use_count、地址相等分别说明什么？（第 5 问）

|操作|表示什么|
|---|---|
|`p.get()`|返回保存的原始指针|
|`if (p)`|检查存储指针是否非空|
|`p.use_count()`|当前共享所有权组的强引用数量|
|`p1.get() == p2.get()`|两个指针保存的地址是否相同|
|所有权等价|两个 shared_ptr 是否共享同一所有权组|
这里有一个高频陷阱：两个 shared_ptr 保存相同的地址，不代表它们共享同一个控制块。
这正是第 1 问的错误情况。
反过来，通过别名构造创建的两个共享指针，也可能保存不同的访问地址，但共享同一个控制块。
`owner_before` / `owner_less` 可以用于所有权关系相关的排序与比较，首轮了解即可。

#### 正确回答

#### 我存在的问题
|考点|判断|主要问题|
|---|---|---|
|父子对象循环引用|基本正确|知道互相强引用会导致对象无法析构|
|1. weak_ptr 的作用|部分正确|不清楚为什么不能解引用|
|2. lock / expired / use_count|部分错误|把 `lock()` 当成权限锁，把 `use_count()` 当成弱引用计数|
|3. 多线程安全|不会|不理解检查与访问之间的竞争窗口|
|4. 其他循环引用场景|不会|不清楚 lambda、事件订阅等场景|
|5. 缓存与观察者|不会|不理解强缓存与弱缓存的生命周期区别|
首先纠正三个关键概念：
1. `weak_ptr::lock()` 不是互斥锁。 它的作用是尝试从弱引用获得一个临时的 `shared_ptr`，从而确保对象在使用期间存活。
2. `weak_ptr::use_count()` 返回强引用计数，不是弱引用计数。
3. `weak_ptr` 并不是不允许修改对象。 只要 `lock()` 成功，并且对象的类型和 const 限定允许修改，就可以通过得到的 `shared_ptr` 修改对象。

##### 一、为什么父子对象会发生循环引用？
你对原代码的判断正确。
```cpp
parent->child = child;
child->parent = parent;
```
这会形成下面的所有权关系：
![](../../_Pasted_Image/Pasted%20image%2020261028163416.png)
当 `TestFamily()` 结束，局部变量 `parent`、`child` 都会析构，但两个对象内部仍然相互持有强引用，强引用计数无法归零。

因此不会输出析构日志。

###### 应该怎样修改？
业务要求是：父对象拥有子对象，子对象只观察父对象。
所以改成：
```cpp
struct Parent;

struct Child
{
    std::weak_ptr<Parent> parent;

    ~Child()
    {
        std::cout << "~Child\n";
    }
};

struct Parent
{
    std::shared_ptr<Child> child;

    ~Parent()
    {
        std::cout << "~Parent\n";
    }
};
```
这样：
- `Parent → Child`：强引用，负责所有权。
- `Child → Parent`：弱引用，只负责观察。

`TestFamily()` 结束时可以正常析构，输出：
```cpp
~Parent
~Child
```
注意：不能随意决定弱化哪一条引用。 如果业务规定子对象拥有父对象，就应该根据这种所有权语义重新设计引用方向，而不是仅为了消除环就随意改动。

##### 二、lock() 到底是什么？（重点）

你说： lock 是申请访问与修改对象资源的权限。

这里需要重点纠正。
`weak_ptr::lock()` 不是获取互斥锁，也不是申请访问权限，而是尝试获得共享所有权。

例如：
```cpp
auto p = std::make_shared<int>(10);

std::weak_ptr<int> w = p;

auto temp = w.lock();
```
执行过程如下：
![](../../_Pasted_Image/Pasted%20image%2020261028163438.png)
因此，推荐这样使用：
```cpp
if (auto sp = w.lock())
{
    *sp = 20;
}
```
这里发生了什么？
1. `w.lock()` 尝试获得有效的强引用。
2. 成功后，`sp` 是一个 `shared_ptr<int>`。
3. 在 `sp` 保持所有权期间，对象不会因为强引用计数归零而析构。
4. 如果对象不是 const，就可以通过 `sp` 修改对象。
如果 `w` 的类型是 `std::weak_ptr<const int>`，得到的是 `std::shared_ptr<const int>`，便不能通过它修改整数。
###### 为什么 weak_ptr 不能直接解引用？
因为弱引用不会延长对象生命周期。如果允许直接 `*w`，对象可能已经销毁，就会有悬空访问风险。所以标准库要求先通过 `lock()` 获取有效强引用，再访问对象。
##### 三、expired()、lock()、use_count() 的区别

|函数|作用|
|---|---|
|`expired()`|判断对象是否已过期，即强引用计数是否为 0|
|`use_count()`|查询当前强引用计数|
|`lock()`|尝试获取新的 `shared_ptr`，成功则保持对象存活|
例如：
```cpp
auto p = std::make_shared<int>(10);
std::weak_ptr<int> w = p;

std::cout << w.use_count() << '\n'; // 1
std::cout << w.expired() << '\n';   // 0

p.reset();

std::cout << w.use_count() << '\n'; // 0
std::cout << w.expired() << '\n';   // 1

auto sp = w.lock();                 // 空 shared_ptr
```
对象一旦销毁，`weak_ptr` 不能通过 `lock()` 将其重新恢复。
还有一个面试考点：
```cpp
std::shared_ptr<int> sp(w);
```
如果 `w` 已过期，这种构造会抛出 `std::bad_weak_ptr`。
而：
```cpp
auto sp = w.lock();
```
失败时只是返回空的 `shared_ptr`，不会因为过期而抛这个异常。
##### 四、为什么先 expired() 再访问可能不安全？
你这部分说不知道，我们通过多线程例子理解。
```cpp
if (!w.expired())
{
    auto sp = w.lock();
}
```
假设：
1. 线程 A 调用 `expired()`，发现对象还存在。
2. 线程 B 释放了最后一个 `shared_ptr`。
3. 对象被销毁。
4. 线程 A 再调用 `lock()`，结果失败。
因此：`expired() == false` 只代表检查当时对象还活着，不能保证后续访问时对象仍然存活。

正确方式：
```cpp
if (auto sp = w.lock())
{
    sp->DoSomething();
}
```
`lock()` 会原子地尝试获取强引用。如果成功，至少在这个 `sp` 有效期间，对象不会被销毁。
但注意：`lock()` 只保证对象生命周期，不保证对象内部数据的线程安全。
如果多个线程同时修改对象成员，仍然可能需要 `std::mutex` 等同步机制。另外，多个线程同时修改同一个 `weak_ptr` 变量本身，也需要相应同步。
##### 五、循环引用还会出现在哪些地方？
除了父子对象互相持有，游戏客户端中还常见下面这种情况。
###### lambda 捕获 shared_ptr
假设对象内部保存一个回调：
```cpp
struct Enemy
{
    std::function<void()> callback;

    void Attack() {}

    ~Enemy()
    {
        std::cout << "~Enemy\n";
    }
};
```
错误写法：
```cpp
auto enemy = std::make_shared<Enemy>();

enemy->callback = [enemy]()
{
    enemy->Attack();
};
```
由于 lambda 按值捕获 `enemy`，它内部保存了一个 `shared_ptr<Enemy>`。
所有权关系变成：
```cpp
Enemy 对象
    ↓ 持有
callback
    ↓ 捕获 shared_ptr
Enemy 对象
```
即使外部的 `enemy` 变量析构，对象仍可能因这个自引用环无法释放。
可以改为弱引用：
```cpp
std::weak_ptr<Enemy> weakEnemy = enemy;

enemy->callback = [weakEnemy]()
{
    if (auto sp = weakEnemy.lock())
    {
        sp->Attack();
    }
};
```
这样回调不会强制延长 `Enemy` 的生命周期。
这种思想也适用于事件订阅、异步回调和部分观察者关系。
##### 六、强缓存和弱缓存有什么区别？
假设游戏中需要缓存敌人模型资源。

|缓存类型|存储方式|生命周期特点|
|---|---|---|
|强缓存|`shared_ptr<Resource>`|缓存本身保持资源存活|
|弱缓存|`weak_ptr<Resource>`|缓存不延长资源生命周期|
|弱观察者列表|`weak_ptr<Observer>`|不因注册观察者而强制让观察者存活|
例如：
```cpp
std::unordered_map<std::string,
                   std::weak_ptr<Resource>> cache;
```
查询时：
```cpp
auto resource = cache["EnemyModel"].lock();

if (!resource)
{
    // 资源已不存在，需要重新加载或创建
}
```
弱缓存适合希望资源在无人使用后能够自动销毁的情况。
不过弱缓存也需要清理过期条目。对于 `make_shared` 的合并分配，长期保留弱引用还可能使部分分配存储继续保留。
另一方面，即使没有循环引用，只要强缓存始终持有 `shared_ptr`，资源就会一直存活。因此缓存是否长期占用内存，并不完全取决于有没有循环引用。
