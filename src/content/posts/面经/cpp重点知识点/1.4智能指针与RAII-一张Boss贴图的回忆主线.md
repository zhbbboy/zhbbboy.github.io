# 智能指针与 RAII：一张 Boss 贴图的回忆主线

> 配套笔记：[10 道综合面试题与学习记录](<4.智能指针与RAII.md>)。本文用于学完后的串联回忆。

## 先复习这一版：一张 Boss 贴图串起 10 道题

**只用一个场景：创建贴图 → 交给角色 → UI 共享 → 缓存观察 → 注册刷新回调 → 多线程读取 → 退出关卡清理。**

先记这一句：**资源随对象清理；独占靠移动，共享认控制块；弱引用先 lock，回调查捕获；线程分三层，UE 先分体系。**

主例使用普通 C++ 的 `Texture`，用一个像素数组代表它拥有的资源。后面的并发和 UE 内容都接着这张贴图展开。先读主例和生命周期表，忘记哪个分支，再回到对应原题。

### 主例：从独占贴图到共享、观察和销毁

这是一份可独立编译的 C++17 程序。`onRefresh` 是贴图自己保存的回调，`task` 模拟事件系统保存的另一份回调。

```cpp
#include <functional>
#include <iostream>
#include <memory>
#include <utility>

struct Asset {
    virtual ~Asset() = default;
};

struct Texture final : Asset, std::enable_shared_from_this<Texture> {
    std::unique_ptr<int[]> pixels = std::make_unique<int[]>(4);
    int width = 2;
    std::function<void()> onRefresh;

    Texture() { std::cout << "load\n"; }
    ~Texture() override { std::cout << "destroy\n"; }

    void Connect() {
        onRefresh = [w = weak_from_this()] {
            if (auto self = w.lock()) {
                std::cout << "refresh=" << self->width << '\n';
            } else {
                std::cout << "skip\n";
            }
        };
    }
};

int main() {
    std::weak_ptr<Texture> cache;
    std::function<void()> task;

    auto prepared = std::make_unique<Texture>();
    std::shared_ptr<Texture> actor(std::move(prepared));
    actor->Connect();

    auto ui = actor;
    std::shared_ptr<Asset> generic = actor;
    std::shared_ptr<int> width(actor, &actor->width);
    cache = actor;
    task = actor->onRefresh;

    std::cout << "owners=" << actor.use_count() << '\n';
    actor.reset();
    ui.reset();
    task();

    generic.reset();
    std::cout << "width=" << *width << '\n';
    width.reset();
    task();

    std::cout << std::boolalpha << "expired=" << cache.expired() << '\n';
    cache.reset();
    task = {};
}
```

先预测输出，再对照：

```text
load
owners=4
refresh=2
width=2
destroy
skip
expired=true
```

#### 一张所有权图：谁负责让贴图活着？

图中的箭头表示拥有或观察关系，不是编译器内存布局。

```text
actor、ui、generic、width ── 强拥有 ──→ 同一个控制块 ── 管理 ──→ Texture
                                                                  │
                                                        pixels 独占 int[4]

width.get() ── 访问 ──→ Texture.width
cache、回调捕获的 w ── 弱观察 ──→ 同一个所有权组
```

**找谁释放，看控制块；读写哪里，看存储指针。** `width` 访问的是一个 `int`，却与其他三个共享指针一起保持整个 `Texture` 存活。`generic` 的静态类型变了，所有权组没有变。

#### 一条时间线：对象和控制块为什么不同时消失？

| 动作 | 强所有者数量 | 此刻应该想到什么 |
| --- | ---: | --- |
| `make_unique<Texture>()` | 尚未建立共享控制块 | `prepared` 独占贴图，贴图又通过 `pixels` 独占数组 |
| 移动进 `actor` | 1 | `prepared` 变空，转交的是拥有关系，贴图本身没有被搬走 |
| 建立 `ui/generic/width` | 4 | 复制、向上转换、别名构造都加入原所有权组 |
| 建立 `cache/task` | 仍为 4 | 两者存的是弱观察关系，不是新的强拥有者 |
| `actor.reset()`、`ui.reset()` | 4 → 3 → 2 | 放弃当前句柄的份额；贴图还有 `generic/width` 持有 |
| 第一次 `task()` | 临时 2 → 3 → 2 | `lock()` 成功产生局部 `self`，回调结束再释放它 |
| `generic.reset()` | 1 | 最后一个强所有者是访问成员的 `width` |
| `width.reset()` | 0 | 执行贴图销毁；析构函数体输出后，成员继续按规则析构，像素数组自动清理 |
| 第二次 `task()` | 0 | 弱引用不能复活贴图，回调跳过；`cache.expired()` 为真 |
| `cache.reset()` | 0 | `task` 仍捕获弱引用，控制块还需保留 |
| `task = {}` | 0 | 外部弱引用也全部放下，控制块才可以回收 |

注意：`Texture` 内部的 `onRefresh` 和 `enable_shared_from_this` 关联信息，也会随对象销毁而清理。上表不把控制块内部弱计数硬编码成某个用户可见数字。[共享销毁规则](https://eel.is/c++draft/util.smartptr.shared.dest)、[弱引用观察接口](https://eel.is/c++draft/util.smartptr.weak.obs)

**主例第一遍只回答三件事：谁还强持有贴图？`lock()` 有没有拿到临时强引用？最后还剩哪份弱引用保留控制块？**

### 沿着“创建 → 交接”，想起独占、RAII 和分配

#### 创建时：外层管贴图，贴图管像素

`prepared` 管理一个 `Texture`，`pixels` 管理 `int[4]`，是两层资源所有权。正常返回、提前返回、异常栈展开时，都让已构造成功的 RAII 对象按规则清理。若 `Texture` 构造函数抛异常，不执行这个完整对象的析构函数，但已构造好的 `pixels` 成员会被清理。

把像素资源换成文件、`malloc` 内存或池内对象，就沿同一条线追问：**获取协议是什么，最终该调用 `fclose`、`free`，还是“析构对象 + 归还槽位”？** 删除器必须匹配，依赖的池或句柄系统必须仍然有效。删除器管资源清理，分配器管相应存储的分配归还，二者不能混同。

回忆 `unique_ptr` 的四个接口，只在尚未交给 `actor` 的 `prepared` 上想：

| 操作 | 在这张贴图上记什么 |
| --- | --- |
| `prepared.get()` | 借用地址；拥有者仍负责销毁，外部不能再自行 `delete` |
| `prepared.release()` | 交出责任、不销毁；调用方必须按原释放协议接回管理 |
| `prepared.reset()` | 清理原资源；可以再接管另一个匹配的指针 |
| `prepared.swap(other)` | 交换管理状态，包括对应删除器 |

`reset(get())`、从 `get()` 创建第二个独立拥有者都不能当作正常的所有权交接。数组使用 `unique_ptr<T[]>` 的对应删除方式，但它不保存长度、不检查越界；需要长度和扩容时考虑 `vector`。[独占指针接口](https://eel.is/c++draft/unique.ptr.single.modifiers)、[创建与数组初始化](https://eel.is/c++draft/unique.ptr.create)

`std::move(prepared)` 本身只是转换表达式，实际交接由构造 `actor` 的操作完成。**这里移动的是拥有者，不是 `Texture` 对象。** 本例有用户声明的析构函数和不可复制成员，不能顺便推断 `Texture` 自身可复制或具有隐式移动操作。业务类优先让成员管理资源；真要支持复制再设计深拷贝，真要支持对象移动再检查特殊成员函数。

#### 交接时：先问是否真的需要共享，再问怎么分配

主例先演示独占，再将其升级为共享。对象在此前已经由 `make_unique` 创建，建立共享所有权时再取得控制块所需的管理存储。如果业务一开始就需要共享，可直接使用 `std::make_shared<Texture>()`，后面的共享、观察和销毁逻辑继续适用。

`make_shared` 典型实现合并对象与控制块的分配；从 `new Texture` 建立共享所有权，典型实现则分开分配。**不要把合并分配理解成“所有资源都在同一块里”**：主例的 `pixels` 数组仍是另一份分配；函数对象等也可能有各自的分配行为。

若改用 `make_shared`，强引用归零后贴图析构，`pixels` 仍会释放自己的数组；但包含贴图原位置的合并分配块，可能等外部弱引用也消失后才能整体归还。对象内嵌的大数组与指向外部缓冲区的成员，需要分别分析。[共享创建规则](https://eel.is/c++draft/util.smartptr.shared.create)

异常追问也放在这里：**构造失败，清理已构造成员；共享控制块创建失败，由对应构造协议处理已取得的资源；裸指针接管前抛异常，不能指望尚未建立的 RAII 自动补救。** C++17 前后的实参求值规则不同，不能把旧的交错求值泄漏情形不加限定地套用到所有版本。

#### `generic` 提醒你：接口类型变了，销毁策略有没有丢？

本例 `Asset` 使用虚析构。若讨论非虚析构变体，需同时去掉 `~Texture` 的 `override`，再比较下面的默认删除路径；不要实际运行不合法删除来猜结果。

- `unique_ptr<Texture>` 转成默认删除器的 `unique_ptr<Asset>`：最终通过 `Asset*` 删除，需要满足基类多态删除规则。
- `shared_ptr<Asset>(new Texture)`，或由 `make_shared<Texture>()` 转成基类共享指针：原所有权组保留具体对象的销毁方式。
- 先得到一个静态类型为 `Asset*` 的裸指针，再交给默认删除的 `shared_ptr<Asset>`：如果基类析构非虚，不能靠 `shared_ptr` 自动补回已丢失的删除类型信息。

**最后怎么删，看建立所有权时保存的策略；不要只看最后一个变量写的是 `shared_ptr<Base>`。** 工程中仍应为允许经基类销毁的多态接口设计合适的析构方式。

### 沿着“共享 → 观察 → 回调”，想起控制块和引用环

#### 共享只认原所有权组

`ui = actor` 共享控制块；另写 `shared_ptr<Texture>(actor.get())` 则会重新建立独立的控制块，产生重复销毁风险。普通指针地址相等，不足以证明所有权相同；`width` 与 `actor` 的访问地址不同，也不妨碍它们共享所有权。

要把 `generic` 转回贴图接口，用保留原所有权的 `dynamic_pointer_cast<Texture>(generic)` 等转换接口。向下动态转换依赖相应多态/RTTI 条件，失败得到空指针；静态转换不会替你检查真实动态类型。去 const 不会赋予修改真正 const 对象的权利，reinterpret 转换也不会修复别名、对齐或生命周期问题。[共享指针转换](https://eel.is/c++draft/util.smartptr.shared.cast)

`shared_ptr` 的 `reset()` 只是交还当前份额，没有通用的 `release()`；观察到 `use_count()==1` 也不能把 `get()` 直接塞进 `unique_ptr`。主例的“独占 → 共享”不是能任意倒放的操作。

#### 弱引用不是锁权限，而是临时争取一份所有权

`cache` 不让贴图续命；`lock()` 成功时，局部 `self` 才在使用期间保持贴图存活。它不是互斥锁，不防止其他线程修改贴图。通过 `self` 能否修改对象取决于类型限定，而不是“弱指针只能读”。

不要只记 `expired()` 的布尔值：它可能在下一刻过时。访问通常直接使用 `if (auto self = w.lock())`。从已过期弱引用显式构造 `shared_ptr` 会抛 `bad_weak_ptr`，而 `lock()` 失败返回空指针；`weak_ptr::use_count()` 观察的是强所有者数量。

#### 回调只改“捕获谁”，就能带出自身引用和循环引用

| 对 `onRefresh` 做的变体 | 生命周期如何变化 |
| --- | --- |
| 捕获裸 `this` | 回调不保活；外部 `task` 比贴图活得久时，调用就可能访问悬空对象 |
| 捕获 `self = shared_from_this()` | 回调保活；因为本例贴图自己保存回调，会形成 `Texture → onRefresh → Texture` 强引用环 |
| 捕获 `w = weak_from_this()` | 主例写法；不保活，执行时 `lock()`，失效则跳过 |

若强回调只由外部任务队列持有，并不存在返回对象的强拥有路径，就不一定形成环，只是把生命周期延长到任务释放。是否用强捕获，取决于任务是否必须保活对象，不能机械地全部换成弱捕获。

`Connect()` 放在建立共享所有权之后，正是 `enable_shared_from_this` 的回忆入口：**获取自身应加入已有控制块，不是用 `shared_ptr(this)` 再建一个。** 本例继承公开且无歧义；构造期间尚未建立关联，不能直接依赖 `shared_from_this()`，提前保存的空 `weak_from_this()` 副本也不会在以后自动补上关联。析构期间同样不能靠它重新保活自身。[自身引用接口](https://eel.is/c++draft/util.smartptr.enab)

把同一个规则用于父子对象、UI 订阅和事件系统：先画强拥有路径，再把“只观察、不负责续命”的回指设计为弱引用。强缓存没有环也可能长期保留贴图；弱缓存则要处理过期、重新加载和清理条目。**不析构先查谁还强持有，不能只查有没有裸指针丢失。**

### 沿着“传给接口 → 放进容器”，想起借用、const 和性能

仍然只传这张贴图，按函数是否需要负责生命周期来选参数：

| 接口形式 | 在主例中如何回忆 |
| --- | --- |
| `Use(const Texture&)` | 必须有对象，只借用并通过该路径只读 |
| `MaybeUse(Texture*)` | 允许为空的借用，不获得释放责任 |
| `Take(unique_ptr<Texture>)` | 接收 `prepared` 的独占所有权；调用者明确移动交接 |
| `Keep(shared_ptr<Texture>)` | 参数自己持有一份共享所有权，可供后续保留 |
| `Inspect(const shared_ptr<Texture>&)` | 借用这个句柄；若函数内可能重入并重置原句柄，按需复制一份来保活 |
| `Replace(shared_ptr<Texture>&)` | 可以替换调用方的句柄 |

`const shared_ptr<Texture>` 限制句柄修改，`shared_ptr<const Texture>` 限制经该指针修改贴图。后者不消除其他可变别名，也不意味着对象内部资源深层不可变。[接口语义建议](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#Rr-smartptrparam)

把 `prepared` 放入 `vector<unique_ptr<Texture>>`：扩容可能改变**智能指针元素**的位置，通常不搬动其独立拥有的贴图；清除对应拥有者后，借用的 `Texture*` 仍会失效。再把 `pixels` 换成 `vector<int>`，像素缓冲区扩容就可能让旧的元素地址失效，哪怕贴图还活着。**保住外层对象，不等于保住所有内部地址。**

从这里继续回答性能：值和连续数据有局部性优势；独占指针带来间接访问，但不需要共享计数；共享指针还要管理控制块与计数，频繁跨线程复制可能产生竞争。普通解引用通常直接使用存储指针，不是每次都先查控制块；大小、分配次数及优化收益按目标实现测量。

### 同一张贴图的变体一：加载线程发布，渲染线程读取

复用主例的 `Asset/Texture` 定义，不重复定义它们，也不使用主例的 `main`。下面两个函数分别由不同线程调用，使用 C++20；读取早于发布时，允许暂时拿不到贴图。

```cpp
#include <atomic>

std::atomic<std::shared_ptr<const Texture>> current;

void PublishTexture() {
    auto next = std::make_shared<Texture>();
    next->width = 4;
    current.store(std::move(next), std::memory_order_release);
}

void TryReadTexture() {
    auto snapshot = current.load(std::memory_order_acquire);
    if (snapshot) {
        std::cout << "render=" << snapshot->width << '\n';
    }
}
```

这里的约定是**发布完成后不再修改该对象**。读线程取得快照后，在快照存活期间对象不会因为槽位被替换而销毁；如果还要并发修改贴图字段，需要另外设计同步。

| 问题落在哪一层 | 用主例记规则 |
| --- | --- |
| 控制块 | 不同线程操作各自的共享指针副本，共享计数管理有安全保证 |
| 同一个指针变量 | 多线程读写同一个 `current` 槽位，需要互斥锁或原子智能指针 |
| `Texture` 对象本身 | 共享句柄和计数安全不替代字段同步；本变体选择发布后只读 |

release/acquire 在读取取得相应发布结果时建立可见性联系；原子智能指针不保证无锁，析构和存储释放也不应被理解为全都发生在一个原子步骤里。[原子共享指针](https://eel.is/c++draft/util.smartptr.atomic.shared)、[相关计数与释放规则](https://eel.is/c++draft/util.smartptr.atomic.general)

最后一份强引用可能在加载线程、渲染线程或主线程中释放。真实图形资源若要求在特定线程清理，应通过资源封装、删除器和线程队列安排；队列与分配器还必须活到所有相关清理完成。**先分析最后谁放手，再分析允许谁执行释放。**

### 同一张贴图的变体二：搬进 UE，先判断它是哪类对象

| 仍然是这条资源链 | UE 中先想什么 |
| --- | --- |
| 普通 C++ 贴图描述、工具数据或任务对象 | 按项目约定使用 `TUniquePtr`、`TSharedPtr`、`TWeakPtr`；需要非空共享句柄时考虑 `TSharedRef` |
| 回调需要观察普通 C++ 对象 | `TWeakPtr::Pin()` 对照标准库的 `weak_ptr::lock()`；获取自身关联 `TSharedFromThis` |
| 贴图变成 `UTexture2D`，角色变成 Actor | 进入 UObject 生命周期体系，不能照搬主例的默认 `delete`/普通共享指针管理方式 |
| 可被 GC 追踪的 UObject 成员强引用 | 在相应反射结构中按要求使用 `UPROPERTY()` 标记的 `TObjectPtr`，不能只看指针类型就断定参与 GC |
| 观察可能销毁的目标、按需加载资源、普通 C++ 持有 UObject | 分别联系 `TWeakObjectPtr`、`TSoftObjectPtr`、`TStrongObjectPtr` 或显式 GC 引用收集方案 |

资源路径不等于保活已加载对象；GC 保活也不等于 Actor 永远不能被显式销毁。回调要考虑有效性、取消、退订和游戏线程约束。`ESPMode::ThreadSafe` 主要保障相应共享引用管理，不能替代对象数据同步或 UObject 的线程访问规则。具体支持以项目 UE 版本为准。[Epic：智能指针库](https://dev.epicgames.com/documentation/en-us/unreal-engine/smart-pointers-in-unreal-engine)、[Epic：UObject 指针](https://dev.epicgames.com/documentation/en-us/unreal-engine/object-pointers-in-unreal-engine)

### 复习时只展开这六句话

| 记忆入口 | 顺着主例展开什么 | 对应原题 |
| --- | --- | --- |
| **创建先交给 RAII，移动交责任。** | `prepared/pixels` → 构造失败 → 数组与删除器 → Rule of Zero/Five → 独占升级共享 | 1、2 |

### 其余考点挂在哪个位置？

这些是主线的展开位置，不需要再记新的业务例子。原题已有的 `【进阶，首轮可略】` 标记继续适用。

| 想不起的分支 | 挂回主例的位置 |
| --- | --- |
| PImpl、不完整类型、返回与容器移动 | 把 `pixels` 隐藏成前置声明的实现类；删除处看完整定义。工厂返回独占句柄通常直接 `return p;`，移动的是句柄，类本身能否移动另查特殊成员函数 |
| 私有构造、类专属分配、数组和版本 | 改“创建贴图”这一步。标准库内部创建不继承工厂成员函数的私有访问权；`make_shared` 的分配路径不等于调用类专属普通 `operator new`。`make_unique` 从 C++14 提供，`shared_ptr<T[]>` 的数组语义从 C++17 支持，数组版 `make_shared` 从 C++20 提供 |
| C API、句柄和输出参数 | 改“获取与归还像素资源”的协议；核对 `T**`、失败时资源归属和替换旧资源。`out_ptr/inout_ptr`、复杂分配器/对齐组合及 `for_overwrite` 留作进阶 |
| 手写原理 | 独占：禁复制、移动交接、赋值处理旧资源、析构按协议清理；共享：复制加入旧控制块，强零销毁资源，弱引用管理结束再回收控制块；弱提升不能把已销毁对象从零计数复活。完整线程安全实现留作进阶 |
| 大小与罕见状态 | 对照图里的“句柄 / 控制块 / 对象 / 像素”。`unique_ptr` 大小受删除器影响；`shared_ptr` 常见两个指针但不是固定标准布局。空别名状态、`get_deleter`、所有权排序等回原题按进阶标记查看 |
| 旧 `auto_ptr` | 挂在“独占交接”上：其复制转移所有权容易误用，C++11 弃用、C++17 移除，新代码使用 `unique_ptr` |
| 对象不析构、内存上涨、UAF 或卡顿 | 依次查“还有谁强持有 → 是否成环 → 对象与存储是否分开释放 → 借用是否过期 → 最后在哪个线程释放”。用日志、引用路径、ASan、内存快照和耗时验证；进程内存不立即下降，不能直接等同于泄漏 |
