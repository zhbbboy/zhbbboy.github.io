## `vector`

### 第 1 题：基础确认——`vector` 的存储和容量

**范围：连续存储、基本访问、数量与容量。**

```cpp
std::vector<int> values;
values.reserve(8);
values.push_back(10);
values.resize(4);
```

1. 用几句话说明 `vector` 的存储特点、随机访问和尾部插入的复杂度。容器对象本身和元素一定在同一处吗？
2. 上述操作后元素数量是多少？`size()` 和 `capacity()` 分别表示什么？`reserve` 和 `resize` 有什么区别？
3. `operator[]` 和 `at()` 访问越界时有什么区别？仅预留容量后，能否直接用下标访问还未创建的元素？

> 基础回答清楚即可。初始化方式、`data()`、`clear()` 和容量回收等细节，遇到疑问时再补。

#### 正确回答
vector 是一种采用连续内存存储的动态数组，支持 O(1) 的随机访问，尾部插入的摊还时间复杂度为 O(1)，发生扩容时单次最坏复杂度为 O(n)。
vector 容器对象与其管理的元素存储空间是分开管理的。
size 表示当前实际存在的元素数量，capacity 表示当前存储空间能够容纳的元素数量。reserve 用于预留容量，不改变 size；resize 用于调整元素数量，可能构造或销毁元素。
operator[] 在 C++17 中不保证边界检查，越界访问属于未定义行为，而 at() 会进行边界检查，越界时抛出 std::out_of_range 异常。
#### 我存在的问题
| 知识点                      | 判断   | 点评                          |
| ------------------------ | ---- | --------------------------- |
| 动态数组与连续存储                | 正确   | 底层采用连续内存存储                  |
| 随机访问复杂度                  | 正确   | O(1)                        |
| 尾部插入复杂度                  | 部分正确 | 应为摊还 O(1)，单次最坏 O(n)         |
| `size()` 与 `capacity()`  | 正确   | 能区分元素数量与容量                  |
| 代码执行结果                   | 基本正确 | `capacity()` 至少为 8，而不是一定为 8 |
| `reserve()` 与 `resize()` | 正确   | 能区分容量与元素数量                  |
| `operator[]` 与 `at()`    | 部分错误 | 越界访问不一定直接报错                 |
#### 示例
##### **一、为什么尾部插入是摊还 O(1)？**
需要分为两种情况：
- 容量充足：直接在尾部构造元素，O(1)。
- 容量不足：需要重新分配内存并搬迁已有元素，O(n)。
因此，`vector` 尾部插入的**摊还时间复杂度为 O(1)，单次最坏时间复杂度为 O(n)**。

具体为什么是摊还 O(1)，我们在第 2 题扩容机制中详细学习。
##### **二、reserve 和 resize 的区别**
你的理解基本正确，通过下面的图再巩固一下。
![](../../_Pasted_Image/Pasted%20image%2020261126142356.png)

|对比|`reserve(n)`|`resize(n)`|
|---|---|---|
|主要作用|预留容量|调整元素数量|
|是否改变 size|否|是（当数量不同时）|
|是否创建新元素|否|扩大 size 时会创建|
|是否销毁已有元素|否|缩小 size 时会销毁末尾元素|
|是否可能重新分配内存|是|是|
|是否能够缩小容量|否|否|
**容量是已经准备好的存储空间能够容纳的元素数量，size 才是当前实际存在的元素数量。**
##### **三、operator[] 与 at() 的区别**
这是本题最需要纠正的地方。
```cpp
std::vector<int> v;

v.reserve(10);

v[0] = 100;     // A
v.at(0) = 100;  // B
```

|访问方式|是否进行边界检查|越界后的行为|
|---|---|---|
|`operator[]`|C++17 不要求进行检查|未定义行为（UB）|
|`at()`|是|抛出 `std::out_of_range` 异常|
你认为 `operator[]` 越界会直接报错，这是不准确的。
**未定义行为不等于程序一定报错。** 它可能表现为程序崩溃、数据损坏、看起来正常运行等情况。

而 `at()` 的行为是明确的，可以通过异常处理机制捕获：
```cpp
try
{
    v.at(0) = 100;
}
catch (const std::out_of_range& e)
{
    std::cout << e.what();
}
```
虽然已经执行了 `reserve(10)`，但是此时 `size()` 仍然为 0，没有可供访问的元素。


#### 面试追问

### 第 2 题：扩容——什么时候重分配，元素怎样搬迁？

**范围：重分配、迁移、摊还复杂度和异常安全。**

```cpp
std::vector<std::string> names{"alpha", "beta"};
const auto oldCapacity = names.capacity();
names.reserve(oldCapacity + 1); // 假设请求合法且分配成功
```

1. 这次 `reserve` 是否需要重分配？用自己的话描述新存储、旧元素迁移和旧存储处理的过程。
2. 如果末尾追加时容量充足，和容量不足时相比，可能发生什么？为什么说末尾追加通常具有摊还常数复杂度，但某一次仍可能很慢？
3. 元素迁移一定使用移动构造吗？结合之前学过的 `noexcept`、复制和异常安全说明；元素不可复制且移动可能抛异常时，还应注意什么？
4. 批量读取文件记录时，如果已知或只能估计记录总数，分别怎样决定是否预留容量？为什么不应假定固定扩容倍率？

#### 正确回答
vector 采用连续内存存储。当插入元素超过当前容量，或者 reserve 请求的容量大于当前容量时，会触发重分配。
扩容时会申请更大的连续内存，在新空间中通过移动或拷贝构造迁移已有元素，成功后销毁旧元素、释放旧空间并更新内部状态。
vector 通常采用倍数增长策略，因此虽然单次扩容复杂度为 O(n)，但连续插入 n 个元素的总复杂度为 O(n)，尾部插入的摊还复杂度为 O(1)。
为了保证异常安全，当移动构造可能抛出异常且元素支持拷贝时，vector 通常会选择拷贝构造；当移动构造为 noexcept 时，则通常优先使用移动构造。
实际开发中可以使用 reserve 提前预留容量，减少重分配次数，但不应该在每次插入前都只预留一个额外元素的容量。
#### 我存在的问题
| 知识点              | 判断   | 存在的问题                     |
| ---------------- | ---- | ------------------------- |
| `reserve` 触发重分配  | 错误   | 本题一定发生重分配                 |
| 扩容底层过程           | 基本正确 | 需要补充元素构造与析构               |
| 缩小容量             | 错误   | `reserve` 不会缩小容量          |
| 容量充足时插入          | 正确   | 直接在尾部构造元素                 |
| 摊还时间复杂度          | 未掌握  | 不理解为什么是摊还 O(1)            |
| `noexcept` 与元素迁移 | 未掌握  | 需要理解异常安全机制                |
| 扩容倍率             | 正确   | C++ 标准没有规定具体倍率            |
| 提前预留容量           | 基本正确 | 应使用 `reserve`，而不是提前构造大量元素 |
#### 示例
##### **一、reserve 什么时候触发重分配？**
原题：
```cpp
std::vector<std::string> names{"alpha", "beta"};

const auto oldCapacity = names.capacity();

names.reserve(oldCapacity + 1);
```
假设请求合法且操作成功，这里**一定会发生内存重分配**，因为请求的容量大于当前容量。
`reserve(n)` 只有两种情况：

|条件|行为|
|---|---|
|n > capacity()|重新分配存储空间|
|n ≤ capacity()|不进行重分配，容量不变|
例如：
```cpp
std::vector<int> v{1, 2, 3};

v.reserve(100);
v.reserve(5);
v.reserve(1);
```
最后：
```cpp
size()     // 3
capacity() // 至少为 100
```
`reserve` **不会删除元素，也不会缩小容量。** 你把它与 `resize` 的行为混淆了。
##### **二、vector 扩容的完整底层过程**
假设当前 `vector` 的容量为 4，并且已经装满，现在需要插入第五个元素。
![](../../_Pasted_Image/Pasted%20image%2020261126144741.png)
常见的 `vector` 实现内部维护三个指针：
```cpp
T* start;           // 已分配空间的起始位置
T* finish;          // 已构造元素的末尾位置
T* end_of_storage;  // 已分配空间的末尾位置
```
通过它们计算：
```cpp
size     = finish - start;
capacity = end_of_storage - start;
```
扩容成功后，容器会更新这些指针。
注意，这三个指针属于常见实现方式，并不是 C++ 标准规定的唯一内部结构。
##### **三、什么是摊还时间复杂度？**
这是你目前没有掌握的重点。
**摊还时间复杂度（Amortized Time Complexity）** 是指将一系列操作的总开销分摊到每一次操作上，分析长期执行这些操作的平均成本上界。

假设 `vector` 每次扩容为原来的 2 倍，从空容器开始不断执行 `push_back()`。
![](../../_Pasted_Image/Pasted%20image%2020261126144819.png)
![](../../_Pasted_Image/Pasted%20image%2020261126144827.png)
![](../../_Pasted_Image/Pasted%20image%2020261126144839.png)
以连续插入 8 个元素为例：

|插入次数|是否扩容|搬迁旧元素数量|
|---|---|---|
|1|是|0|
|2|是|1|
|3|是|2|
|4|否|0|
|5|是|4|
|6|否|0|
|7|否|0|
|8|否|0|
|合计||7|
可以发现，虽然某一次插入需要移动大量元素，但是大部分插入都不需要扩容。
对于这种倍数扩容策略，连续插入 n 个元素时，总搬迁次数是 O(n)，新元素构造次数也是 O(n)。

因此：![](../../_Pasted_Image/Pasted%20image%2020261126144858.png)
**这就是为什么单次插入最坏为 O(n)，但连续插入的摊还复杂度仍然为 O(1)。**
摊还复杂度并不是基于随机概率计算的平均复杂度，而是分析一系列操作的整体开销。
##### **四、为什么 noexcept 会影响 vector 扩容？**

这个知识点你在移动语义专题中学过，现在重新串联一下。
假设 `vector` 中已经有四个对象：
```
[A, B, C, D]
```

现在扩容，需要把这四个对象搬迁到新空间。
**情况一：使用移动构造，但中途抛出异常**
![](../../_Pasted_Image/Pasted%20image%2020261126144931.png)
此时如果扩容失败，`vector` 很难保证原容器的数据完全不变。
**情况二：使用拷贝构造，但中途抛出异常**
![](../../_Pasted_Image/Pasted%20image%2020261126145002.png)
这种操作失败后原有状态保持不变的保证，叫作**强异常安全保证（Strong Exception Guarantee）**。
###### **vector 如何选择？**
常见实现会采用类似 `std::move_if_noexcept` 的策略。

|元素类型的情况|通常采用的迁移方式|
|---|---|
|移动构造为 `noexcept`|移动构造|
|移动构造可能抛异常，支持拷贝|拷贝构造|
|移动构造可能抛异常，不支持拷贝|移动构造|
|不支持移动，但支持拷贝|拷贝构造|
第三种情况你回答正确：由于不能拷贝，只能尝试移动。如果移动构造真的抛出异常，相关扩容操作可能无法维持强异常安全保证，标准允许其效果未指定。

因此我们在编写资源管理类时，如果能够确保移动构造不抛异常，应该考虑标记：
```cpp
Player(Player&& other) noexcept;
```
这样既有利于移动性能，也有利于容器提供异常安全保证。
##### **五、为什么不能每次插入前都 reserve？**
你已经知道这种写法不好，但还没有理解根本原因。
```cpp
for (...)
{
    v.reserve(v.size() + 1);
    v.push_back(value);
}
```

如果每次 `reserve` 都只增加一个单位的容量，那么原本的倍数增长就会变成线性增长。
所以更合理的方式是：
```cpp
std::vector<Player> players;

players.reserve(expectedCount);

for (...)
{
    players.emplace_back(...);
}
```
如果知道准确数量，就提前预留足够容量；如果只能估计数量，可以根据内存成本和实际负载合理预留，但没有必要固定多预留 1.5 倍。
#### 面试追问

### 第 3 题：修改容器——迭代器什么时候失效，怎样删除元素？

**范围：重分配、插入、删除、遍历安全。**

```cpp
std::vector<int> values{1, 2, 3, 4};
auto first = values.begin();
auto middle = values.begin() + 2;
auto oldEnd = values.end();
```

1. 分别分析：发生重分配、容量充足时在末尾追加、容量充足时在中间插入，以及删除中间元素。已有迭代器、引用和旧 `end()` 哪些会失效？
2. 若遍历时删除偶数，为什么不能在 `erase(it)` 后继续使用原来的 `it`？请手写一个合法循环。
3. 删除多个满足条件的元素时，C++17 中怎样使用 `remove_if` 和 `erase`？如果业务不要求保持顺序，还有什么删除策略，代价是什么？
4. `clear()`、缩小 `resize()` 或尝试 `shrink_to_fit()` 后，怎样分别判断元素生命周期、容量和迭代器有效性？

#### 正确回答
vector 的迭代器失效主要与内存重分配、元素位置变化及对象生命周期有关。
当发生重分配时，所有迭代器、指针和引用都会失效。如果没有发生重分配，插入操作会使插入位置及之后的迭代器失效，删除操作会使删除位置及之后的迭代器失效，包括旧的 end()。
遍历删除时，需要使用 erase 返回的新迭代器，不能继续使用已经失效的旧迭代器。
批量删除可以使用 remove_if 与 erase，将总复杂度控制在 O(n)。如果不要求保持元素顺序，也可以采用末尾元素覆盖和 pop_back 的方式实现常数次元素操作的删除。
clear 不会缩减容量，而 shrink_to_fit 可以请求缩减容量，但标准不保证一定成功。
#### 我存在的问题
|知识点|判断|存在的问题|
|---|---|---|
|重分配导致迭代器失效|正确|理解了内存地址变化|
|尾部插入|基本正确|旧 `end()` 已经失效|
|中间插入|部分正确|插入位置及之后的迭代器全部失效|
|中间删除|部分错误|删除位置及之后的迭代器全部失效|
|遍历删除|部分正确|必须接收 `erase()` 的返回值|
|`remove_if`|未掌握|需要学习批量删除机制|
|交换末尾元素删除|基本正确|可以避免大量元素移动|
|`clear()`|正确|元素被销毁，容量不变|
|`resize()`|正确|缩小时被删除元素及旧 `end()` 失效|
|`shrink_to_fit()`|未掌握|不清楚容量回收机制|
#### 示例
##### **一、vector 迭代器失效规则**
###### **1. 发生内存重分配**
```cpp
values.reserve(values.capacity() + 1);
```
这一点你回答正确。
由于元素被迁移到新的存储空间，原来所有指向元素的迭代器、指针、引用，以及旧的 `end()` 都会失效。
###### **2. 尾部插入（不发生扩容）**
```cpp
std::vector<int> values{1, 2, 3, 4};
values.reserve(8);

auto oldEnd = values.end();

values.push_back(5);
```
![](../../_Pasted_Image/Pasted%20image%2020261126153159.png)
你认为旧 `end()` 变成指向新元素的迭代器，这个理解不严谨。
虽然在某些实现中，它内部保存的地址恰好是新元素所在的地址，但按照 C++ 标准，旧 `end()` 已经失效，不能继续依赖它。
另外，`end()` 本来就不指向任何有效元素，而是表示尾后位置。
###### **3. 中间插入和删除（不发生扩容）**
![](../../_Pasted_Image/Pasted%20image%2020261126153222.png)
![](../../_Pasted_Image/Pasted%20image%2020261126153232.png)
即使没有发生扩容，中间插入或删除也会影响后续元素的位置与对应的对象状态。
因此，完整规则如下：

|操作|first|middle|oldEnd|
|---|---|---|---|
|A：发生重分配|失效|失效|失效|
|B：尾部插入，无扩容|有效|有效|失效|
|C：中间插入，无扩容|有效|失效|失效|
|D：中间删除|有效|失效|失效|
**记忆规律：**
- 重分配：全部失效。
- 插入且不重分配：插入位置及之后失效。
- 删除：删除位置及之后失效。

对于受影响位置的旧指针和引用，也不能继续依赖它们访问原来的元素。
##### **二、为什么遍历时不能直接 erase(it)？**
原题：
```cpp
for (auto it = v.begin(); it != v.end(); ++it)
{
    if (*it % 2 == 0)
    {
        v.erase(it);
    }
}
```
你已经发现了跳过元素的问题，但实际上还有一个更严重的问题：`erase(it)` **执行后，原来的** `it` **已经失效，继续执行** `++it` **属于未定义行为。**
因此，仅仅把 `++it` 放进循环内部还不够，还需要更新迭代器。
###### **erase 的返回值**
```cpp
it = v.erase(it);
```
`erase()` 返回的是删除位置之后的元素对应的新有效迭代器。如果没有后续元素，则返回新的 `end()`。
正确写法：
```cpp
std::vector<int> v{1, 2, 4, 5, 6, 7};

for (auto it = v.begin(); it != v.end();)
{
    if (*it % 2 == 0)
    {
        it = v.erase(it);
    }
    else
    {
        ++it;
    }
}
```
这是非常常见的 STL 面试手撕代码，需要熟练掌握。
##### **三、remove_if + erase 批量删除**

逐个调用 `erase()` 存在一个性能问题：每删除一个元素，其后面的元素都可能需要向前移动。
如果需要删除大量元素，最坏情况下总复杂度可能达到 O(n²)。

C++17 中可以使用 **Erase-Remove Idiom（删除惯用法）**。
```cpp
std::vector<int> v{1, 2, 3, 4, 5, 6};

auto newEnd = std::remove_if(
    v.begin(),
    v.end(),
    [](int x) {
        return x % 2 == 0;
    }
);

v.erase(newEnd, v.end());
```
###### **第一步：remove_if**
`remove_if` 并不会真正删除容器元素，而是通过移动赋值等操作，把需要保留的元素集中到前面，并返回新的逻辑尾部。
![](../../_Pasted_Image/Pasted%20image%2020261126153322.png)
###### **第二步：erase**
将 `newEnd` 到原来 `end()` 之间的元素真正删除，销毁多余元素并修改 `size()`。

|对比|逐个 erase|remove_if + erase|
|---|---|---|
|删除大量元素|可能反复搬迁|集中整理，一次删除尾部|
|最坏总复杂度|O(n²)|O(n)|
|是否保持剩余元素顺序|是|是|
**注意：**`remove_if` **是算法库中的算法，并不是** `vector` **的成员函数，它本身不会改变容器的** `size()`**。**
##### **四、不要求顺序时如何实现 O(1) 删除？**
你已经想到这个优化方向了，在游戏客户端中非常实用。
假设需要删除下标为 1 的元素：
![](../../_Pasted_Image/Pasted%20image%2020261126153341.png)
代码：
```cpp
if (index < v.size())
{
    if (index != v.size() - 1)
    {
        v[index] = std::move(v.back());
    }

    v.pop_back();
}
```

这种方式通常称为 **Swap and Pop（交换末尾删除）**，这里采用的是直接移动末尾元素的写法。

优点是只需要一次移动赋值和一次尾部删除，按元素操作次数计算为 O(1)。

缺点是会破坏元素原来的排列顺序。如果还有 ID 到数组下标的映射，也需要同步更新。

适合游戏中的子弹管理、粒子管理、活动实体列表等不要求保持顺序的场景。
##### **五、clear、resize 和 shrink_to_fit**
前两个你已经掌握，现在补充第三个。
```cpp
std::vector<int> v{1, 2, 3, 4, 5};
v.reserve(100);
```
此时 `size = 5`，`capacity` 至少为 100。
以下操作分别独立执行：

|属性|`clear()`|`resize(2)`|`shrink_to_fit()`|
|---|---|---|---|
|size|0|2|5|
|capacity|不变|不变|可能缩小|
|元素销毁|全部|3、4、5|保留五个元素的值|
|迭代器失效|全部|删除位置及之后|重分配时全部失效|
###### **shrink_to_fit 是什么？**
```
v.shrink_to_fit();
```
它用于请求容器减少多余的容量，使 `capacity()` 尽可能接近 `size()`。
![](../../_Pasted_Image/Pasted%20image%2020261126153401.png)
需要注意：
- `shrink_to_fit()` 是一个**非强制性请求**，不保证一定缩减容量。
- 如果发生重分配，所有旧迭代器、引用和指针都失效。
- 如果没有发生重分配，则不会因此失效。
- `clear()` 只销毁元素，不会缩减容量。
