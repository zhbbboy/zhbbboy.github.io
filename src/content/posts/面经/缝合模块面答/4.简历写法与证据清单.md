# 缝合模块简历写法与证据清单

目标是把一个专业领域项目翻译成面试官能理解的 C++ 工程经历。先确定个人贡献，再选 3～4 条最能讲清楚的工作，最后补数据和证据。下方均为待个人核对的草稿。

## 一、项目基本信息

**项目名称：**GME 几何建模内核——缝合模块开发与性能优化  
**项目时间：**【填写自己实际参与的起止时间】  
**项目性质：**【实习／团队项目／开源贡献，按事实填写】  
**技术栈：**C++、CMake、GoogleTest、空间索引、拓扑数据结构【只保留自己使用或掌握的】

**项目简介：**参与几何建模内核的缝合模块开发，在给定容差下处理曲面片体边界匹配及拓扑连接，为后续建模操作提供支持。

如果个人仅负责性能优化，把标题改为“缝合模块性能优化”也可以。不要写成自己独立开发了整个 GME 或整个缝合模块，除非事实如此。

## 二、游戏客户端／通用 C++ 版本

> 以下条目从仓库实现提炼；逐条确认自己实际参与的设计、实现和验证后再使用。

- 参与 C++ 几何建模内核缝合模块开发，处理片体边界的候选匹配与拓扑连接，分析容差、方向及对象生命周期对结果的影响。
- 针对边、顶点候选配对，参与引入基于容差的空间网格筛选与包围盒预筛；根据输入规模选择直接遍历或索引，减少无效比较。
- 优化拓扑数据收集和重复计算，通过单次调用内的曲线比较缓存、链表尾节点缓存等方式减少重复查询与扫描，并处理缓存失效。
- 参与 GoogleTest 功能及边界验证，覆盖【填写实际做过的场景】，在【填写具体环境】下对比优化前后行为与性能。

空间有限时优先保留第二、三条及一条可验证的测试或结果。技术栈不要堆砌没有亲手使用过的工具。

## 三、CAD／图形几何岗位版本

- 参与 B-rep 缝合接口开发，围绕 Body、Face、Edge、Coedge 和 Vertex 的关系处理边界匹配与拓扑连接。
- 针对容差范围内的边点候选，结合空间网格及包围盒进行保守筛选，保留几何、方向和拓扑约束检查。
- 参与【按实际选择：容差处理／共边方向分析／属性复制／持久化】功能与测试，关注特殊拓扑、归属关系和生命周期。
- 通过【实际测试名称或验证方式】验证结果、回退路径和边界条件；在【测试场景】中记录性能表现【真实数据】。

这版适用于确实理解 B-rep 与所写功能的情况；不熟悉的内容先学习，暂不放简历。

## 四、量化结果怎么写

格式：**具体场景 + 优化动作 + 对比口径 + 结果 + 正确性验证**。

> 在【N 个片体、M 条边】的【测试场景】下，通过【具体方案】，将【优化前统计值】降至【优化后统计值】，耗时下降【百分比】；使用【具体测试】验证输出行为。

公式：耗时下降百分比 = `(优化前耗时 - 优化后耗时) / 优化前耗时 × 100%`；加速倍数 = `优化前耗时 / 优化后耗时`。例如 100 ms 到 50 ms，是耗时下降 50%、速度为原来的 2 倍。实际数据没有核实前不能套用这个例子。

基准建议记录：机器与系统、编译器和构建类型、代码提交、输入及规模、预热和轮次、统计值（例如中位数）、是否包含数据构造、负载与测量时间。分别记录优化前后和 ACIS/GME 对比；二者回答的是不同问题。

已有某次验证记录为 Debug 与 Release 各 561/561 通过，这是特定版本和筛选范围内的测试结果；它不是“新增 561 项测试”，也不能直接证明某次性能优化提升了多少。

## 六、写简历前的检查

- 项目简介能否让不懂 CAD 的面试官在 20 秒内理解？
- 每条是否包含具体动作，而不是“负责性能优化、具有良好编码能力”？
- 每个术语是否能用例子解释并回答两层追问？
- 是否准确区分参与、主导、独立完成与工具协助？
- 数字是否有测试场景、版本和原始记录？
- 是否把测试总数、PR 数或提交数误写成个人新增量？
- 是否避免披露不适合公开的代码、数据和客户信息？
