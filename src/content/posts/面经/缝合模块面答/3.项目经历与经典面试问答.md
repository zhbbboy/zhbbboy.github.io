# 项目经历与经典面试问答

面向游戏客户端和通用 C++ 岗位：先说明业务背景，再把重点放在问题、分析、方案、取舍和验证。下面的回答是**基于代码整理的参考话术**，不是已经替你确认的个人经历；工具、贡献、数据和合作方式都要按事实调整。

## 一、30 秒和 2 分钟介绍

### 30 秒版本

> 我参与的是 GME 几何建模内核的缝合模块。它负责在一定容差内识别曲面片体可能连接的边界，并维护模型里的连接关系。我主要关注缝合过程的性能和正确性，例如减少边、顶点之间不必要的候选比较，优化重复拓扑遍历，并针对不同输入规模选择处理路径。这个过程中接触较多的是 C++ 数据结构、空间筛选、对象生命周期和测试验证。

把“主要关注”改成与你实际负责范围一致的内容。没有参与的部分可以说“我了解模块采用了……”，不要说成自己的成果。

### 2 分钟版本

> 项目的背景是几何建模。模型可能由多块独立的曲面片体组成，缝合需要找出在容差内可连接的边或顶点，并更新边、面等拓扑对象之间的关系。它不只是坐标比较，因为两条边可能端点接近但曲线不同，更新时也需要维护方向和对象归属。
>
> 我关注的一个问题是候选匹配开销。对于较大的输入，直接检查很多边和顶点组合会产生大量无效比较。模块中使用空间网格筛选候选，并对距离较远的体使用包围盒预筛；小输入则保留直接遍历，避免建索引的固定开销。另外，代码还通过单次调用缓存和合并拓扑遍历减少重复工作。
>
> 这类优化的关键是筛选不能漏掉真实候选，快路径不适用时要回到通用处理。我会用正常接边、跨网格边界、容差边界、退化边和特殊拓扑等测试去检查结果，再通过相同条件下的多轮测试比较性能。具体我负责的部分是【按实际填写】，测量结果是【有证据后填写】。

这里“我会用”是验证思路；只有实际执行过，才能改成“我做了”。

## 二、最常见的项目问题

### 1. 你在项目里负责什么？

**回答结构：**团队负责什么 → 我负责的子问题 → 做过的具体动作 → 最终结果。

> 我参与缝合模块的【具体接口／问题】，主要负责【定位、设计、实现、测试、评审中实际承担的部分】。其中一个具体问题是【场景】，我做了【动作】，最后通过【测试或评审证据】验证了【可确认的结果】。

准备时把“参与”和“独立负责”分开。提交作者、AI 协作记录和实际主导程度不是一回事，面试时要如实说明。

### 2. 项目中最有挑战的问题是什么？

可以选择“加速候选筛选时保持正确性”：

> 缝合会根据容差寻找可能重合的边界，筛选太激进就可能漏掉正确结果。比如两个接近的点可能刚好落在网格边界两侧，只查本格会漏掉。我会把周围格子也作为候选，再保留后续的精确检查；还需要考虑负坐标、退化数据、密集分布和处理顺序。对于不能证明适用的拓扑，保留通用路径。

如果面试官继续问，能画出网格边界的例子，比背术语更有说服力。

### 3. 为什么这样优化？有没有其他方案？

> 我们要减少的是无效候选，而不是跳过正确性检查。网格索引实现相对直接，适合按距离做局部查询；包围盒能在体级别提前排除明显不可能的组合。其他方案还可以考虑排序扫描、层次包围盒或空间树，但构建成本、动态更新、数据分布和实现复杂度不同，应结合实际数据测量。小输入下直接循环可能更便宜。

不要说项目实际比较过所有方案，除非有记录。

### 4. 怎么定位性能瓶颈？

> 先固定输入和构建配置，重复测量得到基线。然后看每个阶段的调用次数、候选数量和耗时，必要时使用 profiler 查看热点。确认主要成本后再调整，最后在相同环境下复测，并检查优化后输出是否一致。

如果实际没有做某一步，要说“如果重新排查，我会……”，不要把通用流程讲成已经发生的经历。

### 5. 你做的优化效果怎么样？

> 在【具体模型、规模和构建配置】下，优化前【A】、优化后【B】，测量方式是【预热、轮次、统计口径】，功能结果通过【具体验证】确认。小模型／密集数据下的情况是【实际结果】。

**目前待补：**已查看的提交记录证明有优化实现，但没有确认一组可归因的前后耗时。没有测量结果时可以回答“目前没有整理出可复核的量化结果”，不要编造百分比。

### 6. 遇到过什么 bug，怎么排查？

从真实经历中选一个，按以下顺序说：

1. **现象**：什么输入、什么结果异常，能否稳定复现。
2. **缩小范围**：将模型或测试缩小到仍能复现的最小案例；保留错误码、调用顺序和配置。
3. **定位原因**：用断点、日志、对照测试等确定发生错误的层次，区分几何判断和拓扑修改。
4. **修复与验证**：解释修改、为什么不会影响其他路径，以及新增或运行了哪些测试。
5. **反思**：哪项假设原来不成立，后续怎样避免。

可以准备“网格边界漏候选”作为**假设性的排查题**，但不要说成实际遇到的 bug，除非有对应记录。

### 7. 你怎么保证修改不会破坏原有功能？

> 对候选筛选，要求保守地包含所有可能匹配对象，真正合并仍由后续判断决定。对快路径，先验证前置条件，无法处理就回退。测试时不仅比较是否成功，还检查几何、连接关系、输出数量和对象生命周期，特别覆盖容差边界、退化情况和带变换的输入。

如果被问到“证明”，要区分某条筛选规则的推理、有限测试覆盖以及完整形式化证明，不能把测试通过称为证明所有情况正确。

### 8. 项目里用到哪些 C++ 知识？

| 知识 | 在项目中的关联 | 可以准备的追问 |
| --- | --- | --- |
| `vector` / 内联容器 | 保存候选和拓扑指针，小数据时减少分配 | 扩容、迭代器失效、内存局部性、容量与大小。 |
| `unordered_map` / `unordered_set` | 网格索引、去重、单次调用缓存 | 哈希冲突、平均与最坏复杂度、rehash、键的相等性。 |
| 指针与所有权 | 拓扑对象之间关联；接口区分借用和新建对象 | 悬空指针、释放责任、容器析构是否删除指针所指对象。 |
| 生命周期 | 缓存与一次缝合调用绑定 | 对象改变、删除或地址复用后缓存如何失效。 |
| 移动语义 | 转移临时收集容器 | `std::move` 只是转换，是否移动由类型决定。 |
| 调试与测试 | 定位候选、拓扑和资源问题 | 如何做最小复现，Debug 与 Release 的区别。 |

不要因为代码里使用裸指针就推断必须手动 `delete`；要按具体实体的所有权和工程 API 处理。容器保存指针通常不意味着容器拥有指向的对象。

### 9. 为什么游戏客户端要招做过 CAD 的人？

> 业务知识不同，但我在项目里练习了 C++ 工程中的性能分析、空间数据筛选、复杂对象关系维护和测试。比如用保守的空间筛选减少昂贵的细节计算，这种思路和游戏中的宽相位筛选有相通之处。我也知道游戏实时系统有帧时间、资源加载和引擎架构等不同约束，需要结合具体场景学习。

不要暗示自己做过引擎、碰撞系统或 UE，除非确实做过。

### 10. 如果让你重新做，会怎么改进？

> 先整理一组覆盖小输入、大输入、稀疏和密集分布的基准，同时记录候选数、耗时和分配数；再检查快路径与回退的边界是否明确，补充差异测试。对于更复杂的空间结构，先用数据验证是否有必要，而不是直接增加复杂度。

## 三、CAD 岗位可能继续追问

1. B-rep 中几何与拓扑分别是什么？Edge 和 Coedge 为什么要区分？
2. 两条边端点相同，为什么可能不是同一条边？闭合曲线如何处理？
3. 容差选择如何影响漏匹配和误匹配？具体接口怎样定义有效容差？
4. 面的边界方向、非流形连接和实体闭合之间有什么关系？
5. 带变换的模型如何比较？为什么包围盒需要在同一坐标系下？
6. 缝合和布尔操作、几何修复有什么区别？

不确定时先讲已知边界：例如“我了解这条普通路径；具体特殊曲线或其他选项需要看接口实现”，不要假装掌握整个几何内核。
