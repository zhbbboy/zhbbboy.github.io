GAMES104 第 2 节《引擎架构分层》（Engine Architecture & Subsystems）是全课程最重要的基石之一。王希老师在这一节详细拆解了游戏引擎从代码组织到模块依赖、从内存/线程管理到组件化（Component-Based）设计的核心逻辑。

以下为您提炼的第 2 节精炼笔记：
### 一、 核心解耦理念：Runtime 与 Editor 的分离

引擎软件工程中最核心的设计原则之一是：**运行时（Runtime）与编辑器（Editor）必须严格解耦**。
- **Runtime（运行时）**：
    - **目标**：极致的性能、极小的内存占用、绝对的稳定性。
    - **原则**：只包含玩家在最终发布（Shipping）包体中运行游戏所需的代码。**绝不能依赖 Editor 层的任何逻辑**。
- **Editor（编辑器）**：
    - **目标**：易用性、可扩展性、极高的开发效率。
    - **原则**：依赖并包裹 Runtime。Editor 通过调用 Runtime 提供的接口来进行场景预览、物理模拟和实时渲染，同时提供可视化 UI、Undo/Redo、Gizmo 绘制等创作功能。

### 二、 核心模块依赖关系与组织架构
游戏引擎五层架构（自上而下）

```
+-------------------------------------------------------+
| 1. 工具层 (Tooling Layer)                             |  ▲ 可定制性极高
+-------------------------------------------------------+  │ (Upper Levels)
| 2. 功能层 (Function Layer)                            |  │ 随业务/玩法
+-------------------------------------------------------+  │ 频繁变动
| 3. 资源层 (Resource Layer)                            |  │
+-------------------------------------------------------+  │
| 4. 核心层 (Core Layer)                                |  │ 稳定度极高
+-------------------------------------------------------+  │ (Lower Levels)
| 5. 平台层 (Platform Layer)                            |  ▼ 几年难改一次
+-------------------------------------------------------+
```

#### 各层精炼职责与对应组件

##### 1. 工具层 (Tooling Layer) —— _可定制性最高_

- **职责**：为策划、美术、程序员提供可视化的编辑环境（即“引擎编辑器”）。
    
- **核心组件**：关卡编辑器 (Level Editor)、材质编辑器 (Material Shader Graph)、动画状态机编辑器、Profiler 性能分析工具、Gizmo 辅助调试。

##### 2. 功能层 (Function Layer) —— _运行时的肉体 (Tick 驱动的核心)_

- **职责**：驱动游戏每一帧运行（Tick）的核心逻辑与计算系统。
    
- **核心组件**：
    
    - **渲染系统**：Mesh, Material, Light, Post-Processing
        
    - **物理系统**：Rigid Body, Collision, Raycast
        
    - **动画系统**：Skeleton, Pose, Blend Tree, IK
        
    - **Gameplay / Entity 系统**：Component-Based 逻辑框架
##### 3. 资源层 (Resource Layer) —— _数据驱动的中枢_
- **职责**：实现“数据与计算分离”，将磁盘中的资产转化为内存中高效的数据结构。
    
- **核心组件**：资产导入与离线编译 (Asset Pipeline)、虚拟文件系统 (VFS)、打包 (Pak)、GUID 管理、异步加载与 Streaming (GC / 延迟加载)。
##### 4. 核心层 (Core Layer) —— _极致性能的基础_

- **职责**：提供高复用、高性能的通用底层设施，绝大部分逻辑为纯数学与内存操作。
    
- **核心组件**：数学库 (Vector/Matrix/Quaternion/SIMD)、自定义内存分配器 (Memory Pool/Frame Allocator)、多线程任务调度 (Job System / Task Graph)。
##### 5. 平台层 (Platform Layer) —— _绝对稳定的基石_

- **职责**：屏蔽各种硬件与操作系统的物理差异。
    
- **核心组件**：
    - **图形 API 抽象 (RHI)**：DirectX, Vulkan, Metal, OpenGL ES
        
    - **系统接口**：OS File System, Socket 网络、Input 设备抽象 (Keyboard/Mouse/Gamepad)。
### 三、 世界表达：组件化架构 (Component-Based Architecture)

为了解决传统面向对象（OOP）继承树过于庞大、难以维护的问题（如“深层继承噩梦”），现代引擎普遍采用“组合优于继承”的组件化模式。
#### 1. 传统继承 vs 组件组合
- **继承模式 (Inheritance)**：`Actor` $\rightarrow$ `Pawn` $\rightarrow$ `Character` $\rightarrow$ `Monster`。随着功能增加，类结构极度臃肿。
- **组件化模式 (Composition)**：`GameObject` 本质上只是一个**空壳 (ID / Container)**，具体的行为和数据全部挂载在独立的 `Component` 上：
    - `TransformComponent`（空间位置/旋转/缩放）
    - `MeshRendererComponent`（视觉表现）
    - `RigidBodyComponent`（物理属性）
    - `AudioComponent`（发声能力）
#### 2. 引擎内部的 Tick 机制与驱动
- **GameObject 的生命周期**：`Awake()` $\rightarrow$ `Start()` $\rightarrow$ `Update()` / `FixedUpdate()` $\rightarrow$ `OnDestroy()`。
- **批量驱动模式 (Batch Processing)**：  
    - **不推荐**：每个 GameObject 独立遍历调用自己的 Component Update（缓存不友好，虚函数开销大）。
    - **引擎推荐**：各个子系统（如 `RenderSystem`、`PhysicsSystem`）直接收集对应的 Component 进行**集中式/数据连续的批量更新**。

### 四、 关键基础设施系统

#### 1. 内存管理 (Memory Management)

- **为什么不用默认内存分配？** 频繁在堆上分配/释放小内存会导致 CPU 沉重开销及巨大的**内存碎片**。
- **解决方案**：  
    - **Frame Allocator**：每帧清空的临时分配器（适合每帧生成的渲染指令或临时计算数据）。
    - **Pool Allocator**：固定大小对象的分配器（适合粒度相同的 GameObject 或 Component）。
    - **Block / Arena Allocator**：预先申请大块内存自行分配。

#### 2. 线程与并行化 (Threading & Task System)

- **单线程主循环的局限**：无法发挥现代多核 CPU 性能。
- **主流线程模型**：  
    - **主线程 (Game Thread)**：负责 Gameplay 逻辑、输入处理、动画更新、物理同步。
    - **渲染线程 (Render Thread)**：接收主线程生成的渲染指令（Render Commands），提交给 GPU。
    - **Job / Worker Threads**：利用 Task Graph（任务图）并行处理耗时任务（如遮挡剔除、射线检测、资产解压缩）。

### 五、 本节总结与核心思想

1. **强模块化与单向依赖**：上层可以调用下层，下层绝不能知道上层的存在（如渲染系统不知道什么是“玩家”或“怪”）。
2. **组合优于继承**：以组件化方式构建游戏世界中的实体。
3. **性能导向（Data-Oriented Mindset）**：内存连续放置、减少虚函数调用、多线程任务并行，一切为每帧 16.6ms (60FPS) 的硬性指标服务。

## 这三条 Takeaways 是 GAMES104 第 2 节最灵魂的底层设计思想：
### GAMES104 第2节：引擎架构分层（三大核心 Takeaways 深度提炼）

**核心思想**：游戏引擎本质上是一个“通过分层降低复杂度，通过时间驱动虚拟世界”的实时系统。
### 1. Engine is designed with a layered architecture（引擎采用分层架构设计）

可以大概分为五层有上至下：
1. 工具层
2. 功能层
3. 资源层
4. 核心层
5. 平台层

- **解耦与单向依赖**：上层系统（如 Gameplay）可以调用下层（如 Resource/Core），下层严禁反向依赖上层。这种严格的层次结构降低了庞大代码库的复杂度。
- Runtime 与 Editor 隔离：
    - **Runtime（底层/核心）**：仅包含游戏运行必须的模块，追求极致性能与小包体。
    - **Editor（上层/工具）**：包裹 Runtime 提供可视化操作，绝不把编辑器代码打包进最终 Release 游戏。
- **数据与计算分离**：数据层（Resource）只管资产管理与加载，计算层（Function/Subsystems）只管逐帧逻辑与渲染。

### 2. Lower levels are more stable and upper levels are more customizable（底层更稳定，上层可定制性更高）

|**层级**|**稳定度 & 变更频率**|**可定制性 & 灵活性**|**代表模块**|**设计哲学**|
|---|---|---|---|---|
|**底层 (Lower Levels)**|**极高**（几年难得改动一次）|**极低**（标准化、抽象化）|数学库、内存分配器、RHI (DirectX/Vulkan)、Task System|**高性能与绝对可靠**。屏蔽硬件差异，作为整座大厦的基石。|
|**中层 (Middle Levels)**|**中等**（随技术演进升级）|**中等**（提供通用参数）|渲染管线、物理引擎、动画状态机、场景管理|**模块化与通用性**。提供强劲的通用功能，不掺杂具体游戏逻辑。|
|**上层 (Upper Levels)**|**极低**（随项目/玩法频繁改动）|**极高**（高度自由扩展）|Gameplay 逻辑、组件 (Components)、关卡脚本、UI|**开发效率与表现力**。通过组件化组合自由拼接玩法，支持策划快速迭代。|

### 3. Virtual world is composed by a set of clocks - ticks（虚拟世界由一组时钟/Tick 驱动）

- **本质：时钟驱动的世界**：游戏里的物理、动画、渲染和 AI，本质上都是在不同频率的 Tick（时钟脉冲）下不断更新数据。
-
- **非同步时钟系统**：引擎内部并非只有“一个”简单的 Game Loop，而是由**多套独立的 Tick** 协同运作：
    - **Physics Tick（物理时钟）**：通常为固定频率（如固定 60Hz / $16.6\text{ms}$），保证碰撞检测与动力学计算的数值稳定性。
    - **Render Tick（渲染时钟）**：受限于显示器刷新率（如 60Hz, 144Hz 或无限制），随硬件性能浮动。
    - **Gameplay/Animation Tick（逻辑/动画时钟）**：依据帧间隔时间 $\Delta t$ 变频更新。

- **Delta Time ($\Delta t$) 的核心地位**：利用 $\Delta t$ 解耦“计算逻辑”与“硬件帧率”，确保游戏在 30FPS 和 144FPS 下的角色移动速度与物理表现一致。
