这一节记录 2026-10-09 最新代码中的胜利判定、终局停止连射、胜利提示和胜利后重开。第2节的单发、连射、换弹，第3节的敌人和波次，第4节的死亡提示都继续保留；这次是在已有流程上补齐一局游戏的结束方式。

示例依据当前 UE 5.4 项目。标为“完整函数”的代码取自本次源码，省略注释、调整排版；标为“伪代码”的内容帮助理解逻辑，不是要额外复制进项目的实现。

## 1. 从需求推导：谁知道游戏什么时候胜利？

先分清各个对象分别知道什么：

| 对象 | 它掌握的信息 | 本次职责 |
| --- | --- | --- |
| EnemyCharacter | 自己的生命值 | 接受伤害，死亡时请求销毁 |
| EnemySpawner | 波次配置、当前波索引、本波敌人数组 | 判断一波是否结束，以及所有波是否完成 |
| 玩家 Character | 自己的死亡/胜利状态、当前武器、HUD引用 | 接受胜利通知，结束玩家操作中的相关状态 |
| HUD | 已绑定的界面控件 | 显示胜利提示 |

敌人死亡只能说明“一个敌人被击杀”。只有 Spawner 能结合全部波次判断“这一局清完了”。因此执行方向是：

```text
最后一个敌人死亡
    → Spawner 清理本波数组
    → 判断已没有下一波
    → PlayerCharacter->WinGame()
    → 玩家记录胜利、停止连射、禁用移动
    → HUDWidget->ShowVictory()
```

HUD收到显示通知时，游戏逻辑已经作出了胜利判断。`ShowVictory()` 本身只改变控件可见性。

## 2. 先把三种状态想清楚

玩家现在有两个普通 C++ 成员：

```cpp
bool bIsDead = false;
bool bHasWon = false;
```

它们不是 `UPROPERTY`，也没有保存到存档。它们描述当前这一个玩家实例的状态，重开地图后新实例重新使用初始值。

| 情况 | bIsDead | bHasWon | 本次新增逻辑的处理 |
| --- | --- | --- | --- |
| 正在游戏 | false | false | 允许开始射击、换弹、接受伤害；不允许重开 |
| 已死亡 | true | false | 禁止上述新射击/换弹/受伤请求；允许重开 |
| 已胜利 | false | true | 禁止上述新射击/换弹/受伤请求；允许重开 |

正常的调用链把死亡和胜利作为互斥的结束状态：`WinGame()` 会拒绝已经死亡的玩家；胜利后 `ReceiveEnemyDamage()` 会直接返回。当前源码还没有创建独立的状态枚举，表格只是帮助理解这两个布尔量组合出的行为。

## 3. Spawner 怎样发现最后一波结束

### 3.1 Tick 中完整的判断顺序

```cpp
void AMyEnemySpawner::Tick(float DeltaTime)
{
    Super::Tick(DeltaTime);

    if (!bWaveActive)
    {
        return;
    }

    CleanupDeadEnemies();

    if (CurrentWaveEnemies.Num() == 0)
    {
        bWaveActive = false;
        ++CurrentWaveIndex;

        if (CurrentWaveIndex >= Waves.Num())
        {
            UE_LOG(
                LogTemp,
                Warning,
                TEXT("All Waves Completed!")
            );

            if (!IsValid(PlayerCharacter))
            {
                PlayerCharacter = Cast<AMyArenaShooterCharacter>(
                    UGameplayStatics::GetPlayerCharacter(
                        GetWorld(),
                        0
                    )
                );
            }

            if (IsValid(PlayerCharacter))
            {
                PlayerCharacter->WinGame();
            }

            return;
        }

        SpawnWave();
    }
}
```

按顺序读这个完整函数：

1. `!bWaveActive` 就返回：只有处于活动中的波次才继续检查。
2. `CleanupDeadEnemies()` 把已经无效的敌人从本波数组移除，并更新剩余数量HUD。
3. 数组为空，说明这一个已活动的波次没有剩余有效敌人。
4. 先设 `bWaveActive = false`，再把 `CurrentWaveIndex` 加一。
5. 如果索引已经达到数组长度，就通知玩家胜利并返回。
6. 否则调用原有 `SpawnWave()` 生成下一波。

难点是**“没有当前波敌人”和“没有下一波配置”要同时成立，才走胜利分支**。

### 3.2 数组索引为什么用 >=，而HUD显示要 +1

例如 `Waves` 中配置了3波：

```text
内部索引0 → 第1波
内部索引1 → 第2波
内部索引2 → 第3波

第3波清完后：
    CurrentWaveIndex 原来是2
    ++CurrentWaveIndex 后变成3
    Waves.Num() 也是3
    3 >= 3：没有下一波，进入胜利分支
```

最后一波结束后索引等于长度，是用来判断“已经走出有效索引范围”。这时不要继续读取 `Waves[CurrentWaveIndex]`。当前代码先判断、再返回，因此不会用索引3读取只有3个元素的数组。

`CleanupDeadEnemies()` 更新剩余数量时，索引还未加一，因此最后一波HUD正常会收到“第3/3波，剩余0”。胜利分支没有再把HUD更新成“第4/3波”。

### 3.3 最后通知前为什么再找一次玩家

Spawner 的 `BeginPlay()` 原本就缓存了 `PlayerCharacter`。终局分支增加了一次补取：

```cpp
if (!IsValid(PlayerCharacter))
{
    PlayerCharacter = Cast<AMyArenaShooterCharacter>(
        UGameplayStatics::GetPlayerCharacter(GetWorld(), 0)
    );
}
```

这里尝试取得索引0的玩家角色，再转成项目的玩家类型。只有转换成功、引用有效时才调用 `WinGame()`。

要理解它的范围：这是进入胜利分支时的一次补取。如果这时仍取不到玩家，函数仍然会返回，而且 `bWaveActive` 已经是 false；后面的 Tick 不会持续重试胜利通知。这条链依赖玩家实例在结束时已经存在。初学阶段验证时，先确认场景实际生成的是 `BP_MyArenaShooterCharacter`。

## 4. WinGame 怎样把胜利落实到玩家

头文件增加一个 public 入口：

```cpp
void WinGame();
```

它是供 Spawner 直接调用的普通 C++ 函数，当前没有加 `UFUNCTION(BlueprintCallable)`。

完整实现：

```cpp
void AMyArenaShooterCharacter::WinGame()
{
    if (bIsDead || bHasWon)
    {
        return;
    }

    bHasWon = true;

    if (IsValid(CurrentWeapon))
    {
        CurrentWeapon->StopFire();
    }

    GetCharacterMovement()->DisableMovement();

    if (HUDWidget)
    {
        HUDWidget->ShowVictory();
    }
}
```

### 4.1 先检查状态，再记录胜利

`if (bIsDead || bHasWon)` 表示：已经死亡或已经胜利，就忽略这次通知。第一次有效通知才会执行 `bHasWon = true`。

这样，即使 `WinGame()` 被重复调用，也不会反复执行后面的结束操作。这种写法是“在入口用状态挡住重复执行”。

### 4.2 为什么设置 bHasWon 还要调用 StopFire

第2节的连射不是每发子弹都由输入回调直接生成：

```text
按下鼠标 → StartFire() 把 bFirePressed 设为true
    → 武器每帧 Tick
    → 条件满足就继续 Fire()
```

因此，新输入被拒绝之后，之前已经存在的 `bFirePressed = true` 仍可能让武器继续射击。`CurrentWeapon->StopFire()` 把它设回 false，终止这条已经启动的连射链。

完整的“阻止继续开火”有两个部分：

```text
WinGame / Die → StopFire → 清除旧的按住状态
StartFireInput → 检查终局状态 → 拒绝新的开始射击请求
```

`StopFire()` 没有销毁武器，没有销毁已经飞出的子弹，也没有取消换弹定时器。它直接控制的是武器后续 Tick 能否因为“仍按住”而继续开火。

### 4.3 DisableMovement 改变的是移动组件状态

`GetCharacterMovement()->DisableMovement()` 禁用角色移动，内部把移动模式设为 `MOVE_None`。它没有让整个世界停止 Tick，也没有自动解绑增强输入。官方说明见 [DisableMovement所在的移动组件API](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Engine/UCharacterMovementComponent?lang=en-US)。

当前 `Move()` 仍只检查 `bIsDead`；胜利时主要通过移动组件禁用来处理移动。`Look()`、`Dash()`、跳跃绑定没有新增统一的终局判断。因此，这一阶段要记为“对部分操作增加终局控制”，不能理解成已经把全部输入关闭。

## 5. 死亡也要停止已经开始的连射

本次 `Die()` 完整函数：

```cpp
void AMyArenaShooterCharacter::Die()
{
    bIsDead = true;

    if (IsValid(CurrentWeapon))
    {
        CurrentWeapon->StopFire();
    }

    GetCharacterMovement()->DisableMovement();

    if (HUDWidget)
    {
        HUDWidget->ShowGameOver();
    }

    UE_LOG(LogTemp, Warning, TEXT("Player Dead"));
}
```

以前“死亡后按下鼠标被拒绝”和“死亡前按住的连射被停止”是两件事。本次在 `Die()` 中也调用 `StopFire()`，补上了第二件事。

来源于受伤链的死亡：

```text
AI请求伤害
    → ReceiveEnemyDamage 检查玩家状态
    → 扣血、更新血条、闪红、受伤声音
    → 生命值降为0
    → Die
    → bIsDead = true
    → StopFire
    → DisableMovement
    → ShowGameOver
```

`Die()` 自己没有新增重复执行的入口判断；这里的重复受伤保护仍由 `ReceiveEnemyDamage()` 完成。旧章节中“死亡前已按住的连射还可能继续”的记录是当时的实现情况，这次 `StopFire()` 已补上该路径。

## 6. 新射击、换弹和伤害都检查结束状态

### 6.1 开始射击与请求换弹

```cpp
void AMyArenaShooterCharacter::StartFireInput(const FInputActionValue& Value)
{
    if (bIsDead || bHasWon)
    {
        return;
    }

    if (IsValid(CurrentWeapon))
    {
        CurrentWeapon->StartFire();
    }
}
```

```cpp
void AMyArenaShooterCharacter::ReloadInput(const FInputActionValue& Value)
{
    if (bIsDead || bHasWon)
    {
        return;
    }

    if (IsValid(CurrentWeapon))
    {
        CurrentWeapon->StartReload();
    }
}
```

两个入口都使用 `bIsDead || bHasWon`。结束后，即使增强输入系统仍然触发这些回调，也不会再把新请求送给武器。

`StopFireInput()` 没有增加这个限制。松开鼠标时清理按住状态仍然允许执行，不需要等角色恢复到正常游戏状态。

### 6.2 接受敌人伤害

```cpp
void AMyArenaShooterCharacter::ReceiveEnemyDamage(float Damage)
{
    if (bIsDead || bHasWon || Damage <= 0.0f)
    {
        return;
    }

    CurrentHealth = FMath::Clamp(CurrentHealth - Damage, 0.0f, MaxHealth);

    if (HUDWidget)
    {
        HUDWidget->UpdateHealth(CurrentHealth, MaxHealth);

        HUDWidget->ShowDamageFlash();
    }

    if (DamageSound && IsLocallyControlled())
    {
        UGameplayStatics::PlaySound2D(
            this,
            DamageSound
        );
    }

    if (CurrentHealth <= 0.0f)
    {
        Die();
    }
}
```

新加入的 `bHasWon` 让胜利后到达的攻击请求直接返回，不再扣血、闪红、播放受伤声音或进入死亡。

AIController 本次没有改变，仍会按照距离和攻击冷却提出伤害请求。玩家在受伤入口拒绝请求，并不表示 AI 已经停止 Tick。第3节记录了“AI提出请求”和“玩家接受请求”的区分。

普通波次里的敌人通常已经在胜利前全部销毁；如果地图还有不属于该 Spawner 数组的敌人，它的逻辑不会因为显示胜利文字自动停止。

## 7. UI新增 VictoryText 和 ShowVictory

### 7.1 声明与完整函数

在 `MyHUDWidget.h` 的原有控件后追加：

```cpp
UPROPERTY(meta = (BindWidget))
UTextBlock* VictoryText = nullptr;
```

public 函数区追加：

```cpp
void ShowVictory();
```

完整实现：

```cpp
void UMyHUDWidget::ShowVictory()
{
    if (VictoryText)
    {
        VictoryText->SetVisibility(ESlateVisibility::Visible);
    }
}
```

这个函数没有创建HUD，也没有判断剩余敌人，只把已经绑定的控件设为可见。正常顺序仍然是玩家 `BeginPlay()` 创建HUD并 `AddToViewport()`，终局再使用同一个HUD实例。

### 7.2 WBP_HUD需要连接的配置

1. `WBP_HUD` 的父类继续使用 `UMyHUDWidget`。
2. 在已有布局里追加一个 Text Block，名称精确为 `VictoryText`，类型与 `UTextBlock*` 对应，并确认勾选 **Is Variable**。
3. 文字可以写成“胜利！按重新开始键再来一局”；具体键位以 `IMC_Player` 中 `RestartAction` 的映射为准。
4. 设计器默认将 `VictoryText` 设为 `Hidden` 或 `Collapsed`，并配置位置、字号和颜色。
5. `GameOverText` 的默认隐藏也继续保留，编译并保存Widget蓝图。

这里的蓝图步骤是依据 C++ 绑定要求整理的配置说明，没有把二进制 `.uasset` 的内部值当作已验证结果。普通 `BindWidget` 要求有同名且类型兼容的控件；名字不匹配可能导致蓝图编译失败。函数里的空指针判断不能替代这项绑定要求。

## 8. NativeConstruct：HUD建立时先隐藏短暂反馈

### 8.1 本次完整实现

在头文件 protected 区声明：

```cpp
virtual void NativeConstruct() override;
```

```cpp
void UMyHUDWidget::NativeConstruct()
{
    Super::NativeConstruct();

    HideHitMarker();
    HideDamageFlash();
}
```

角色创建Widget并加入视口时，UE建立底层界面并调用构建生命周期。这里在父类构建行为之后，主动隐藏命中标记和受伤遮罩，让它们等待真正的游戏事件再显示。

```text
玩家 BeginPlay
    → CreateWidget<UMyHUDWidget>：创建HUD实例，初始化蓝图控件绑定
    → AddToViewport：加入视口，建立对应的界面
    → UE调用 NativeConstruct
    → Super::NativeConstruct
    → HideHitMarker
    → HideDamageFlash
    → 后续碰撞/受伤事件再调用各自的Show函数
```

本地 UE 5.4 的 `UUserWidget::Initialize()` 会调用蓝图类的 `InitializeWidget()`；运行时界面重建会调用 `NativeConstruct()`。在父类 `NativeConstruct()` 中还会触发蓝图的 Construct 事件。因此本项目的两次Hide放在 `Super` 后面；如果蓝图 Construct 里显示这两个控件，后面的C++ Hide仍会把它们隐藏。

### 8.2 为什么不在C++构造函数里操作绑定控件

构造函数执行时，Widget蓝图中的控件绑定还没有准备好。这里应在已建立界面的生命周期里操作这些引用。

`NativeConstruct()` 是引擎生命周期函数，通过 `override` 覆盖父类行为，当前代码无需手动调用它。`Super::NativeConstruct()` 用于保留父类构建行为。官方类声明见 [UUserWidget API](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/UMG/UUserWidget)。

### 8.3 它不保证一个对象一生只执行一次

底层界面重新建立、移除后重新加入层级等情形可能再次触发Construct阶段。若要理解只初始化一次的事件，可进一步查阅 OnInitialized。本项目每次构建时隐藏这两个短暂反馈，是可以重复执行的操作。官方说明见 [UUserWidget::Construct](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/UMG/UUserWidget/Construct?lang=en-US)。

当前 `NativeConstruct()` **只隐藏 HitMarkerText 和 DamageFlashOverlay**，没有隐藏 `VictoryText`、`GameOverText`，也没有清除反馈定时器。因此胜负文字仍依赖蓝图默认隐藏。第4节中上一阶段“C++没有初始化隐藏”的记录，在这两个短暂反馈控件上已由本次实现补齐。

## 9. 重新开始：把允许条件从死亡扩展到死亡或胜利

### 9.1 当前完整函数

```cpp
void AMyArenaShooterCharacter::RestartGame(const FInputActionValue& Value)
{
    if (!bIsDead && !bHasWon)
    {
        return;
    }

    FString CurrentLevelName = UGameplayStatics::GetCurrentLevelName(this, true);

    UGameplayStatics::OpenLevel(this, FName(*CurrentLevelName));
}
```

难点在这一句：

```cpp
if (!bIsDead && !bHasWon)
{
    return;
}
```

它的含义是“既没死、也没胜利，仍在游戏中，就不重开”。只有至少一个结束状态成立，才继续执行。

```text
还活着且没赢：!false && !false = true → return
已经死亡：    !true  && !false = false → 可以重开
已经胜利：    !false && !true  = false → 可以重开
```

从逻辑上看，允许重开的条件是 `bIsDead || bHasWon`，取反后就是提前返回条件 `!bIsDead && !bHasWon`。不要误写成两个否定之间用 `||`，那样死亡时“没赢”为true、胜利时“没死”为true，都会把重开挡住。

### 9.2 地图名字与 OpenLevel

`UGameplayStatics::GetCurrentLevelName(this, true)` 取得当前地图名；第二个参数要求移除编辑器或流送可能添加的前缀，便于在PIE里使用正常地图名。参见 [GetCurrentLevelName参数说明](https://dev.epicgames.com/documentation/en-us/unreal-engine/BlueprintAPI/Game/GetCurrentLevelName)。

返回值是 `FString`。`FName(*CurrentLevelName)` 把该字符串构造成传给 `OpenLevel` 的名字参数，其中 `*CurrentLevelName` 是 `FString` 提供的字符指针访问方式。

`UGameplayStatics::OpenLevel(this, FName(*CurrentLevelName))` 请求打开同一张地图，通过重新加载来重新开始这一局。它不是逐个手动把当前角色血量、弹药和波次改回初始值。官方入口见 [OpenLevel所在的UGameplayStatics API](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Engine/UGameplayStatics)。

```text
RestartAction Started
    → RestartGame
    → 已死亡或已胜利？
    → 取得无编辑器前缀的地图名
    → OpenLevel请求重新加载
    → 地图中的相关Actor和玩家重新创建/开始运行
    → 新玩家初始化血量、HUD和武器
    → 新武器初始化弹匣与备用弹药
    → 新Spawner从 CurrentWaveIndex = 0 开始 SpawnWave
```

这条链针对当前项目的地图Actor。`GameInstance` 等跨地图对象并不会因此全部重建；本次血量、弹药、波次都放在重新创建的Actor中，所以这一方式能让它们重新初始化。

## 10. 把最后一颗子弹一直跟到胜利与重开

```text
1. 武器 Fire
   → 相机射线选瞄准点
   → 从枪口计算方向
   → SpawnActor生成子弹
   → 检查生成结果有效后播放枪口效果、声音、扣弹药

2. 子弹实际碰撞最后一个Enemy
   → Enemy->TakeProjectileDamage(Damage)
   → 有效伤害使生命值变为0
   → Enemy请求Destroy，并返回true表示接受了本次伤害
   → 子弹通知玩家显示命中标记
   → 在实际接触点生成命中特效、播放命中声音
   → 子弹请求Destroy

3. 后续Spawner Tick
   → CleanupDeadEnemies移除已无效的Enemy引用
   → 更新本波剩余数量为0
   → 本波数组空，bWaveActive设false
   → 当前波索引加一
   → 索引达到Waves.Num，已经没有下一波
   → 取得有效玩家并调用WinGame

4. 玩家WinGame
   → 若已死或已赢，直接返回
   → bHasWon设true
   → StopFire清除按住连射状态
   → DisableMovement
   → HUD显示VictoryText
   → 后续新射击、换弹、伤害请求被入口判断拒绝

5. 按重新开始键
   → RestartGame允许胜利状态重开
   → OpenLevel重新加载当前地图
   → 新的一局初始化
```

这里跨越了输入回调、子弹移动碰撞事件、Spawner逐帧检查和地图加载流程，不是一个函数从头执行到尾。Enemy调用 `Destroy()` 后也不会自动把自己从 `CurrentWaveEnemies` 中删除；数组清理由 Spawner 的后续检查完成。销毁语义见 [AActor::Destroy](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Engine/AActor/Destroy)。

把难点改写成伪代码：

```text
当子弹实际撞到敌人：
    如果敌人接受伤害：
        通知发射玩家显示命中标记
    播放符合条件的接触效果和声音
    销毁子弹

当Spawner更新：
    如果当前没有活动波次：结束本次更新
    清理无效敌人
    如果本波仍有敌人：结束本次更新

    结束本波并推进索引
    如果索引已超出配置：通知玩家胜利，然后结束更新
    否则：生成下一波

当玩家收到胜利通知：
    如果已经死亡或胜利：忽略通知
    否则：记录胜利，停止连射，禁用移动，显示胜利提示
```

## 11. 按执行链验证，并记住当前实现范围

| 观察到的表现 | 优先检查的位置 |
| --- | --- |
| 最后一波结束但没有胜利提示 | 本波数组是否清空、索引是否到达长度、玩家引用是否有效、WinGame是否被状态拒绝、VictoryText是否绑定 |
| 日志有All Waves Completed但没有胜利 | 区分SpawnWave里的旧完成日志与Tick里的新胜利分支；日志本身不保证WinGame已执行 |
| 终局后继续自动射击 | Die/WinGame是否实际调用，CurrentWeapon是否有效，StopFire是否清掉bFirePressed |
| 刚进入地图就显示胜负文字 | VictoryText/GameOverText的蓝图默认可见性；NativeConstruct目前没有隐藏它们 |
| 胜利后重开无效 | RestartAction映射与绑定、两个否定之间是否使用&&、地图名是否正确 |
| 某波没有任何敌人也不推进 | 波次是否配置正数量、出生点是否有效、是否成功生成至少一个敌人使bWaveActive变true |

最后一行来自当前 `SpawnWave()` 的实现：如果没有成功生成任何敌人，波次可能一直不活动，Tick便不会进入清空后推进的流程。空 `Waves` 也会在最初 `SpawnWave()` 的范围判断处返回，没有自动调用 `WinGame()`。本阶段的正常链依赖有效的波次与出生点配置。

当前胜利范围是该 Spawner 管理的全部配置波次。它没有统计地图里所有Enemy，也没有暂停游戏、关闭AI或统一屏蔽所有输入。正在飞行的子弹和已开始的换弹定时器仍可能继续。若最后击杀与致命受伤很接近，代码按实际事件调用顺序处理；玩家已经死亡时，后来的 `WinGame()` 会被拒绝，当前没有另设“同帧优先胜利”规则。
