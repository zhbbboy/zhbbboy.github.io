> 学习阶段说明：第 1～11 节完整保留基础单发阶段的逐步记录；第 12 节起追加连射、弹药、换弹与 HUD 的后续实现。早期段落中的“当前”“尚未实现”对应当时的学习阶段，最新代码请对照后续记录。

这节记录在第一节角色基础移动的基础上，创建武器、绑定射击输入、从枪口生成子弹，以及子弹飞行和碰撞销毁的过程。

当前项目使用 UE 5.4 和 C++。本节代码对应 `AMyArenaShooterCharacter`、`AMyWeapon`、`AMyProjectile` 的当前实现。先理解各对象负责什么，再结合具体按键走完整条执行链。

按最新实现，子弹命中敌人后会调用敌人的受伤函数，默认造成 25 点伤害，再销毁子弹；敌人血量归零时销毁。弹药、射速、换弹、准星瞄准和射击特效尚未实现。敌人的血量管理、AI 追击和攻击会在第三节展开，本节先把射击到伤害的连接讲清楚。

## 1. 先理解这次增加的三个对象

| 对象 | 本节职责 | 不同对象之间的调用 |
| --- | --- | --- |
| Character：玩家角色 | 持有武器，接收射击输入 | 调用当前武器的 `Fire()` |
| Weapon：武器 Actor | 保存枪口位置和子弹类 | 从枪口生成 Projectile |
| Projectile：子弹 Actor | 移动、碰撞、携带伤害和自身清理 | 命中敌人时调用 `TakeProjectileDamage(Damage)` |

```text
玩家角色 Character
    │ 持有 CurrentWeapon
    ↓
武器 Weapon
    │ 保存 ProjectileClass
    │ Fire() 时 SpawnActor
    ↓
子弹 Projectile
    │ ProjectileMovement 驱动
    ↓
碰撞 → 命中回调 → 判断是否为 Enemy → 敌人扣血 → 子弹 Destroy
```

角色不需要亲自计算每颗子弹的飞行；武器不需要监听角色的所有移动输入；子弹也不需要知道鼠标按键叫什么。把这些职责分开后，后面替换不同武器和子弹更方便。

### 1.1 当前是生成实体子弹的射击方式

```text
按下射击
↓
创建一个存在于游戏世界中的 Projectile Actor
↓
子弹经过时间飞行
↓
碰撞后处理命中
```

这与直接执行 Line Trace、立即判断射线击中谁的方式不同。当前没有执行射线检测；伤害来自子弹碰撞后显式调用敌人的受伤函数，UE 不会仅因为发生 Hit 就自动扣血。

### 1.2 两条链需要同时成立

```text
准备链：角色生成 → 武器生成 → 挂到相机 → 输入映射启用 → 射击回调已绑定

运行链：左键 → IA_Fire → FireInput → Weapon.Fire → 生成子弹 → 飞行 → 命中或超时销毁
```

准备链是配置和初始化依赖示意，不强制规定所有引擎回调的绝对先后顺序。运行时每次开火使用已经准备好的武器和输入绑定，不是每次点击都重新生成一把枪。

## 2. 创建武器类 AMyWeapon

武器是独立放在游戏世界中的对象，所以本节让它继承 `AActor`，不需要继承带有角色移动功能的 `ACharacter`。

```text
AActor
├─ AMyWeapon
└─ AMyProjectile
```

### 2.1 武器的成员声明

在 `MyWeapon.h` 中使用以下前置声明：

```cpp
class USceneComponent;
class USkeletalMeshComponent;
class AMyProjectile;
```

以下成员放在已有的 `AMyWeapon` 类内部：

```cpp
private:
    UPROPERTY(VisibleAnywhere, Category = "Weapon")
    USceneComponent* Root;

    UPROPERTY(VisibleAnywhere, Category = "Weapon")
    USkeletalMeshComponent* WeaponMesh;

    UPROPERTY(VisibleAnywhere, Category = "Weapon")
    USceneComponent* MuzzleLocation;

    UPROPERTY(EditDefaultsOnly, Category = "Weapon")
    TSubclassOf<AMyProjectile> ProjectileClass;

public:
    AMyWeapon();
    void Fire();
```

这些成员分别回答四个问题：

| 成员                | 回答的问题                   |
| ----------------- | ----------------------- |
| `Root`            | 武器的组件以谁作为整体位置、旋转和缩放的基准？ |
| `WeaponMesh`      | 武器用哪个组件显示模型？            |
| `MuzzleLocation`  | 子弹从哪里、朝哪个方向生成？          |
| `ProjectileClass` | 每次开火要生成哪一种子弹类？          |

`CreateDefaultSubobject`、`SetupAttachment`、`UPROPERTY` 在第一节已经出现，本节继续使用它们。

### 2.2 构造函数：建立组件结构

```cpp
AMyWeapon::AMyWeapon()
{
    PrimaryActorTick.bCanEverTick = false;

    Root = CreateDefaultSubobject<USceneComponent>(TEXT("Root"));
    RootComponent = Root;

    WeaponMesh = CreateDefaultSubobject<USkeletalMeshComponent>(TEXT("WeaponeMesh"));
    WeaponMesh->SetupAttachment(Root);

    MuzzleLocation = CreateDefaultSubobject<USceneComponent>(TEXT("MuzzleLocation"));
    MuzzleLocation->SetupAttachment(WeaponMesh);
}
```

组件的空间层级是：

```text
AMyWeapon
└─ Root：USceneComponent，作为 RootComponent
   └─ WeaponMesh：USkeletalMeshComponent
      └─ MuzzleLocation：USceneComponent
```

当前代码中的组件内部名称是 `WeaponeMesh`，变量名称是 `WeaponMesh`。字符串里的拼写不会决定变量名；在编辑器里找组件时注意这处区别。

武器没有需要手动每帧处理的逻辑，所以关闭 Actor Tick。`Fire()` 由角色调用，关闭 Tick 不会阻止普通函数调用。

#### 首次出现：USceneComponent 与 RootComponent

`USceneComponent` 是具有位置、旋转和缩放的组件，但它本身不一定显示模型，也不负责碰撞。这里用它做武器的空间根节点和枪口标记。

```cpp
RootComponent = Root;
```

`RootComponent` 是 Actor 自带的根组件引用。把刚创建的 `Root` 赋给它后，武器 Actor 的位置、旋转和缩放以这个组件为基准，其他场景组件再挂在它下面。

这里只声明 `Root` 指针不够，要先创建组件，再指定它为根组件。

#### 首次出现：USkeletalMeshComponent

它是显示骨骼网格体的组件，适合之后需要骨骼、动画等功能的武器资源。

注意 **Skeletal Mesh 与 Static Mesh 是不同资源类型**。当前项目导入的部分枪械资源是 `SM_...` 静态网格体，不能直接当作骨骼网格体填入这个组件。若使用静态枪模型，需要采用匹配的 `UStaticMeshComponent`，或在蓝图中配置相应静态网格体组件，并明确模型和枪口的层级关系。

这与射击函数是否被调用是两个问题：模型没有显示，不代表武器 Actor 没有生成。

#### 首次出现：用 SceneComponent 表示枪口

`MuzzleLocation` 本身不需要是可见模型，它是一个可以调整位置和旋转的标记。

在武器蓝图中把它放到枪口前方，并让它的局部 **+X 方向** 指向期望的射击方向。本节子弹的初始方向与这一点有关。

挂在 WeaponMesh 下意味着：模型组件发生位置和旋转变化时，枪口标记也随之变化。仅把枪口放到正确位置还不够，旋转也要正确。

## 3. 让角色生成并持有武器

### 3.1 区分“武器类”和“武器实例”

在角色头文件中前置声明 `AMyWeapon`，并添加：

```cpp
private:
    UPROPERTY(EditDefaultsOnly, Category = "Weapon")
    TSubclassOf<AMyWeapon> DefaultWeaponClass;

    UPROPERTY()
    AMyWeapon* CurrentWeapon = nullptr;
```

#### 首次出现：TSubclassOf

`TSubclassOf<AMyWeapon>` 保存一个受类型限制的类引用：它只能指向 `AMyWeapon` 或其派生类，包括 `BP_MyWeapon` 生成的蓝图类。

```text
DefaultWeaponClass = BP_MyWeapon 的类
            ↓ 交给 SpawnActor
CurrentWeapon = 实际生成的一把武器对象
```

类用于决定创建什么对象；实例指针用于访问已经创建出来的对象。不能只在蓝图选择 `DefaultWeaponClass`，就认为 `CurrentWeapon` 自动有了对象。

与第一节的 `UInputAction*` 也不同：`FireAction` 指向已经存在的输入资产，本节的 `TSubclassOf` 则用于指定要实例化的 Actor 类型。

`CurrentWeapon` 使用 `UPROPERTY()` 让 UE 认识这个对象引用，但没有编辑器可见、可编辑的标记。它由运行时代码赋值，不需要在蓝图里手动挑一把已经生成的枪。

### 3.2 在 BeginPlay 中生成武器

在角色 `.cpp` 中包含 `MyWeapon.h`。下面是最新的 `BeginPlay()`：先初始化玩家血量，再启用输入映射、生成武器。血量部分将在第三节说明，这里保留这一行，避免将旧版本片段当作完整的当前函数。

```cpp
void AMyArenaShooterCharacter::BeginPlay()
{
    Super::BeginPlay();

    CurrentHealth = MaxHealth;

    if (APlayerController* PlayerController = Cast<APlayerController>(Controller))
    {
        if (UEnhancedInputLocalPlayerSubsystem* Subsystem =
            ULocalPlayer::GetSubsystem<UEnhancedInputLocalPlayerSubsystem>(
                PlayerController->GetLocalPlayer()
            ))
        {
            if (DefaultMappingContext)
            {
                Subsystem->AddMappingContext(DefaultMappingContext, 0);
            }
        }
    }

    if (DefaultWeaponClass)
    {
        FActorSpawnParameters SpawnParams;

        SpawnParams.Owner = this;
        SpawnParams.Instigator = this;

        CurrentWeapon = GetWorld()->SpawnActor<AMyWeapon>(
            DefaultWeaponClass,
            FirstPersonCameraComponent->GetComponentLocation(),
            FirstPersonCameraComponent->GetComponentRotation(),
            SpawnParams
        );

        if (CurrentWeapon)
        {
            CurrentWeapon->AttachToComponent(
                FirstPersonCameraComponent,
                FAttachmentTransformRules::SnapToTargetIncludingScale
            );

            CurrentWeapon->SetActorRelativeLocation(
                FVector(30.0f, 10.0f, -10.0f)
            );
        }
    }
}
```

#### 首次出现：GetWorld 与 SpawnActor

`GetWorld()` 取得这个角色所在的 `UWorld`，即当前游戏世界。Play 的游戏世界与编辑器中的世界不是简单同一个对象；这里在游戏开始后的角色上取得所在世界，再向它创建 Actor。

```cpp
GetWorld()->SpawnActor<AMyWeapon>(
    DefaultWeaponClass,
    SpawnLocation,
    SpawnRotation,
    SpawnParams
);
```

可以逐项读成：

| 部分 | 含义 |
| --- | --- |
| `<AMyWeapon>` | 按 `AMyWeapon*` 类型取得生成结果 |
| `DefaultWeaponClass` | 真正要生成的类，本节在蓝图中指定 `BP_MyWeapon` |
| `SpawnLocation` | 初始世界位置 |
| `SpawnRotation` | 初始世界旋转，类型是 `FRotator` |
| `SpawnParams` | Owner、Instigator、碰撞处理等生成参数 |
| 返回值 | 已生成的武器指针；生成失败时可能为空 |

`SpawnActor` 创建的是游戏世界中的完整 Actor。`CreateDefaultSubobject` 创建的是类的默认组件，两者用途不同。正常的非延迟生成还涉及构造、组件初始化、BeginPlay 等生命周期过程，不能理解成只给一个指针分配空间。可参考 [Actor 生成说明](https://dev.epicgames.com/documentation/en-us/unreal-engine/spawning-actors-in-unreal-engine)。

这里的 `if (CurrentWeapon)` 确保生成成功后才继续挂载。`if (DefaultWeaponClass)` 则是在生成之前检查蓝图有没有指定类，它们检查的是不同阶段。

#### 首次出现：FActorSpawnParameters、Owner 与 Instigator

`FActorSpawnParameters` 是设置生成选项的结构体。当前代码只明确设置其中两个字段，其余保持默认行为。

| 字段 | 类型与用途 | 生成武器时的值 |
| --- | --- | --- |
| `Owner` | Actor 引用，建立 UE 的 Owner 关系，可参与网络和归属相关逻辑 | 当前 Character |
| `Instigator` | Pawn 引用，表示行为的发起者，常用于伤害等来源追踪 | 当前 Character |

两者这里都填写 `this`，因为正在执行角色的 `BeginPlay()`，`this` 指的就是当前角色，而 Character 也是 Pawn。

Owner 关系不等于组件挂载关系，不会自动让枪跟随相机；也不等于 C++ 中独占资源的所有权，更不会自动让子弹忽略发射者的碰撞。这些需求要分别配置。字段定义可参考 [FActorSpawnParameters](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Engine/FActorSpawnParameters)。

#### 首次出现：GetComponentLocation 与 GetComponentRotation

这两个函数取得场景组件的 **世界位置与世界旋转**。

角色生成武器时取得相机的世界变换，武器生成子弹时取得枪口的世界变换。`SpawnActor` 需要的是实际出生位置和旋转，所以这里使用世界坐标。

它们与 `GetRelativeLocation()` 这类相对变换不同：父组件移动或旋转后，世界变换也会随层级关系更新。

### 3.3 将武器挂到相机并设置偏移

#### 首次出现：AttachToComponent

```cpp
CurrentWeapon->AttachToComponent(
    FirstPersonCameraComponent,
    FAttachmentTransformRules::SnapToTargetIncludingScale
);
```

这会把武器 Actor 的根组件挂到相机组件下面。因此，角色移动或转动视角时，武器也跟着相机变化。

第一节的 `SetupAttachment()` 用于构造默认组件时建立挂载关系；这里的 `AttachToComponent()` 用于将已经生成的武器挂到另一个对象的组件上。

```text
角色 Capsule
└─ FirstPersonCamera
   └─ CurrentWeapon 的 Root
      └─ WeaponMesh
         └─ MuzzleLocation
```

#### 首次出现：FAttachmentTransformRules

挂载不仅要指定父组件，还要决定如何处理已有位置、旋转和缩放。

| 规则 | 可以这样理解 |
| --- | --- |
| `KeepRelativeTransform` | 保留已有相对变换 |
| `KeepWorldTransform` | 挂载时尽量保持原来的世界变换 |
| `SnapToTargetIncludingScale` | 对齐到目标位置、旋转和缩放 |
| `SnapToTargetNotIncludingScale` | 对齐目标位置、旋转，保留挂载时的世界缩放 |

**当前代码使用 IncludingScale，包含缩放对齐。** 源码旁“不要继承 Camera 的 Scale”的注释与实际使用的规则相反；如果想在挂载时保留世界缩放，应考虑 NotIncludingScale。保留挂载时的世界缩放，也不等于之后父组件缩放永远不会影响子组件。

本笔记解释现有代码的真实含义，不把这处注释当作 API 的定义。可查阅 [FAttachmentTransformRules](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Engine/FAttachmentTransformRules)。

#### 首次出现：SetActorRelativeLocation

```cpp
CurrentWeapon->SetActorRelativeLocation(FVector(30.0f, 10.0f, -10.0f));
```

挂载后设置武器相对于父组件的位置。相机的局部 X 大致是前方，Y 是右方，Z 是上方，因此这段设置让枪位于相机前方 30 厘米、右侧 10 厘米、下方 10 厘米。

先对齐，再加偏移，可以把武器放到第一人称画面的右下方。这个偏移处于相机的局部坐标系中，跟随相机转动，而不是固定向世界 X 方向移动 30 厘米。

## 4. 绑定射击输入：从左键到 FireInput

### 4.1 创建 IA_Fire 并指定给角色

创建 `IA_Fire`，Value Type 使用 **Digital / Bool**。在现有 `IMC_Player` 中将它映射到 **Left Mouse Button（鼠标左键）**。

在角色头文件中添加：

```cpp
private:
    UPROPERTY(EditDefaultsOnly, Category = "Input")
    UInputAction* FireAction = nullptr;

public:
    void FireInput(const FInputActionValue& Value);
```

在 `BP_MyArenaShooterCharacter` 的类默认值中，把 Fire Action 设置为 `IA_Fire`。

仍然使用第一节已经启用的 `IMC_Player`，不用为了新增射击再创建一个输入子系统。

### 4.2 在输入组件中绑定 Started

以下内容放在已有 `SetupPlayerInputComponent()` 的 `EnhancedInputComponent` 判定内部，与 Move、Look 等绑定并列：

```cpp
if (FireAction)
{
    EnhancedInputComponent->BindAction(
        FireAction,
        ETriggerEvent::Started,
        this,
        &AMyArenaShooterCharacter::FireInput
    );
}
```

这些 API 在第一节已经解释。此处使用 `Started`，当前默认 Trigger 行为下，一次按下左键尝试开火一次，持续按住不会每帧重复调用这个绑定。

因此本节是按次触发的基础射击。以后实现自动武器，需要增加按住状态、射速或定时器等逻辑；不能简单把每帧触发等同于可控射速。

### 4.3 角色只把射击请求交给武器

```cpp
void AMyArenaShooterCharacter::FireInput(const FInputActionValue& Value)
{
    if (IsValid(CurrentWeapon))
    {
        CurrentWeapon->Fire();
    }
}
```

当前回调只需要知道操作开始，不读取 Bool 的数值，所以参数 `Value` 没有使用。

角色负责检查“是否有可用武器”，然后调用它；子弹的类、枪口位置和生成细节属于 Weapon 的职责。

#### 首次出现：IsValid

`IsValid(CurrentWeapon)` 检查 UE 对象是否可用：不仅要求引用不为空，也检查对象是否已进入待销毁或垃圾状态。

```text
CurrentWeapon 可用 → 调用 Fire()
CurrentWeapon 不可用 → 不继续调用
```

只检查 `CurrentWeapon != nullptr`，不能完整表达“这个 UE 对象仍然可用”。`IsValid` 也不是任意 C++ 指针的通用修复工具，应在对象引用由 UE 正常管理的前提下使用。

## 5. 武器 Fire：从枪口生成子弹

### 5.1 当前实现

在 `MyWeapon.cpp` 中包含 `MyProjectile.h`，让编译器认识子弹类型的定义。

```cpp
void AMyWeapon::Fire()
{
    if (!ProjectileClass)
    {
        return;
    }

    if (!MuzzleLocation)
    {
        return;
    }

    FActorSpawnParameters SpawnParams;
    SpawnParams.Owner = this;
    SpawnParams.Instigator = GetInstigator();

    GetWorld()->SpawnActor<AMyProjectile>(
        ProjectileClass,
        MuzzleLocation->GetComponentLocation(),
        MuzzleLocation->GetComponentRotation(),
        SpawnParams
    );
}
```

第一处判断确认武器蓝图已经指定子弹类，第二处确认枪口组件存在。`return` 表示直接结束本次 Fire，后面的生成不再执行。

`ProjectileClass` 的类型是 `TSubclassOf<AMyProjectile>`，在 `BP_MyWeapon` 的类默认值中指定 `BP_MyProjectile`。因此生成出来的子弹会使用子弹蓝图中的模型和组件默认配置。

当前代码没有保存这次 `SpawnActor` 的返回值。调用了 Fire 并不证明生成一定成功；调试时可以保存返回的 `AMyProjectile*` 并检查它。

### 5.2 首次出现：GetInstigator 与行为来源传递

生成武器时：

```cpp
SpawnParams.Owner = this;       // this 是 Character
SpawnParams.Instigator = this;  // 发起者也是 Character
```

生成子弹时：

```cpp
SpawnParams.Owner = this;                 // this 是 Weapon
SpawnParams.Instigator = GetInstigator(); // 取出武器记录的 Character
```

`GetInstigator()` 取得这个 Actor 上保存的发起 Pawn。本节把角色身份从武器传递给子弹。

| 对象 | Owner | Instigator |
| --- | --- | --- |
| Weapon | Character | Character |
| Projectile | Weapon | Character |

```text
子弹由哪把武器直接创建？→ Owner：Weapon
这次行为由哪个玩家角色发起？→ Instigator：Character
```

来源信息可以帮助追踪是谁开的枪。但设置 Owner、Instigator 本身不会造成伤害，也不会自动完成击杀统计。最新实现是在命中回调中显式调用敌人的受伤函数；该函数当前只接收伤害数值，没有使用来源引用。

### 5.3 枪口的位置与方向怎样变成出生变换

```text
相机转动
↓
挂在相机下的武器随之转动
↓
武器组件层级中的 MuzzleLocation 获得新的世界位置和旋转
↓
Fire() 读取枪口世界变换
↓
子弹从该位置、按该旋转生成
```

这里不是直接从相机中心生成子弹，也没有自动“瞄准屏幕中心”。当前行为是从枪口按枪口朝向发射。相机与枪口有位置偏移，近距离时枪口射线与视线不一定重合；准星瞄准和近墙处理是后续设计内容。

## 6. 创建子弹类 AMyProjectile

### 6.1 三个组件分别负责什么

在 `MyProjectile.h` 中前置声明：

```cpp
class USphereComponent;
class UStaticMeshComponent;
class UProjectileMovementComponent;
```

在子弹类内部声明以下成员：

```cpp
private:
    UPROPERTY(VisibleAnywhere, Category = "Projectile")
    USphereComponent* CollisionComponent;

    UPROPERTY(VisibleAnywhere, Category = "Projectile")
    UStaticMeshComponent* ProjectileMesh;

    UPROPERTY(VisibleAnywhere, Category = "Projectile")
    UProjectileMovementComponent* ProjectileMovement;

    UPROPERTY(EditDefaultsOnly, Category = "Damage")
    float Damage = 25.0f;
```

它们放在 `AMyProjectile` 类内部：

| 组件 | 本节职责 |
| --- | --- |
| `CollisionComponent` | 球形碰撞体，负责判断撞到了什么 |
| `ProjectileMesh` | 显示子弹外观 |
| `ProjectileMovement` | 计算并执行子弹移动 |

```text
AMyProjectile
└─ CollisionComponent：Sphere，作为空间根组件
   └─ ProjectileMesh：StaticMesh，跟随显示

ProjectileMovement：移动逻辑组件
        └─ UpdatedComponent 指向 CollisionComponent
```

`ProjectileMovement` 不是挂在球体下的另一个空间节点，而是驱动某个组件移动的逻辑组件。

最新增加的 `Damage` 不是组件，而是每颗子弹携带的伤害数值。C++ 默认值为 25；`EditDefaultsOnly` 允许在 `BP_MyProjectile` 类默认值中配置不同伤害，所以实际数值以生成所用蓝图的默认值为准。

#### 首次出现：USphereComponent 与 UStaticMeshComponent

`USphereComponent` 提供球形碰撞体。使用简单球体处理子弹碰撞，比让模型的复杂形状负责所有移动碰撞更容易理解和控制。

`UStaticMeshComponent` 显示静态网格体。静态网格体的“静态”表示资源类型，不表示这个组件永远不能移动；它挂在移动的碰撞体下，也会跟着移动。

子弹可以有碰撞体但没有可见模型，也可以有模型却关闭模型自己的碰撞。这是两个独立职责。

### 6.2 当前子弹构造函数

需要的头文件：

```cpp
#include "MyProjectile.h"
#include "Components/SphereComponent.h"
#include "Components/StaticMeshComponent.h"
#include "GameFramework/ProjectileMovementComponent.h"
```

```cpp
AMyProjectile::AMyProjectile()
{
    PrimaryActorTick.bCanEverTick = false;

    CollisionComponent =
        CreateDefaultSubobject<USphereComponent>(TEXT("CollisionComponent"));
    RootComponent = CollisionComponent;
    CollisionComponent->InitSphereRadius(5.0f);

    CollisionComponent->SetCollisionEnabled(ECollisionEnabled::QueryAndPhysics);
    CollisionComponent->SetCollisionObjectType(ECC_WorldDynamic);
    CollisionComponent->SetCollisionResponseToAllChannels(ECR_Block);

    ProjectileMesh =
        CreateDefaultSubobject<UStaticMeshComponent>(TEXT("ProjectileMesh"));
    ProjectileMesh->SetupAttachment(CollisionComponent);
    ProjectileMesh->SetCollisionEnabled(ECollisionEnabled::NoCollision);

    ProjectileMovement =
        CreateDefaultSubobject<UProjectileMovementComponent>(TEXT("ProjectileMovement"));
    ProjectileMovement->UpdatedComponent = CollisionComponent;

    ProjectileMovement->InitialSpeed = 3000.0f;
    ProjectileMovement->MaxSpeed = 3000.0f;
    ProjectileMovement->bRotationFollowsVelocity = true;
    ProjectileMovement->ProjectileGravityScale = 0.0f;

    InitialLifeSpan = 5.0f;
}
```

### 6.3 首次出现：球体半径与碰撞 API

```cpp
CollisionComponent->InitSphereRadius(5.0f);
```

初始化球体半径。默认单位下是 5 厘米的未缩放半径；如果 Actor 或组件有缩放，世界中的碰撞尺寸也会受影响。

碰撞的三个设置分别回答不同问题：

| API | 当前参数 | 回答的问题 |
| --- | --- | --- |
| `SetCollisionEnabled()` | `QueryAndPhysics` | 这个组件参与哪些种类的碰撞处理？ |
| `SetCollisionObjectType()` | `ECC_WorldDynamic` | 这个组件被视为哪一种碰撞对象？ |
| `SetCollisionResponseToAllChannels()` | `ECR_Block` | 遇到各个通道时，本组件采取什么响应？ |

`QueryAndPhysics` 允许碰撞查询与物理碰撞；它不等于开启 **Simulate Physics**。本节使用 ProjectileMovement 驱动子弹，不需要为了飞行而额外让球体模拟刚体物理。

`WorldDynamic` 是对象类型标签，不是“自动移动”的开关。

`Block` 是阻挡响应；另外常见的还有 `Overlap` 和 `Ignore`。真正两个组件相遇时，还要结合双方的碰撞配置。本子弹设置 Block All，不代表另一方关闭碰撞或设为 Ignore 时仍会产生阻挡命中。

模型部分：

```cpp
ProjectileMesh->SetCollisionEnabled(ECollisionEnabled::NoCollision);
```

关闭模型的碰撞，让球体负责移动碰撞，避免外观与碰撞职责混在一起。调整模型显示大小，不一定会改变根球体的碰撞半径。

### 6.4 首次出现：UProjectileMovementComponent 与 UpdatedComponent

```cpp
ProjectileMovement->UpdatedComponent = CollisionComponent;
```

`UpdatedComponent` 指定移动组件要驱动谁。本节让它驱动根球体，子弹的 Actor 变换随根组件变化，下面的模型也跟着变化。

```text
ProjectileMovement 更新
↓
移动 CollisionComponent
↓
球体沿移动路径检测碰撞
↓
ProjectileMesh 通过挂载关系跟随
```

移动组件通常对被更新的组件执行扫掠碰撞。把碰撞球作为移动目标，才能让移动与预期的碰撞形状对应起来。

武器和子弹虽然都关闭了 **Actor Tick**，但子弹仍然能移动，因为 ProjectileMovement 有自己的组件 Tick。`PrimaryActorTick.bCanEverTick = false` 不会统一关闭这个 Actor 上所有组件的 Tick。

相关定义可对照 [UProjectileMovementComponent](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Engine/UProjectileMovementComponent)。

### 6.5 子弹速度、朝向与重力

| 属性 | 当前值 | 含义 |
| --- | --- | --- |
| `InitialSpeed` | `3000.0f` | 初始化时采用的速度大小，约 30 米每秒 |
| `MaxSpeed` | `3000.0f` | 移动组件使用的速度上限，不是射程 |
| `bRotationFollowsVelocity` | `true` | 更新朝向，让它跟随当前速度方向 |
| `ProjectileGravityScale` | `0.0f` | 将投射物重力影响缩放为零 |

初始速度和最大速度不是同一个概念：一个设置出生时的速度大小，一个限制后续速度大小。速度为 3000，也不是一帧直接移动 3000 厘米；移动组件会结合时间步长推进。

#### 为什么只设置出生旋转，子弹就能朝枪口方向飞

当前代码没有手动写 `Velocity = ...`。在 UE 5.4 的 ProjectileMovement 默认实现中：

- 初始 `Velocity` 为局部 `(1, 0, 0)`，也就是 +X 方向。
- `bInitialVelocityInLocalSpace` 默认开启。
- `InitialSpeed > 0` 时，以初始 Velocity 的方向设置速度大小，再转换到世界方向。

因此，在蓝图没有覆盖这些默认值的前提下：

```text
枪口世界旋转
↓
作为子弹的出生旋转
↓
子弹局部 +X 转成该朝向下的世界方向
↓
按 InitialSpeed 飞行
```

`bRotationFollowsVelocity` 负责“让朝向跟随速度”，不是“看到模型朝向哪里就自动往那里飞”。如果默认 Velocity 为零、蓝图覆盖了相关属性，或枪口 +X 不对，效果可能不同，应检查实际初始速度和旋转。

本节重力缩放为零，且没有其他加速度或寻的配置时，子弹基本沿初始方向直线飞行。以后添加重力或寻的，需要重新考虑轨迹。

### 6.6 首次出现：InitialLifeSpan

```cpp
InitialLifeSpan = 5.0f;
```

这是 Actor 的初始生存时间，单位是秒。子弹进入游戏后的生命周期计时达到约 5 秒，会自动请求销毁。它不是武器射速或两次开火的间隔。

运行中需要调整寿命时可以使用 `SetLifeSpan()`，但当前代码只设置初始值。零寿命通常表示不启用自动寿命销毁，不代表生成后立即销毁。

```text
先碰到物体 → 命中回调主动 Destroy
一直没碰到 → 生存时间到期自动销毁
```

有了超时清理，朝空中连续开火不会让所有未命中的子弹无限留在世界里。

## 7. 子弹命中：事件绑定、回调与销毁

### 7.1 在头文件中声明命中回调

```cpp
protected:
    UFUNCTION()
    void OnProjectileHit(
        UPrimitiveComponent* HitComponent,
        AActor* OtherActor,
        UPrimitiveComponent* OtherComponent,
        FVector NormalImpulse,
        const FHitResult& Hit
    );
```

#### 首次出现：UFUNCTION 与动态委托

`UFUNCTION()` 让 UE 的反射系统认识这个函数。本节的 `OnComponentHit` 是动态多播委托，使用 `AddDynamic` 绑定时，接收函数需要按相应要求声明为 UFUNCTION，并使用匹配的参数签名。

它没有写 `BlueprintCallable`，所以不能仅因为加了 `UFUNCTION()` 就认为蓝图事件图可以任意调用它。

与第一节的原生成员函数形式 `BindAction` 相比，这是另一种绑定机制，不能照搬“所有输入回调都必须加 UFUNCTION”的结论。

委托可以先理解为通知机制：组件负责在事件发生时发出通知，我把自己的处理函数登记进去，之后由它调用。多播表示可以登记多个接收者。

### 7.2 在 BeginPlay 中登记命中处理函数

```cpp
void AMyProjectile::BeginPlay()
{
    Super::BeginPlay();

    CollisionComponent->OnComponentHit.AddDynamic(
        this,
        &AMyProjectile::OnProjectileHit
    );
}
```

#### 首次出现：OnComponentHit 与 AddDynamic

可以把这一句读成：

```text
CollisionComponent → 哪个组件提供通知：子弹的碰撞球
OnComponentHit     → 什么通知：发生阻挡命中
AddDynamic        → 登记一个动态回调
this              → 在哪一个对象上执行：当前子弹
OnProjectileHit   → 执行哪个函数
```

登记时没有发生撞击，也不是立即执行一次 `OnProjectileHit()`。之后满足阻挡命中条件时，事件携带碰撞参数调用已经登记的函数。

OnComponentHit 与 Overlap 是不同事件：阻挡命中看 Hit，重叠进入看 Overlap。本节采用的是球体扫掠移动中的阻挡碰撞。

物理模拟产生的命中通知与移动扫掠产生的通知也要区分。**Simulation Generates Hit Events** 针对物理模拟命中，不能把勾选它当成所有 ProjectileMovement 命中问题的唯一解决办法。先检查是否有有效扫掠、阻挡响应、正确的 UpdatedComponent 和事件绑定。可参考 [On Component Hit 官方说明](https://dev.epicgames.com/documentation/en-us/unreal-engine/BlueprintAPI/Collision/OnComponentHit)。

### 7.3 命中回调的五个参数

| 参数 | 可以先这样理解 |
| --- | --- |
| `HitComponent` | 收到这次通知的本方组件，本节通常是 CollisionComponent |
| `OtherActor` | 撞到的另一个 Actor |
| `OtherComponent` | 对方具体被碰到的组件 |
| `NormalImpulse` | 法线方向相关的物理冲量；扫掠阻挡碰撞中通常为零 |
| `Hit` | 更完整的命中信息，例如撞击点、法线、是否阻挡命中 |

`UPrimitiveComponent` 是具有渲染或碰撞等能力的场景组件基类，Sphere、StaticMesh 等都属于它的派生类型，所以回调可以用这个基类接收不同组件。

#### 首次出现：FHitResult

第一节 `Landed()` 已经接收过这个类型，本节开始实际理解它携带的碰撞信息：

- `Hit.ImpactPoint`：撞击位置，之后可以用于生成命中特效。
- `Hit.ImpactNormal`：撞击表面法线，之后可以用于决定特效朝向。
- `Hit.bBlockingHit`：是否记录了阻挡命中。

本节回调暂时没有读取这些字段。它们不是伤害数值，收到 Hit 也不会自动让敌人扣血。

### 7.4 最新命中处理：判断敌人、传递伤害、销毁子弹

在 `MyProjectile.cpp` 顶部包含敌人类的完整定义：

```cpp
#include "MyEnemyCharacter.h"
```

```cpp
void AMyProjectile::OnProjectileHit(
    UPrimitiveComponent* HitComponent,
    AActor* OtherActor,
    UPrimitiveComponent* OtherComponent,
    FVector NormalImpulse,
    const FHitResult& Hit
)
{
    if (AMyEnemyCharacter* Enemy = Cast<AMyEnemyCharacter>(OtherActor))
    {
        Enemy->TakeProjectileDamage(Damage);
    }

    Destroy();
}
```

这一段要按三个步骤读：

```text
OtherActor：本次碰撞实际撞到的 Actor
↓
Cast<AMyEnemyCharacter>：它是不是我的敌人类型？
├─ 是 → Enemy->TakeProjectileDamage(Damage)
└─ 否 → 不执行敌人受伤函数
↓ 两条分支最后都走到这里
Destroy()：销毁当前子弹
```

#### 首次重点使用：Cast<T>

`OtherActor` 的静态类型是 `AActor*`。墙、玩家、敌人都可以是 Actor，但并非都具有 `TakeProjectileDamage()`。

```cpp
if (AMyEnemyCharacter* Enemy = Cast<AMyEnemyCharacter>(OtherActor))
```

它检查对象是否为 `AMyEnemyCharacter` 或其派生类实例。`BP_MyEnemyCharacter` 继承这个 C++ 类，因此转换可以成功；普通墙体转换失败，得到空指针。

这不会创建新敌人，也不会把墙变成敌人；成功时只是通过更具体的类型引用同一个对象。这里的 `Enemy` 在这个 if 的作用域中使用。

#### TakeProjectileDamage 是自己写的函数

```cpp
Enemy->TakeProjectileDamage(Damage);
```

这不是引擎自动提供的伤害 API，而是第三节在 `AMyEnemyCharacter` 中实现的普通成员函数。子弹告诉敌人“受到多少伤害”，敌人负责自己的血量和死亡判断。

当前调用传入 `Damage`，没有传入攻击者，也没有使用 `UGameplayStatics::ApplyDamage`、`TakeDamage`、伤害类型或击杀统计。因此虽然 Spawn 时保存了 Instigator，当前扣血函数还没有使用它来追踪击杀来源。

以敌人最大血量 100、子弹伤害 25 为例：

```text
第一次命中：100 → 75
第二次命中： 75 → 50
第三次命中： 50 → 25
第四次命中： 25 →  0 → 敌人 Destroy()
每次命中后，当前子弹也都会 Destroy()
```

这是四次成功命中的示例，不是点击四次就一定击杀；敌人血量和子弹伤害也可能被蓝图覆盖。

#### 两个 Destroy 分别销毁谁

| 执行位置 | 当前 this | 销毁的对象 |
| --- | --- | --- |
| 子弹的 `OnProjectileHit()` | 当前子弹 | 这一颗 Projectile |
| 敌人的 `TakeProjectileDamage()` | 被命中的敌人 | 血量归零的 Enemy |

Actor 销毁由 UE 生命周期管理，不应写成 `delete this`。请求 `Destroy()` 也不表示这一行执行后内存立即释放。

当前子弹碰到非敌人时，同样会执行最后的 `Destroy()`。所以“没有造成敌人伤害”不等于“子弹没发生碰撞”。

### 7.5 命中日志：区分当前代码与临时调试代码

最新 `OnProjectileHit()` 已没有旧版的通用 `Projectile Hit` 日志。命中敌人时，日志来自敌人的 `TakeProjectileDamage()`；命中墙或玩家时，可能直接销毁而不输出敌人受伤日志。

排查“子弹刚生成就消失”时，可以临时在命中回调开头加入：

```cpp
UE_LOG(
    LogTemp,
    Warning,
    TEXT("Projectile Hit: %s"),
    *GetNameSafe(OtherActor)
);
```

这段是调试建议，不是当前源码中已经存在的实现。也可以给 `OnProjectileHit()` 设置断点，直接查看 `OtherActor` 和 `OtherComponent`。

`GetNameSafe()` 获取对象名并处理空对象情况；它返回 FString，前面的 `*` 用于取得 `%s` 所需的字符指针，不是在解引用 OtherActor。`Warning` 是选用的日志级别，不代表命中本身是错误。

## 8. 整条执行链：用具体操作走一遍

### 8.1 开始 Play：角色装备默认武器

```text

↓
角色进入游戏，BeginPlay 初始化血量并启用输入映射
↓
DefaultWeaponClass 已在蓝图中指定为 BP_MyWeapon
↓
准备 FActorSpawnParameters
Owner = Character，Instigator = Character
↓
读取相机世界位置、世界旋转
↓
UWorld::SpawnActor<AMyWeapon>()
↓
生成武器，初始化它的组件与蓝图配置
↓
返回指针，保存到 CurrentWeapon
↓
确认武器生成成功
↓
AttachToComponent：武器根组件挂到相机
↓
SetActorRelativeLocation：添加前、右、下的偏移
```

输入映射启用与操作绑定也必须完成；它们属于准备阶段，不要把这张图当作 BeginPlay 与所有输入初始化回调的严格时序表。

### 8.2 点一下左键：生成一颗子弹

```text

↓
已经启用的 IMC_Player 找到 Left Mouse Button → IA_Fire
↓
当前默认 Trigger 行为下，操作开始：Started
↓
增强输入组件找到之前登记的绑定
↓
调用当前角色的 FireInput(Value)
↓
IsValid(CurrentWeapon)
↓ 可用
CurrentWeapon->Fire()
↓
检查 ProjectileClass 和 MuzzleLocation
↓
准备生成参数
Owner = Weapon，Instigator = Character
↓
读取枪口世界位置、世界旋转
↓
SpawnActor<AMyProjectile>(BP_MyProjectile, 枪口位置, 枪口旋转, 参数)
↓
创建子弹及组件，应用蓝图默认配置
↓

↓
子弹生成完成，进入后续的移动更新
```

这是正常、非延迟生成与现有代码下的主线示意。类默认对象、蓝图构造和具体引擎生命周期还有更多步骤，不必把“SpawnActor 内部发生的所有过程”机械简化成单次普通函数调用。

### 8.3 子弹命中墙面：从移动到销毁

```text
ProjectileMovement 的组件 Tick
↓
按当前速度与时间步长移动 UpdatedComponent
↓
UpdatedComponent 是根球体 CollisionComponent
↓
沿移动路径执行扫掠碰撞检查
↓
与墙面的组件形成阻挡命中
↓
CollisionComponent 发出 OnComponentHit 通知
↓
动态委托调用本子弹的 OnProjectileHit(...)
↓
OtherActor 指向被击中的墙面 Actor
↓
Cast<AMyEnemyCharacter>(OtherActor) 失败：墙体不是敌人
↓
跳过敌人受伤函数，不输出敌人伤害日志
↓
Destroy() 请求销毁当前子弹
```

“通知发生”与“我处理通知的函数”是两个环节。没有绑定，自己的回调不会因此自动执行；只有绑定但没有有效命中，也不会凭空产生回调。

### 8.4 子弹命中敌人：从输入到击杀的整条链

```text
左键 → IA_Fire Started → Character::FireInput
↓
CurrentWeapon->Fire → 从枪口 SpawnActor<AMyProjectile>
↓
ProjectileMovement 移动根碰撞球并进行扫掠
↓
撞到 BP_MyEnemyCharacter 的阻挡组件
↓
OnComponentHit → Projectile::OnProjectileHit
↓
Cast<AMyEnemyCharacter>(OtherActor) 成功
↓
Enemy->TakeProjectileDamage(Damage)
↓
Enemy 的 CurrentHealth -= Damage，输出受伤日志
├─ 血量 > 0：敌人继续存在
└─ 血量 <= 0：输出 Enemy Dead，销毁敌人
↓ 受伤函数返回
Projectile::OnProjectileHit 执行 Destroy，销毁子弹
```

血量计算是显式函数调用，不是 OnComponentHit 自带的行为。敌人受伤函数在第三节展开。

### 8.5 子弹没有命中：超时清理

```text
子弹持续飞行
↓
没有阻挡命中，未调用主动 Destroy
↓
初始生存时间约 5 秒到期
↓
UE 请求销毁子弹
```

主动命中销毁与寿命到期清理是两条不同结束路径。

### 8.6 用一张“脑图”把系统连起来

```text

           ↓

           ↓
```

## 9. 蓝图资源与编辑器配置

### 9.1 本项目的资源位置

```text
Content/
├─ Input/
│  ├─ IA_Fire
│  └─ IMC_Player
└─ BluePrints/
   ├─ BP_MyArenaShooterCharacter

      ├─ BP_MyWeapon
      └─ BP_MyProjectile
```

这些蓝图分别继承自己的 C++ 类。C++ 决定基本行为，蓝图指定资源和默认参数。

### 9.2 各个蓝图要填写什么

| 蓝图或资产 | 要配置的内容 |
| --- | --- |
| `IA_Fire` | Value Type：Digital / Bool |
| `IMC_Player` | Left Mouse Button 映射到 IA_Fire |
| `BP_MyArenaShooterCharacter` | Fire Action = IA_Fire；Default Weapon Class = BP_MyWeapon |
| `BP_MyWeapon` | Projectile Class = BP_MyProjectile；配置匹配类型的模型；调整枪口位置与旋转 |
| `BP_MyProjectile` | ProjectileMesh 指定外观；确认碰撞球、ProjectileMovement 和 Damage 默认值 |

编辑后编译并保存蓝图。只创建资源但没有在相关属性中赋值，代码不会根据相似名称自动找到它们。

武器的可视模型和子弹模型不是强制完成生成链的前提，但没有设置模型时，容易出现“日志显示生成了，画面却看不到”的现象。可以在 Play 的场景大纲中辅助确认实例。

### 9.3 头文件依赖与代码片段的放置

本文展示的是当前类里的成员和函数片段，不需要重复创建第二个同名类或同名 BeginPlay。

使用具体组件 API 时，`.cpp` 应包含对应定义。例如武器实现可显式包含：

```cpp
#include "Components/SceneComponent.h"
#include "Components/SkeletalMeshComponent.h"
#include "Engine/World.h"
```

角色中使用 `UWorld::SpawnActor` 也可以显式包含 `Engine/World.h`。不要把本机预编译头或其他文件间接包含了某个类型，当成永远不需要直接依赖声明的保证。

每个类自己的 `.generated.h` 仍放在该头文件最后一个 `#include` 位置。源码构造函数、组件或反射属性发生变化后，若编辑器中出现旧默认值，可保存资产、关闭编辑器、完整编译再重开确认。

## 10. 按执行链排查问题

### 10.1 不要一次修改所有地方

```text
射击输入有没有进入 FireInput？
↓
CurrentWeapon 是否可用？
↓
Fire 是否执行？
↓
子弹 SpawnActor 是否成功？
↓
子弹是否有有效初始速度？
↓
移动碰撞是否产生 Hit？
↓
命中回调是否登记并执行？
```

沿这条链逐段确认，比看到“没子弹”就同时改输入、模型、碰撞和速度更容易定位。

| 现象 | 优先检查 |
| --- | --- |
| Play 后没有武器实例 | DefaultWeaponClass 是否指定，SpawnActor 是否成功，角色是否使用正确蓝图 |
| 武器实例存在但看不到 | 是否配置模型、模型类型是否匹配、偏移和缩放是否合适 |
| 点左键没有任何反应 | IA_Fire 是否进入已启用 IMC，角色 FireAction 是否赋值，Started 是否绑定，视口是否取得焦点 |
| FireInput 执行但不进入 Fire | CurrentWeapon 是否为有效的已生成对象 |
| Fire 执行但没有子弹实例 | ProjectileClass 是否赋值，生成返回值是否为空，枪口变换和出生碰撞设置是否合适 |
| 子弹实例存在但看不到 | ProjectileMesh 是否指定，模型尺寸、出生位置和寿命是否合适 |
| 子弹不飞 | UpdatedComponent、InitialSpeed、初始 Velocity、组件激活状态、是否开启了物理模拟 |
| 子弹方向不对 | 枪口的世界旋转与局部 +X，模型自身朝向，蓝图是否覆盖局部初始速度设置 |
| 子弹穿墙 | 双方碰撞响应，根球体碰撞是否启用，ProjectileMovement 是否扫掠正确组件，回调是否绑定；当前没有通用命中日志 |
| 子弹出生后立即消失，或移动射击时角色抽搐 | 枪口是否位于玩家胶囊内；在命中回调断点或临时日志中确认撞到谁 |
| 子弹命中 Enemy 但不扣血 | OtherActor 是否真是 AMyEnemyCharacter 派生实例，Cast 是否成功，Damage 是否为零，是否运行最新编译版本 |
| 一直按住左键只有一次射击 | 当前绑定 Started，这是本节按次触发的结果 |

这些是复现时的排查方向，不表示当前项目已经出现了所有这些问题。

### 10.2 实际排查案例：移动时射不出子弹，并伴随抽搐

本次学习中出现的现象是：按 A 或 S 加鼠标可以射击，按 W 或 D 加鼠标看不到子弹，并且角色会抽搐。检查重点从输入转到子弹与发射者的自碰撞：子弹可能已经生成，却立刻被自己胶囊阻挡并销毁；角色移动检测也可能碰到刚生成的子弹。

当前球体设置对所有通道 Block。设置 Owner、Instigator 只保存归属和发起者，并不会自动忽略玩家碰撞。最新 C++ 仍没有加入 `IgnoreActorWhenMoving()`，也没有 EndPlay 清理忽略列表。

#### 这次先采用的思路：调整蓝图里的枪口距离

```text
打开 BP_MyWeapon
↓
选中 MuzzleLocation
↓
细节 → 变换 → 相对位置
↓
沿局部 +X 向前调整，例如 X = 50 cm
↓
编译、保存 → Play 测试站立及 WASD 移动射击
```

这不是修改玩家胶囊半径，也不是改变子弹速度。修改的是子弹出生点；`Fire()` 下一次读取枪口世界位置时就会使用调整后的变换。50 cm 是本次说明用的调试值，实际位置以蓝图参数和模型为准，不把它写成 C++ 已硬编码的默认值。

在角色、相机、武器方向一致，平视、默认缩放且 WeaponMesh 未额外偏移的条件下：

```text
相机相对角色：(-10, 0, 60)
武器相对相机：( 30,10,-10)
枪口相对模型：( 50, 0,  0)
→ 枪口相对角色约为：(70,10,50)
```

默认角色胶囊半径为 34 cm，这个平视出生点在胶囊体外。这个加法只是当前条件下的理解例子；转动后应使用组件世界变换，不能把相对坐标永远直接相加。

#### 距离调整能解决什么，还有什么限制

把枪口前移可以解决当前出生点过近的情况，但它仍随相机旋转；大幅俯视、贴墙时需要再次观察。枪口过远也可能穿到墙后，让子弹从墙另一侧出生。

后续更完整的方案是让子弹与发射者双方的移动碰撞互相忽略，并处理出生位置和近墙行为。当前尚未在源码中实现这一步。只在 OnProjectileHit 中 return，也不能撤销已经发生的阻挡或恢复已被停止的 ProjectileMovement。

不要简单把整个 Pawn 通道改成 Ignore：玩家和 Enemy 都是 Pawn，可能因此重新让子弹穿过敌人。排查时保持敌人碰撞规则，针对发射者处理。

### 10.3 Enemy 的模型与碰撞体是不同对象

Enemy 继承 ACharacter，通常主要由 CapsuleComponent 负责角色移动碰撞。网格看起来被穿过，不等于角色胶囊必然失效；要确认实际命中区域，以及子弹球与 Enemy 胶囊双方的响应。

敌人没有显示模型，也不表示胶囊不能阻挡子弹。本次使用胶囊完成命中就能进入受伤链；精确到身体部位的碰撞、骨骼命中和爆头是后续内容。

## 12. 后续学习记录：从点按单发升级到持续射击

前面的第 1～11 节保留最初学习时一步步实现的单发流程：IA_Fire 的 Started → FireInput → 武器 Fire → 生成一颗子弹。它是理解职责、枪口、生成与碰撞的基础，不需要因为现在有连发就删掉。

这一阶段在原有代码上增加“意图 + 条件 + 执行”：玩家按住表示想开火，武器判断冷却、换弹和弹药是否允许，再调用内部 Fire 完成一发。不是推翻原来的子弹飞行与碰撞，而是在原有单发行为外面增加控制。

| 学习阶段 | 当时实现 | 新增理由 |
| --- | --- | --- |
| 前面的基础单发 | 一次 Started 直接调用 FireInput / Fire | 先打通从输入到生成与命中的链 |
| 现在的持续射击 | Started 开始、Completed 停止，武器 Tick 控制后续发射 | 区分按住意图和每一发实际执行 |
| 射击间隔 | FireInterval 配置，FireCooldown 逐帧递减 | 控制射速，快速点按也不能直接绕过 |
| 弹药与换弹 | 弹匣、备用、换弹状态、一次性定时器 | 有限弹药，等待完成后从库存转移 |
| 弹药 UI | 武器通知角色，再转发 HUD | 让实际弹药变化成为屏幕文字 |

当前 C++ 默认弹匣 30 发、备用 90 发、射击间隔 0.15 秒、换弹耗时 1.5 秒，蓝图可以覆盖。下面记录这一阶段的代码；对照前面的旧版函数理解新增步骤，不把两个阶段的同名函数同时复制进项目。

## 13. 先补武器的数据与初始化

### 13.1 武器的成员声明：先区分配置、运行数据和状态

在 `MyWeapon.h` 中前置声明 `USceneComponent`、`USkeletalMeshComponent`、`AMyProjectile`。以下是已有类内部的成员整理，空的访问区段省略：

```cpp
private:
    UPROPERTY(VisibleAnywhere, Category = "Weapon")
    USceneComponent* Root;

    UPROPERTY(VisibleAnywhere, Category = "Weapon")
    USkeletalMeshComponent* WeaponMesh;

    UPROPERTY(VisibleAnywhere, Category = "Weapon")
    USceneComponent* MuzzleLocation;

    UPROPERTY(EditDefaultsOnly, Category = "Weapon")
    TSubclassOf<AMyProjectile> ProjectileClass;

    UPROPERTY(EditDefaultsOnly, Category = "Weapon")
    float FireInterval = 0.15f;
    bool bFirePressed = false;
    float FireCooldown = 0.0f;

    UPROPERTY(EditDefaultsOnly, Category = "Ammo")
    int32 MagazineSize = 30;

    UPROPERTY(EditDefaultsOnly, Category = "Ammo")
    int32 StartingReserveAmmo = 90;

    UPROPERTY(EditDefaultsOnly, Category = "Ammo")
    float ReloadTime = 1.5f;

    int32 CurrentAmmo = 0;
    int32 ReserveAmmo = 0;
    bool bIsReoloading = false;
    FTimerHandle ReloadTimerHandle;

public:
    AMyWeapon();
    virtual void Tick(float DeltaTime) override;
    void StartFire();
    void StopFire();
    void StartReload();

    int32 GetCurrentAmmo() const { return CurrentAmmo; }
    int32 GetReserveAmmo() const { return ReserveAmmo; }

protected:
    virtual void BeginPlay() override;

private:
    void Fire();
    void FinishReload();
    void UpdateAmmoHUD();
```

| 分类 | 成员 | 要解决的问题 |
| --- | --- | --- |
| 空间与资源 | Root、WeaponMesh、MuzzleLocation、ProjectileClass | 枪以谁为根、显示什么、从哪发射、生成什么子弹 |
| 可配置规则 | FireInterval、MagazineSize、StartingReserveAmmo、ReloadTime | 两发间隔、弹匣容量、初始备用数量、换弹用时 |
| 当前数据 | CurrentAmmo、ReserveAmmo、FireCooldown | 现在剩多少弹药、距离允许下一发还剩多久 |
| 行为状态 | bFirePressed、bIsReoloading | 玩家是否仍按住、武器是否正在换弹 |
| 定时器标识 | ReloadTimerHandle | 标识这次安排的换弹定时器 |

配置回答“规则是什么”，运行数据回答“现在是多少”，状态回答“当前是否允许做这件事”。例如 MagazineSize 一直为 30，CurrentAmmo 会从 30 降到 29；StartingReserveAmmo 为开局配置，ReserveAmmo 会随换弹减少。

`bIsReoloading` 保留当前源码拼写；它是“正在换弹”的 bool，不是 UE API。笔记与现有声明、判断保持一致。`Fire()` 现在是 private，角色从公开的开始、停止与换弹入口提出请求，武器自己决定能否生成下一颗子弹。

两个 getter 的返回类型为 int32，末尾 const 表示读取时不修改武器自身成员。角色通过它们取得初始弹药，不需要把 CurrentAmmo 改成 public。`CreateDefaultSubobject`、`SetupAttachment`、`UPROPERTY` 已在第一节出现。

### 13.2 与最初不同：武器现在需要开启 Tick

```cpp
PrimaryActorTick.bCanEverTick = true;
```

前面的构造函数记录了 false：当时武器只在角色回调中完成一次 Fire，不需要每帧处理。现在增加 FireCooldown 倒计时和按住连射，因此将武器 Tick 改为 true；Root、WeaponMesh、MuzzleLocation 的组件结构继续沿用。

子弹 Actor 的 Tick 仍然为 false，飞行由 ProjectileMovement 组件更新。武器 Tick 管“何时生成下一颗”，移动组件管“已生成的一颗如何飞行”。

### 13.3 BeginPlay：将蓝图最终配置转成开局弹药

```cpp
void AMyWeapon::BeginPlay()
{
    Super::BeginPlay();

    CurrentAmmo = MagazineSize;
    ReserveAmmo = StartingReserveAmmo;
}
```

构造函数建立默认规则与组件，BeginPlay 给当前武器实例装入弹匣与备用弹药。蓝图把 MagazineSize 改成20时，CurrentAmmo从20开始；之后射击修改当前数据，不改容量配置。

这个函数没有直接刷新 HUD。角色在正常生成、保存并挂载武器后读取 getter，发送第一次弹药显示；后续变化由武器主动通知。

## 14. 输入只表达操作意图：开始、停止和请求换弹

### 14.1 角色保存输入资产并声明回调

这一阶段把原来的单个 FireInput 回调扩展为 StartFireInput、StopFireInput，并新增 ReloadInput。笔记保留旧版过程；当前项目的输入绑定使用下面的新入口。

`IA_Fire` 使用 Digital / Bool，在现有 IMC_Player 中映射左键。新增 `IA_Reload` 后也要加入这个 Mapping Context，并给角色类默认值的 ReloadAction 赋值。具体换弹键以自己在 IMC 中的设置为准。

```cpp
private:
    UPROPERTY(EditDefaultsOnly, Category = "Input")
    UInputAction* FireAction = nullptr;

    UPROPERTY(EditDefaultsOnly, Category = "Input")
    UInputAction* ReloadAction = nullptr;

public:
    void StartFireInput(const FInputActionValue& Value);
    void StopFireInput(const FInputActionValue& Value);
    void ReloadInput(const FInputActionValue& Value);
```

这些成员放在现有玩家类里，仍使用第一节已启用的增强输入子系统，不另建一个输入系统。

### 14.2 Started 记录按下，Completed 记录松开

以下摘自 SetupPlayerInputComponent 的 EnhancedInputComponent 判定内部，与其他操作绑定并列：

```cpp
if (FireAction)
{
    EnhancedInputComponent->BindAction(
        FireAction,
        ETriggerEvent::Started,
        this,
        &AMyArenaShooterCharacter::StartFireInput
    );

    EnhancedInputComponent->BindAction(
        FireAction,
        ETriggerEvent::Completed,
        this,
        &AMyArenaShooterCharacter::StopFireInput
    );
}

if (ReloadAction)
{
    EnhancedInputComponent->BindAction(
        ReloadAction,
        ETriggerEvent::Started,
        this,
        &AMyArenaShooterCharacter::ReloadInput
    );
}
```

按当前 Digital 默认触发行为理解：Started 在左键按下时进入开始回调，Completed 在释放结束时进入停止回调。持续按住期间，不靠 Started 重复执行，而是让武器保存状态并逐帧判断。若之后给 Input Action 添加 Hold 等 Trigger，需要重新核对 Started、Completed 和 Canceled 的触发语义，不能照搬成所有配置都等于按下与松开。

### 14.3 角色把请求转交给已有武器

```cpp

{
    if (bIsDead)
    {
        return;
    }

    if (IsValid(CurrentWeapon))
    {
        CurrentWeapon->StartFire();
    }
}
```

```cpp
void AMyArenaShooterCharacter::StopFireInput(const FInputActionValue& Value)
{
    if (IsValid(CurrentWeapon))
    {
        CurrentWeapon->StopFire();
    }
}
```

```cpp
void AMyArenaShooterCharacter::ReloadInput(const FInputActionValue& Value)
{

    {
        return;
    }

    {
        CurrentWeapon->StartReload();
    }

```

开始射击和手动换弹先检查 bIsDead，死亡后不接收新的这类请求。StopFireInput 没有死亡判断，因此松开仍可把停止请求交给武器。三个函数不需要读取 Value 的数值，操作时机已经由事件类型表达。

```text
StartFireInput：角色存活 + 武器有效 → 武器.StartFire
StopFireInput：武器有效 → 武器.StopFire
ReloadInput：角色存活 + 武器有效 → 武器.StartReload
```

角色知道“玩家做了什么”，武器知道“现在能不能做”。角色不负责减少弹药，也不自行计算换弹所需数量。

#### 沿用已学：IsValid 与武器内部条件

`IsValid(CurrentWeapon)` 判断 UE 对象引用是否可用，不仅检查非空，还检查待销毁等状态。它不是任意 C++ 指针的通用修复工具，应在对象引用由 UE 正常管理的前提下使用。

这里要分两层判断：角色检查武器实例有效；武器再检查换弹状态、弹药和射击间隔。有效的武器不代表这次请求一定立刻生成子弹。

## 15. 在原有单发执行外加入状态控制、弹药和换弹

### 15.1 当前 Fire：完成一发射击，并处理弹药后续

MyWeapon.cpp 包含 MyProjectile.h 与 MyArenaShooterCharacter.h。先看武器内部“完成一发”的实现，开始、停止和持续射击控制在后面展开：

```cpp
void AMyWeapon::Fire()
{
    if (bIsReoloading)
    {
        return;
    }

    if (CurrentAmmo <= 0)
    {
        StartReload();
        return;
    }

    if (!MuzzleLocation || !ProjectileClass)
    {
        return;
    }

    FActorSpawnParameters SpawnParams;
    SpawnParams.Owner = this;
    SpawnParams.Instigator = GetInstigator();

    GetWorld()->SpawnActor<AMyProjectile>(
        ProjectileClass,
        MuzzleLocation->GetComponentLocation(),
        MuzzleLocation->GetComponentRotation(),
        SpawnParams
    );

    --CurrentAmmo;

    UpdateAmmoHUD();

    if (CurrentAmmo <= 0)
    {
        StartReload();
    }
}
```

执行顺序为：换弹中直接返回 → 弹匣为空则尝试换弹并返回 → 检查枪口和子弹类 → 从枪口生成 → 弹匣减一 → 刷新 HUD → 若刚打空则自动开始换弹。

`ProjectileClass` 仍是 `TSubclassOf<AMyProjectile>`，蓝图中指定 BP_MyProjectile。`--CurrentAmmo` 只减当前弹匣，备用弹药要在完成换弹时才转移。

当前没有保存 SpawnActor 的返回值，所以只要走过这次生成调用，就会继续扣一发；生成失败也可能表现为弹药减少而没有子弹。不能把现有代码记成“确认生成成功后才扣弹药”。Fire 内部没有再次判断 FireCooldown，冷却判断在 StartFire 和 Tick 中完成；现在外部角色也不直接调用这个 private 函数。

### 15.2 StartFire 与 StopFire：为什么先保存状态

```cpp
void AMyWeapon::StartFire()
{
    bFirePressed = true;

    if (bIsReoloading)
    {
        return;
    }

    if (CurrentAmmo <= 0)
    {
        StartReload();
        return;
    }

    if (FireCooldown <= 0.0f)
    {
        Fire();
        FireCooldown = FireInterval;
    }
}
```

```cpp
void AMyWeapon::StopFire()
{
    bFirePressed = false;
}
```

StartFire 一进入就将 bFirePressed 设为 true，再检查是否正在换弹、弹匣是否为空、冷却是否结束。这个顺序表示“玩家想继续开火”，与“这一刻允许开火”是两件事。

```text
玩家按住左键：
    记住：现在仍想开火
    如果正在换弹：暂时不射，保留按住状态
    如果弹匣为空：尝试换弹，本次不射
    如果冷却结束：立即完成首发，并重设冷却

玩家松开左键：
    清除按住状态
    以后 Tick 不再因按住状态自动开火
```

冷却未结束时 StartFire 不会提前射击；快速重复点击也受到同一个 FireCooldown 限制。StopFire 不销毁已经飞出的子弹、不清零冷却，也不取消已经开始的换弹定时器。

### 15.3 Tick 控制连射：意图、允许条件与执行分开

```cpp
void AMyWeapon::Tick(float DeltaTime)
{
    Super::Tick(DeltaTime);

    FireCooldown -= DeltaTime;

    if (FireCooldown < 0.0f)
    {
        FireCooldown = 0.0f;
    }

    if (bFirePressed && !bIsReoloading && FireCooldown <= 0.0f)
    {
        Fire();

        FireCooldown = FireInterval;
    }
}
```

可以按下面的伪代码理解：

```text
每帧：
    剩余冷却 -= 本帧经过的时间
    若小于0：归零

    同时满足“仍按住 + 没换弹 + 冷却结束”时：
        调用 Fire 尝试一发
        冷却重设为 FireInterval
```

三个判断通过 && 组合，必须同时成立。Fire 再检查弹药和资源，这就是 Tick 负责“何时尝试”，Fire 负责“一次尝试做什么”。即使 Fire 因资源缺失返回，调用它之后的 Tick 仍会重设冷却。

`DeltaTime` 是本帧经过的秒数。减去它，才是在扣时间；每帧减一个固定数会让射速随帧率改变。代码在没有按住、甚至换弹期间仍减少冷却，因为减法放在条件判断之前。

FireInterval = 0.15 表示两次尝试之间按倒计时控制间隔，理论连续射速约 1 / 0.15 = 6.67 发/秒。实际执行落在帧上，当前每帧至多发射一次，冷却归零后直接重设，低帧率时不会补发跨过的所有间隔。不要把它记成严格每秒固定生成 6.67 个 Actor。

武器必须保持 PrimaryActorTick.bCanEverTick = true。若沿用旧笔记关闭武器 Tick，按下时首发可能正常，后续冷却却无法继续递减，连射也不会发生。

### 15.4 StartReload：检查条件，只安排一次换弹

```cpp
void AMyWeapon::StartReload()
{
    if (bIsReoloading)
    {
        return;
    }

    if (CurrentAmmo >= MagazineSize)
    {
        return;
    }

    if (ReserveAmmo <= 0)
    {
        return;
    }

    bIsReoloading = true;

    UE_LOG(
        LogTemp,
        Warning,
        TEXT("Reloading...")
    );

    GetWorldTimerManager().SetTimer(
        ReloadTimerHandle,
        this,
        &AMyWeapon::FinishReload,
        ReloadTime,
        false
    );
}
```

为什么依次做三个提前返回？

| 条件 | 返回原因 |
| --- | --- |
| bIsReoloading 已经为 true | 已在等待，不重复安排换弹 |
| CurrentAmmo >= MagazineSize | 弹匣已满，不需要装弹 |
| ReserveAmmo <= 0 | 没有备用弹药可转移 |

全部通过后，先把换弹状态设为 true，再安排定时器。在等待期间 Fire、StartFire 和 Tick 的对应判断共同阻止射击，避免同一把枪一边换弹一边减少弹匣。

同一个入口有三种来源：角色手动 ReloadInput、StartFire 发现空弹匣、Fire 打出最后一发后发现弹匣归零。它们复用规则，不分别写三套换弹计算。

### 15.5 首次出现：GetWorldTimerManager、FTimerHandle、SetTimer

```cpp
GetWorldTimerManager().SetTimer(
    ReloadTimerHandle,
    this,
    &AMyWeapon::FinishReload,
    ReloadTime,
    false
);
```

| 参数 / API | 本次含义 |
| --- | --- |
| GetWorldTimerManager() | 取得所在世界的定时器管理器 |
| ReloadTimerHandle | 保存定时器的标识，便于以后查询或取消 |
| this | 到期时在哪个武器实例上执行回调 |
| &AMyWeapon::FinishReload | 要登记的成员函数，当前不是立即调用它 |
| ReloadTime | 等待时长，当前默认 1.5 秒 |
| false | 不循环，只在到期时回调一次 |

FTimerHandle 不是还剩几秒的 float，也不是换弹状态 bool。SetTimer 把后续工作交给引擎计时，StartReload 随即返回；等待期间游戏继续运行。这里没有用 sleep 阻塞，也没有在 Tick 里自己计算换弹剩余时间。

换弹标记还避免重复按键不断重设同一个定时器，导致完成时间一直往后延。这里使用对象成员函数形式，无需因为“回调”二字就添加 AddDynamic 或 UFUNCTION；子弹命中的动态委托是另一种机制。

ReloadTime 应为正数。UE 中给 SetTimer 传入小于等于 0 的间隔表示清除定时器，不是立刻完成换弹；本实现已先设 bIsReoloading = true，若这样配置会无法靠本次回调退出换弹。可以对照 [UE 5.4 定时器说明](https://dev.epicgames.com/documentation/en-us/unreal-engine/gameplay-timers-in-unreal-engine?application_version=5.4)。

### 15.6 FinishReload：从备用弹药转移，不凭空增加

```cpp
void AMyWeapon::FinishReload()
{
    int32 NeededAmmo = MagazineSize - CurrentAmmo;

    int32 AmmoToReload = FMath::Min(NeededAmmo, ReserveAmmo);

    CurrentAmmo += AmmoToReload;
    ReserveAmmo -= AmmoToReload;

    bIsReoloading = false;

    UpdateAmmoHUD();

}
```

首次出现的 `FMath::Min(A, B)` 取两者较小值。这里先算弹匣缺口，再选择“缺口和库存中较小的数量”作为本次装入数：

```text
缺口 = 弹匣容量 - 当前弹匣
装入数量 = min(缺口, 备用弹药)
当前弹匣 += 装入数量
备用弹药 -= 同样数量
退出换弹状态，通知 HUD
```

| 换弹前 CurrentAmmo / ReserveAmmo | 容量 | 缺口 | 装入 | 换弹后 |
| --- | --- | --- | --- | --- |
| 10 / 90 | 30 | 20 | 20 | 30 / 70 |
| 0 / 90 | 30 | 30 | 30 | 30 / 60 |
| 10 / 5 | 30 | 20 | 5 | 15 / 0 |

换弹前后的“弹匣 + 备用”总数不变；只有射击才消耗总弹药。若只把 CurrentAmmo 设为 MagazineSize 而不扣库存，就会无限补出子弹；若不取 Min，备用只剩 5 发时也会错误装入 20 发。

FinishReload 没有直接调用 Fire。若玩家始终按住，下次武器 Tick 在冷却结束且换弹标记已清除时继续射击；若已经松开，bFirePressed 为 false，换好后停在等待状态。

### 15.7 跨帧执行链：按住到打空，换好后继续

```text
左键 Started → StartFire：按住标记=true
↓ 冷却结束且有弹药
Fire：生成、弹匣减1、通知 HUD
↓ StartFire / Tick 重设冷却
后续 Tick：减时间 → 归零后下一发
↓ 最后一发
Fire：CurrentAmmo 变0 → HUD 显示0 / 备用 → StartReload
↓ 换弹标记=true，登记一次 FinishReload
等待期间：Tick 仍递减射击冷却，但换弹标记阻止射击
↓ 定时器到期
FinishReload：转移弹药 → 换弹标记=false → HUD 显示新弹药
├─ 左键仍按住：之后 Tick 允许时继续射击
└─ 期间松开：StopFire 清除按住标记，换好也不会自行开火
```

正常配置下 1.5 秒换弹比 0.15 秒射击间隔长，冷却通常已归零；但代码的条件始终是“冷却结束”，并不硬编码换好必定当场射击。按住键、等待冷却、等待换弹分别由不同数据表达。

### 15.8 弹药更新怎样送到 HUD

```cpp
void AMyWeapon::UpdateAmmoHUD()
{
    AMyArenaShooterCharacter* OwnerCharacter =
        Cast<AMyArenaShooterCharacter>(GetOwner());

    if (IsValid(OwnerCharacter))
    {
        OwnerCharacter->UpadteAmmoHUD(
            CurrentAmmo,
            ReserveAmmo
        );
    }
}
```

生成武器时已经设置 Owner = Character，所以 GetOwner() 可以取出角色。Cast 确认类型，IsValid 确认引用可用，再调用角色自己的转发入口：

```text
武器 Fire / FinishReload 修改 CurrentAmmo、ReserveAmmo
→ Weapon.UpdateAmmoHUD
→ GetOwner → Cast 为玩家角色
→ Character.UpadteAmmoHUD(弹匣余量, 备用数量)
→ HUDWidget.UpdateAmmo
→ AmmoText.SetText
```

`GetOwner()` 与 `GetInstigator()` 目的不同：前者在这里用于找到持有 HUD 的角色，后者继续把发起 Pawn 传给子弹。Owner 是生成时设置的 Actor 关系，不是去组件父节点里查找。

`UpdateAmmoHUD`、`UpadteAmmoHUD`、`UpdateAmmo` 都是项目自定义函数。中间的 Upadte 拼写保留源码；Widget 格式化和控件绑定详见第 4 节。当前开始换弹只输出 Reloading 日志，不会把 AmmoText 改成“换弹中”；数字在完成后刷新。

### 15.9 阅读当前代码时记住的行为边界

| 情况 | 当前代码的结果 |
| --- | --- |
| 弹匣已满时请求换弹 | StartReload 返回，不安排定时器 |
| 备用为0但弹匣还有子弹 | 仍可射击，暂时无法换弹 |
| 弹匣与备用都为0 | 不生成子弹，换弹入口也返回；按住仍会周期尝试 |
| 松开左键 | 停止后续连射，已经开始的换弹继续 |
| 子弹生成调用失败 | 当前没有返回值检查，仍可能扣弹药 |
| 死亡前已经按住左键 | Die 没有调用 StopFire，武器 Tick 也不检查角色死亡，已有按住状态可能继续射击 |

最后一行是当前实现尚未收齐的状态：StartFireInput 的死亡判断只能阻止新的开始请求，不会自动清除武器之前保存的 bFirePressed。后续可在 Die 里停止当前武器，并定义是否取消换弹；这些是待完善思路，笔记不把它写成已经存在的代码。


## 16. 本阶段的整条执行链、配置与复习

### 16.1 开局：先有 HUD，再读取武器初始弹药

前面的 BeginPlay 保留了当时生成武器的步骤。当前完整函数在这些步骤之前创建 HUD，并在武器成功生成与挂载后追加初始弹药转发：

```cpp
void AMyArenaShooterCharacter::BeginPlay()
{
    Super::BeginPlay();

    CurrentHealth = MaxHealth;

    if (HUDWidgetClass)
    {
        HUDWidget = CreateWidget<UMyHUDWidget>(
            GetWorld(),
            HUDWidgetClass
        );

        if (HUDWidget)
        {
            HUDWidget->AddToViewport();

            HUDWidget->UpdateHealth(CurrentHealth, MaxHealth);
        }
    }

    if (APlayerController* PlayerController = Cast<APlayerController>(Controller))
    {
        if (UEnhancedInputLocalPlayerSubsystem* Subsystem =
            ULocalPlayer::GetSubsystem<UEnhancedInputLocalPlayerSubsystem>(
                PlayerController->GetLocalPlayer()
            ))
        {
            if (DefaultMappingContext)
            {
                Subsystem->AddMappingContext(DefaultMappingContext, 0);
            }
        }
    }

    if (DefaultWeaponClass)
    {
        FActorSpawnParameters SpawnParams;

        SpawnParams.Owner = this;
        SpawnParams.Instigator = this;

        CurrentWeapon = GetWorld()->SpawnActor<AMyWeapon>(
            DefaultWeaponClass,
            FirstPersonCameraComponent->GetComponentLocation(),
            FirstPersonCameraComponent->GetComponentRotation(),
            SpawnParams
        );

        if (CurrentWeapon)
        {
            CurrentWeapon->AttachToComponent(
                FirstPersonCameraComponent,
                FAttachmentTransformRules::SnapToTargetIncludingScale
            );

            CurrentWeapon->SetActorRelativeLocation(
                FVector(30.0f, 10.0f, -10.0f)
            );

            UpadteAmmoHUD(
                CurrentWeapon->GetCurrentAmmo(),
                CurrentWeapon->GetReserveAmmo()
            );
        }
    }
}
```

正常非延迟 SpawnActor 在这个已开始游戏的调用位置会执行武器 BeginPlay；弹药初始化之后，角色读取 GetCurrentAmmo / GetReserveAmmo。所以蓝图配置改变后显示实际值，而不由 UI 写死30 / 90。若之后改成延迟生成，要重新检查这个初始化时机。

### 16.2 把输入、武器状态、子弹和 UI 连起来

```text
资源配置：角色指定武器类与输入资产，武器指定子弹类、射击和弹药参数
↓
准备：创建 HUD → 生成武器并初始化弹药 → 挂到相机 → 显示开局弹药
↓
输入
├─ Fire Started → StartFireInput → StartFire：记录按住并尝试首发
├─ Fire Completed → StopFireInput → StopFire：清除按住
└─ Reload Started → ReloadInput → StartReload：请求换弹
↓
武器 Tick：递减冷却 → 按住且未换弹且到期 → Fire
↓
Fire：检查状态、弹药、资源 → 生成子弹 → 扣弹匣 → 更新 HUD
├─ 弹匣打空：StartReload → 定时器 → FinishReload → 转移库存 → 更新 HUD
└─ 子弹独立飞行：ProjectileMovement 移动碰撞球
       ├─ 命中：OnProjectileHit → Enemy 则扣血 → 子弹销毁
       └─ 未命中：继续飞行 → LifeSpan 到期销毁

HUD 刷新：Weapon → 持有者 Character → HUDWidget → AmmoText
```

阅读代码时先找到“谁持有数据”，再找“谁修改数据”，最后找“修改后通知谁”。输入、射击间隔、换弹等待、子弹飞行、界面显示是衔接的几段，各自有明确入口。

### 16.5 与原来的单发流程对照复述

1. 原来 Started 直接完成单发；现在为什么先调用 StartFire，后续由谁重复执行 Fire？
2. 为什么 bFirePressed 要在换弹判断之前设为 true？松开为什么不取消换弹？
3. FireInterval、FireCooldown、ReloadTime、ReloadTimerHandle 分别表示什么？
4. 快速点按为什么仍受冷却限制？关闭武器 Tick 为什么会破坏这一阶段的射击？
5. 弹匣10、容量30、备用5，完成换弹为什么是15 / 0？换弹前后总弹药有没有改变？
6. 打空后一直按住，与打空后松开，换好后各会怎样？谁真正发出下一颗子弹？
7. 初始弹药和后续弹药分别由谁送给 HUD？数字减少能否证明子弹成功生成？

### 17.2 先分清相机查到谁与子弹撞到谁

### 17.3 子弹的局部初始方向现在明确写出来

```cpp
ProjectileMovement->bInitialVelocityInLocalSpace = true;
```

在Projectile构造函数中，与原来的InitialSpeed=3000配合：局部+X经生成旋转转换成世界速度，沿Fire计算的ShootDirection飞行。这让“射击方向 → Actor旋转 → 局部速度转世界速度”的链更明确。

### 17.4 本次从只前移枪口，进一步加入子弹忽略发起Pawn

```cpp
void AMyProjectile::BeginPlay()
{
    Super::BeginPlay();

    CollisionComponent->OnComponentHit.AddDynamic(this, &AMyProjectile::OnProjectileHit);

    if (IsValid(GetInstigator()))
    {
        CollisionComponent->IgnoreActorWhenMoving(
            GetInstigator(),
            true
        );
    }
}
```

此前笔记记录了先在蓝图前移MuzzleLocation解决出生点太近。本次开始在子弹主动移动的碰撞球上忽略GetInstigator；枪口位置仍按自己模型配置，不需要删除之前排查与调整过程。

这只设置子弹移动扫掠这一侧。相机QueryParams的忽略、子弹IgnoreActorWhenMoving和生成时AlwaysSpawn各解决不同步骤，不能当成同一个开关；当前也未把所有Pawn设为Ignore，所以Enemy仍可参与实际子弹碰撞。

### 17.5 本次新增的Effects资源

| 所属类 | 新增属性 | 当前用途 |
| --- | --- | --- |
| Weapon | MuzzleFlashEffect：UNiagaraSystem* | SpawnSystemAttached挂到MuzzleLocation |

### 17.6 本次生成结果与状态边界

当前Fire保存了SpawnedProjectile，并使用AlwaysSpawn，但没有根据返回值决定是否继续特效、声音、扣弹药。上一阶段的“生成失败也可能扣弹药”这一边界仍未消失；不要因为有了变量就记成“已经检查成功”。

当前每一发重新选点，已生成子弹不会持续追踪移动Enemy。10000单位是相机查询长度，不是硬限制子弹到这里必须停止。命中反馈来自实际Projectile碰撞，准星看中Enemy但子弹撞了近墙时不会显示Enemy命中标记。
