# Game Programming Patterns：对象池模式（Object Pool）核心笔记

## 一、 模式定义与核心价值

- **意图**：通过从固定池中重用对象，而不是单独分配和释放它们，来提高性能和内存使用率。

- **本质**：向内存管理器**预先一次性申请**大块连续内存，内部自建管理机制；对上层逻辑提供类似动态创建/销毁的接口。

- **核心价值**：
    - **消除内存碎片**：避免频繁 `new/delete` 将堆内存打碎成无用空洞。

    - **提高分配效率**：绕过通用的堆内存分配器，获得 $O(1)$ 欧阶的高效分配能力。

    - **平抑性能抖动**：将内存分配开销转移至初始化阶段，避免游戏运行中（如频繁生成粒子）产生 GC 骤停或分配卡顿。

## 二、 模式解决的经典痛点

1. **内存碎片化（Memory Fragmentation）**：连续的空闲内存被不规则分割，导致虽然总剩余内存足够，但无法分配出稍大的连续空间（在主机浸泡测试中易导致崩溃）。

2. **分配性能开销**：通用的堆内存分配算法（如查找合适大小的空闲块）非常耗时，不适合高频（如每帧成百上千次）创建的短生命周期对象。

3. **GC 压力**：在带垃圾回收的语言环境中，频繁产生临时对象会引发 GC 高频触发，导致严重的帧率波动。
## 三、 模式的核心权衡与风险

| **核心风险**       | **现象描述**                         | **应对策略**                                                                                           |
| -------------- | -------------------------------- | -------------------------------------------------------------------------------------------------- |
| **闲置内存浪费**     | 池大小按峰值预分配，极值过后闲置槽位持续占用内存。        | 精细调校池大小；按关卡/场景分别动态调整池容量。                                                                           |
| **池容量耗尽（溢出）**  | 活跃对象达到上限，无法继续创建新对象。              | 1. 调整池大小保证永远不溢出（用于关键游戏实体）；<br>2. 放弃创建（用于视觉粒子）；<br>3. 强行回收最不显著的已有对象（如替换最安静的音效）；<br>4. 运行时动态扩容（溢出池）。 |
| **数据残余（脏数据）**  | 回收对象时未彻底清理字段，新对象复用了上一代的残余状态。     | 在回收或重新初始化时强制重置所有字段；调试期使用魔数（如 `0xDEADBEEF`）清空槽位。                                                    |
| **多类型继承的空洞浪费** | 槽位必须按“最大可能子类”分配内存，存储较小对象时浪费空间。   | 按对象尺寸拆分成多个独立的固定尺寸池（内存管理器的基石做法）。                                                                    |
| **GC 悬挂引用**    | 在 GC 语言中，池未释放对象会导致其引用的外部对象无法被回收。 | 对象归还池时，**务必显式清空**其持有的所有外部对象引用（设为 `null`）。                                                          |

## 四、 核心数据结构与优化技巧：空闲列表（Free List）

### 1. 朴素实现 vs 空闲列表实现

- **朴素遍历法**：每次申请时遍历数组查找 `!inUse()` 的槽位，时间复杂度为 **$O(N)$**（池大且满时性能差）。
- **空闲列表法**：将所有未使用的槽位串联成链表，申请/归还仅需操作链表头，时间复杂度为 **$O(1)$**。
### 2. 零内存开销实现：利用 Union 复用内存

- **技巧**：未使用的对象不需要保存位置、速度等数据，可以利用指针重叠这部分内存。
- **数据结构设计**：
```C++
class Particle {
public:
    Particle* getNext() const { return state_.next; }
    void setNext(Particle* next) { state_.next = next; }
    bool inUse() const { return framesLeft_ > 0; }

private:
    int framesLeft_; // 用作生命周期标记
    union {
        // 使用时的存活数据
        struct {
            double x, y;
            double xVel, yVel;
        } live;

        // 未使用时的链表指针（拆用存活数据的内存）
        Particle* next;
    } state_;
};
```

## 五、 关键设计抉择

### 1. 对象与池的耦合度

- **耦合（对象知道池的存在）**：
    - **优点**：实现简单；可将构造函数私有化并声明池为友元，限制对象的创建途径；可直接利用对象内部状态（如 `inUse()`）判断活性。
    - **缺点**：缺乏通用性，无法复用到其他类型。
- **解耦（通用池，对象不知道池的存在）**：
    - **优点**：能够实现模板化/通用的 `GenericPool<T>`。
    - **缺点**：必须在池外部额外存储“使用中”标记（如位图 `bool inUse[POOL_SIZE]`），增加额外内存开销。
### 2. 重用对象的初始化责任

- **池内部初始化**：
    - **优点**：封装性好，外部代码无法拿到未初始化的野指针。
    - **缺点**：池需要提供并转发各种不同的 `init(...)` 参数重载接口。
- **外部代码初始化**：
    - **优点**：池接口极简（仅返回 `T* create()`）；调用者自由选择初始化方式。
    - **缺点**：需要外部代码显式处理池满返回 `NULL` 的空指针检查。
## 六、 模式对比

- **与享元模式（Flyweight）的区别**：
    - **享元模式**：强调在**同一时间**被多个拥有者**共享**同一份实例（空间复用）。
    - **对象池模式**：强调在**不同时间**被单一拥有者**先后**回收重用，生命周期内不共享（时间复用）。
