# Game Programming Patterns：观察者模式（Observer Pattern）核心笔记

## 一、 模式定义与核心价值

- **解耦（Decoupling）**：允许“发起者（Subject/Observerable）”在发生事件时发送通知，而无需知道“接收者（Observer）”是谁或具体做了什么。
- **一对多依赖关系**：当一个对象状态发生改变时，所有依赖于它的观察者对象都会得到通知并自动更新。
## 二、 经典实现结构与运作流程

1. **观察者接口（Observer）**：定义接收通知的纯虚函数（如 `onNotify(const Entity& entity, Event event)`）。
2. **被观察者/主题（Subject）**：  
    - 维护一个观察者指针列表（数组/单链表/ Vector）。
    - 提供注册/注销接口（`addObserver()`, `removeObserver()`）。
    - 触发事件时遍历列表并依次调用观察者的 `onNotify()`。
## 三、 模式的痛点与经典陷阱

| **经典痛点**                    | **现象描述**                              | **原书解决方案 / 应对策略**                                    |
| --------------------------- | ------------------------------------- | ---------------------------------------------------- |
| **同步阻塞开销**                  | 通知过程是直接函数调用，若观察者逻辑耗时，会直接卡死主线程/引发性能掉帧。 | 观察者内部**仅做轻量记录/标记**，或结合**事件队列（Event Queue）**改为异步分发。   |
| **悬挂指针（Dangling Pointers）** | 观察者对象已被销毁，但未从被观察者列表中注销，触发通知时引发内存崩溃。   | 在观察者析构函数（Destructor）中强制调用 `removeObserver()` 进行自我注销。 |
| **隐式耦合与追踪困难**               | 代码流程隐式跳转，难以静态排查调用链。                   | 严格限制通知范围，避免在 `onNotify()` 中直接发起连锁的 `Subject` 事件触发。   |
| **动态内存分配开销**                | 传统的链表/动态数组管理观察者节点会在堆上频繁分配内存。          | **侵入式链表（Intrusive Linked List）**：将链表节点直接内嵌在观察者对象内部。  |

## 四、 进阶演进形态：侵入式链表（Intrusive Linked List）

- **痛点根源**：传统 `Subject` 使用 `std::vector<Observer*>` 或动态链表节点时，每次 `addObserver()` 都会引发堆内存分配（Heap Allocation）。
- **核心机制**：在 `Observer` 基类中直接内嵌入指向下一个 `Observer` 的指针 `Observer* next_`。
- **优势**：  
    1. **零动态内存分配**：内存随着 `Observer` 对象的创建自动就绪。
    2. **内存局部性极佳**：无需额外分配链表节点结构体。
## 五.核心难点 ：侵入式链表（Intrusive Linked List）无分配内存管理

#### 1. 原文痛点与原理
在游戏开发中，`std::vector` 或传统链表会频繁在堆（Heap）上分配节点内存，造成**内存碎片与 GC/分配开销**。
原文提出的解决方案是**侵入式链表**：**直接把 `next_` 指针放在 `Observer` 类内部**。`Subject` 不再拥有独立的数组或链表容器，它只需持有链表头指针 `head_`。
#### 2. 精简代码实现
```C++
class Observer {
    friend class Subject;
public:
    Observer() : next_(nullptr) {}
    virtual ~Observer() {}
    virtual void onNotify(int event) = 0;

private:
    Observer* next_; // 侵入式指针：指向下一个观察者，无需额外分配 Node 结构
};

class Subject {
public:
    Subject() : head_(nullptr) {}

    // 头插法：注册观察者 O(1)，零内存分配
    void addObserver(Observer* observer) {
        observer->next_ = head_;
        head_ = observer;
    }

    // 移除观察者 O(N)
    void removeObserver(Observer* observer) {
        if (head_ == observer) {
            head_ = observer->next_;
            observer->next_ = nullptr;
            return;
        }

        Observer* current = head_;
        while (current != nullptr) {
            if (current->next_ == observer) {
                current->next_ = observer->next_;
                observer->next_ = nullptr;
                return;
            }
            current = current->next_;
        }
    }

protected:
    void notify(int event) {
        Observer* observer = head_;
        while (observer != nullptr) {
            observer->onNotify(event);
            observer = observer->next_;
        }
    }

private:
    Observer* head_; // 仅维护一个链表头指针
};
```
> **局限性**：采用这种最简单的单链表实现时，一个 `Observer` 实例同时只能监听一个 `Subject`（因为只有一个 `next_` 指针）。若需要监听多个，需拓展为双向链表或维护指针数组。

### 核心难点 2：悬挂指针与自动注销（Dangling Pointers & Auto-Unregister）

#### 1. 原文痛点与原理
如果一个 `Observer` 被 `delete` 销毁了，但**没有**从 `Subject` 的列表中移除，当 `Subject` 再次触发通知时，就会解引用野指针导致程序直接崩溃（Crash）。
**解决方案**：在 `Observer` 的**析构函数**中，强制将其从所有（或绑定的）`Subject` 中移除。
#### 2. 结合 RAII 的自动注销示例
```C++
class Subject; // 前置声明

class AutoObserver {
public:
    virtual ~AutoObserver() {
        // 在析构时自动完成销毁与注销，防止悬挂指针
        if (subject_) {
            subject_->removeObserver(this);
        }
    }

    virtual void onNotify() = 0;

    void setSubject(Subject* subject) { subject_ = subject; }

private:
    Subject* subject_ = nullptr;
};

class Subject {
public:
    void addObserver(AutoObserver* observer) {
        // 简化表达：实际可结合前面的侵入式链表
        observers_.push_back(observer);
        observer->setSubject(this); // 建立双向绑定
    }

    void removeObserver(AutoObserver* observer) {
        // 从列表中移除该观察者...
    }

    void notify() {
        for (auto* obs : observers_) {
            obs->onNotify();
        }
    }

private:
    std::vector<AutoObserver*> observers_;
};
```
### 三、 现代 C++ 演进形态：基于成员函数指针 / Lambda（代替继承）
#### 原文与现代对比
原书传统的面向对象观察者必须强制继承 `Observer` 虚接口。在现代 C++ 中，通常使用 `std::function` + 事件 ID 或委托（Delegate）模式替代继承，降低代码侵入性。
```C++
#include <functional>
#include <vector>

class Signal {
public:
    using Callback = std::function<void(int)>;

    // 注册任何可调用对象（Lambda, 成员函数, 自由函数）
    void connect(Callback cb) {
        callbacks_.push_back(cb);
    }

    void emit(int value) {
        for (const auto& cb : callbacks_) {
            cb(value);
        }
    }

private:
    std::vector<Callback> callbacks_;
};

// 使用示例：无需继承 Observer 接口类
int main() {
    Signal onHealthChanged;

    // 直接使用 Lambda 绑定
    onHealthChanged.connect([](int hp) {
        // UI 更新逻辑
    });

    onHealthChanged.emit(80);
}
```
## 六、 现代 C++ 演化：基于委托/回调（Delegates / std::function）

- **传统面向对象缺陷**：强制要求观察者继承自同一个 `Observer` 接口基类，造成类层次结构污染。
- **现代替代方案**：使用 **信号与槽（Signals & Slots）** 或 `std::function` + 事件 ID 实现基于闭包的回调注册，无需显式继承接口类。
