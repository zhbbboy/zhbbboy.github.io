## 1. 本篇是后续开发建议

当前项目提供可运行玩法的代码起点，但本次检索项目源码和模块配置，尚未发现项目层的 `UAbilitySystemComponent`、`UAttributeSet`、Gameplay Ability 或 Gameplay Effect 接入。

目前能看到的是普通 C++ 属性、布尔状态、动画通知、伤害接口和 StateTree：

| 当前内容 | 源码位置 | 与 GAS 的区别 |
| --- | --- | --- |
| `CurrentHP / MaxHP` | Combat 玩家和敌人 | 普通浮点成员，并非 `FGameplayAttributeData` |
| `bIsAttacking` 等 | CombatCharacter | 角色局部状态，不是自动同步的 GAS 状态标签 |
| `Tags.Add(FName("Player"))` | CombatCharacter 构造函数 | Actor Tag，不是 `FGameplayTag` |
| `ICombatDamageable::ApplyDamage` | 战斗接口及具体实现 | 自定义函数调用，并非应用 Gameplay Effect |
| `StateTree` | 两套 AIController 与任务工具 | AI 决策系统，本身不等于能力系统 |

这些系统可以与 GAS 协作。迁移的重点是重新安排职责与数据来源，而不是给现有函数改名。

## 2. 先认识 GAS 中几个对象的分工

| 概念 | 解决的问题 | 在后续 Boss 项目中的例子 |
| --- | --- | --- |
| Ability System Component，ASC | 管理能力、属性关联、效果与标签等能力系统交互 | 玩家或 Boss 的能力执行入口 |
| Gameplay Ability，GA | 一次可激活、结束或取消的行为流程 | 普攻、蓄力、闪避、范围攻击 |
| AttributeSet | 定义与管理数值属性 | Health、MaxHealth、Stamina |
| Gameplay Effect，GE | 对属性或状态施加规则化影响 | 伤害、治疗、消耗、持续效果 |
| Gameplay Tag | 用结构化标签表达状态与条件 | 攻击中、死亡、硬直、技能分类 |
| Gameplay Cue | 表现类反馈的组织入口 | 命中特效、声音等 |

这里列的是未来概念映射，不表示当前已经建立对应类或资源。AttributeSet 与属性的基础机制可参考 [Epic：Gameplay Attributes 与 Attribute Sets](https://dev.epicgames.com/documentation/en-us/unreal-engine/gameplay-attributes-and-attribute-sets-for-the-gameplay-ability-system-in-unreal-engine?application_version=5.7)；效果应用及运行时 Spec 可参考 [Epic：Gameplay Effects](https://dev.epicgames.com/documentation/en-us/unreal-engine/gameplay-effects-for-the-gameplay-ability-system-in-unreal-engine?application_version=5.7)。

## 3. 现有系统怎样映射到后续架构

| 当前职责 | 可保留的基础 | 接入 GAS 时要调整的部分 |
| --- | --- | --- |
| Enhanced Input | IA、IMC、Controller 的本地映射流程 | 攻击输入改为向能力入口发出激活 / 释放请求 |
| CharacterMovement 与相机 | 移动、碰撞、相机组件 | 能力执行期间的移动限制和恢复规则 |
| Montage 与 Notify | 动作资源、命中时间点 | 把动画完成、中断、取消连接到 Ability 生命周期 |
| 命中扫描 | 扫描形状、骨骼位置、目标筛选经验 | 生成目标信息后，通过统一伤害入口应用效果 |
| `CurrentHP` | 现有 UI 和死亡表现逻辑可作参考 | 以 AttributeSet 作为迁移后生命值的唯一来源 |
| `ReceivedDamage` 等蓝图事件 | 特效和受击表现 | 由新的伤害 / 状态变化通知驱动，避免重复触发 |
| StateTree | 敌人决策与阶段行为选择 | 任务请求能力，等待对应执行结果 |
| Controller 重生 | 操作者与身体分离 | 重新建立能力 Actor Info、初始化属性和绑定 UI |

一个未来攻击流程可以设计为：

```text
IA 攻击输入
    ↓
能力激活请求
    ↓
检查状态 / 消耗 / 冷却
    ↓
播放攻击 Montage
    ↓ 动画事件进入命中时机
扫描或收集目标
    ↓
向目标应用伤害 GE
    ↓
属性变化 → 受击表现 / 血条 / 死亡判断
    ↓
Ability 正常结束或取消，释放状态与临时限制
```

这只是推荐的数据流，尚未规定类名、技能资源结构、伤害公式或联机预测方式。

## 4. 最容易接错的边界

### 4.1 同一伤害只能有一条生效路径

若某次命中既调用旧 `TakeDamage` 减少 `CurrentHP`，又应用 GE 减少 Health，就可能造成重复扣血；若同时维护两套数值，则 UI 和死亡判定可能不一致。

建议先定义统一的目标受伤入口。过渡期可以保留旧接口作为适配层，但必须明确：旧对象走旧实现，完成迁移的对象走新的属性与效果实现，同一次命中不能重复结算。

### 4.2 动画播放成功不代表技能最终成功

模板里 `bIsAttacking` 依赖 Montage 结束回调恢复。迁移后至少要区分：能力激活失败、动画播放失败、命中、自然结束、受击取消、死亡取消。

每条结束路径都要恢复临时状态，例如移动限制、重力、输入等待、事件委托和攻击标签。Platforming 冲刺中“设置零重力后等待动画结束”的代码很适合作为检查这类清理工作的例子。

### 4.3 Actor Tag 和 Gameplay Tag 不能直接互换

当前敌人通过 `ActorHasTag(FName("Player"))` 过滤目标和危险源。即使未来建立了类似玩家阵营的 Gameplay Tag，这段判断也不会自动读取它。需要统一目标与阵营筛选入口，再逐步迁移调用者。

### 4.4 决策与动作分别完成自己的工作

StateTree 可以决定“现在选择什么攻击”，Ability 执行“这次攻击怎样开始和结束”。未来的攻击任务应连接到对应能力的完成或取消结果，不宜仅因为“已发送激活请求”就立即报告任务成功。

模板任务退出时解除委托，并不自动停止攻击动画。迁移后应明确 StateTree 离开状态时是否取消能力、什么情况下允许动作继续，以及怎样防止旧回调结束新任务。

## 5. ASC 放在 Character 还是 PlayerState

**当前只记录取舍，不提前确定所有权方案。** 它取决于是否联网、换身体与死亡后哪些状态需要保留等需求。

| 方案 | 倾向解决的需求 | 必须处理的事项 |
| --- | --- | --- |
| ASC 随 Character | 身体销毁后能力状态也随之结束，生命周期较直接 | 新角色生成时重新初始化能力与属性 |
| ASC 放在 PlayerState 等较持久对象 | 希望更换 Pawn 后仍保留部分玩家能力状态 | Owner / Avatar 重新关联、旧 Pawn 清理、客户端初始化及复制策略 |

本项目 Combat 重生会销毁旧 Character 并创建新 Character，因此无论采用哪种方式，都需要在 Possess 与新角色准备就绪的路径上处理能力系统重新关联。

未来需要联网时，还应单独明确服务端伤害权威、能力执行与复制策略、输入预测，以及客户端 UI 读取什么对象。当前代码中多处直接使用玩家索引 0，不能据此宣称已经具备完整多人玩法。

## 6. 分阶段开发路线与每阶段验收

### 阶段一：确认可以稳定复用的模板行为

核对基础地图和 Combat 地图的类配置，运行移动、跳跃、连击、蓄力、受击、死亡、重生和检查点流程。记录角色蓝图、IMC、AnimBP、Montage 及其关键引用。

**验收：** 能从一次按键追到一次伤害，并说明血条和重生分别由谁更新。蓝图待核对项已补充实际值。

### 阶段二：建立最小 GAS 属性闭环

启用所需插件、补充相应模块依赖，建立 ASC 和最小 AttributeSet，只先处理 Health / MaxHealth 初始化及变化通知。ASC 归属要在实现前根据上一节需求确定。

**验收：** 能通过一个受控入口改变 Health，UI 正确刷新；迁移对象不再同时维护两份生命值。此阶段不要求一次性实现所有技能。

### 阶段三：迁移一招普通攻击

保留已有攻击动画与命中时机，把输入、Montage 执行、命中结算、结束和取消连成一个 Ability 流程。伤害通过新的统一入口生效。

**验收：** 单次命中只结算一次；激活失败、播放失败、自然结束、受击和死亡取消都能恢复状态。

### 阶段四：扩展玩家战斗能力

逐项加入连击、蓄力、闪避、体力消耗、冷却和攻击状态限制。每次迁移一个行为，核对旧入口是否仍会绕过限制。

**验收：** 键盘、手柄和触摸等已启用输入都遵守同一能力规则；重复输入和中断不留下失效状态。

### 阶段五：建立最小 Boss 战斗闭环

先让敌人决策稳定选择一招攻击，再扩展追击、攻击前摇、命中窗口、后摇与死亡。Boss 阶段判断可用生命值阈值等明确条件表达，阶段状态由一个确定的数据来源维护。

**验收：** 决策任务能等待招式结束或取消；阶段切换不重复触发、不与死亡冲突；玩家死亡和重试后战斗能恢复初始状态。

### 阶段六：补齐正式游戏流程

按确定的游戏需求加入锁定、胜负 UI、重试、存档以及需要的联网支持。资源初始化、地图切换和重生都要走相同的状态恢复约定。

**验收：** 能反复完成“进入场景 → 开战 → 玩家失败重试 / Boss 死亡胜利”，并验证新增需求下的状态一致性。

## 7. 第一轮 Boss 功能可以如何切分

以下只是后续功能拆分建议，不是本轮新增类型或接口：

| 功能 | 主要责任 | 当前参考 |
| --- | --- | --- |
| 玩家普攻 | 输入、Ability、Montage 和命中 | CombatCharacter 与攻击通知 |
| 玩家闪避 | 移动能力与中断清理 | Platforming 冲刺开始 / 结束 |
| Boss 追击与选招 | AIController、StateTree、目标信息 | Combat AI 任务与 EQS 上下文 |
| Boss 招式 | 独立能力执行与完成通知 | CombatEnemy 的攻击执行与委托 |
| Boss 阶段 | 单一阶段数据来源与转换条件 | 当前没有专用 Boss 阶段系统 |
| 血条与受击表现 | 监听状态变化、展示反馈 | CombatLifeBar 与蓝图事件 |
| 战斗胜负和重试 | 战斗规则与重新初始化 | Controller 重生、Spawner 激活链可作参考 |

不必先把三个变体合并。先选定玩家和敌人的主要实现，再对确实重复的能力抽取公共部分，可以减少蓝图改父类和资源引用迁移的范围。

## 8. 开发前的检查表

- 当前控制的实际 Character、Controller、GameMode 已核对。
- 当前生命值、死亡状态和阶段状态各有明确的数据来源。
- 一次命中从检测到结算只经过一条伤害路径。
- 每个能力都有正常结束、失败和取消的清理行为。
- 重生后旧角色委托不再驱动新角色 UI 或 AI 任务。
- 联网与 ASC 归属按需求单独确定，示例中的玩家索引 0 没有被误当作通用选目标方案。
